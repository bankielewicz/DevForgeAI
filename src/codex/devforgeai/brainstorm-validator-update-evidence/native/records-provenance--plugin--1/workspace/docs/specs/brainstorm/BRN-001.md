# BRN-001 — Better asynchronous stand-ups in Slack

## 1. Context

The user requested: “Brainstorm ideas for a feature that helps remote teams run better asynchronous stand-ups in Slack. No need to check in with me; go straight to the written brainstorm.”

The opportunity is to help teammates share meaningful changes, find relevant context, and get help without coordinating a meeting. A promising concept is **Async Relay**: a short check-in at a person's preferred time, paired with a visible handoff when someone needs help. This is a proposed direction for exploration, not an approved feature scope.

The framework is **diverge-converge**, chosen because the request opens a new feature space without a fixed shortlist. The ten ideas below span personal routines, team coordination, optional automation, and changes to the stand-up process itself.

No interviews, usage data, team details, or delivery constraints were supplied. Problems, severities, and ratings are hypotheses. Questions are recorded rather than asked, as requested. Every idea remains open, and this document remains draft because dispositions and convergence have not been confirmed.

Slack documents interactive messages, modals, and Home tabs through Block Kit, including buttons, menus, and text inputs. Those surfaces provide a basis for exploring a check-in form and help-request actions. [Slack Block Kit documentation](https://docs.slack.dev/block-kit/).

Slack also documents scheduled messages to channels and direct messages. This suggests a possible delivery mechanism for reminders; recurring schedules, working-hour rules, workspace permissions, and reliability still require validation. [Slack scheduled-message documentation](https://docs.slack.dev/reference/methods/chat.scheduleMessage/).

## 6. Convergence

**Proposed direction: Async Relay.** Explore personal check-in windows, a short change-focused update, and an explicit help-request handoff together. All proposed dispositions below are recommendations only. No disposition or convergence was confirmed; every idea retains `disposition: open` and `reason: null`.

| Idea | Proposed disposition | Proposed reason |
|---|---|---|
| BRN-001#IDEA-01 — Personal check-in windows | promoted | Makes participation fit each teammate's working hours. |
| BRN-001#IDEA-02 — What changed check-in | promoted | Offers the strongest estimated benefit for a small change to the daily workflow. |
| BRN-001#IDEA-03 — Help-request handoff | promoted | Tests whether sharing an update leads to timely, clearly owned help. |
| BRN-001#IDEA-04 — Rolling team digest | parked | Add if a pilot shows that reading scattered updates remains a major cost. |
| BRN-001#IDEA-05 — Small prompt library | parked | Learn which prompts work before building a selection system. |
| BRN-001#IDEA-06 — Lighter cadence experiment | parked | Compare after establishing the team's need for regular context. |
| BRN-001#IDEA-07 — Suggested update draft | parked | Validate the manual writing experience before adding sources and automation. |
| BRN-001#IDEA-08 — Assisted catch-up | parked | Establish whether a structured digest is enough before testing generated summaries. |
| BRN-001#IDEA-09 — Cross-time-zone handover | parked | Validate how often work actually passes between time zones. |
| BRN-001#IDEA-10 — Weekly stand-up tune-up | parked | Keep as an optional facilitated practice until there is evidence a product feature would help. |

An illustrative experience for the proposed starting concept:

1. A contributor receives a check-in during their chosen working window. Their last stated focus appears as context, and they can update, snooze, or mark themselves away.
2. They submit: “Changed: finished the mobile mockups. Next: test the checkout flow. Help: need a reviewer for the empty-state copy.” They preview the destination and text before publishing.
3. The update appears in the team's selected stand-up channel. Its help request offers actions such as “I can help” and “Discuss.” A suggested reviewer becomes the helper only after accepting.
4. The helper acknowledges the request and agrees a next action. The requester confirms when it is resolved. Unclaimed requests remain visible for the facilitator's next working window.

Design details to explore with the proposed concept:

- **Low interruption:** one optional follow-up within the chosen window; snooze and away states stop further reminders for that check-in.
- **Clear meaning:** no response means pending or missing, an explicit same-focus response means unchanged, and absence is recorded without requiring a personal explanation.
- **Useful ownership:** acknowledgment and resolution are separate states; a named helper is a suggestion until they accept.
- **Clear audience:** show where an update will be shared before publishing and let its author correct it afterward.
- **Readable interaction:** provide concise text that makes sense without relying on color, emoji, or visual layout alone.

Suggested discovery sequence: first observe a few existing stand-ups with participant permission, then try the three proposed ideas with a volunteer team using facilitator-managed prompts and help tracking. Compare with that team's baseline over comparable working periods. Build an interactive prototype only after the trial identifies where software would reduce effort. This experiment is proposed, not scheduled or authorized work.
