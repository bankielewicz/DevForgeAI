# ADR-001 — Identity provider decision remains open

## Context and status

[PRD-001 section 12](../prd/PRD-001.md) explicitly requires an ADR for the volunteer
identity provider. The same choice affects session revocation (NFR-001). No current
identity tenant, volunteer credential availability, delivery channel, recovery
policy, budget, or provider administration arrangements were supplied. A smartphone
assumption does not establish access to email or an existing identity account.

This record defines the decision boundary and a recommended integration pattern.
**No provider is selected, and this ADR is not accepted.** Technical architecture
work can proceed against the contract in [ARC-001](../architecture/ARC-001.md).

## Options to evaluate

| Option | Benefit | Evidence still needed |
|---|---|---|
| Existing hosted organization identity service, if one exists | Reuse account administration and support | Existence, volunteer access, external-user support, supported login/recovery flow, and operating cost |
| Dedicated hosted customer identity service | Independent volunteer enrollment and recovery | Verified volunteer authentication channel, operator ownership, costs, privacy controls, and tested integration |
| Application-managed credentials on hosted infrastructure | Full local control | Password/recovery and abuse-handling operations would add responsibility; no demonstrated need justifies this for the pilot |

Prefer a hosted identity service behind an adapter with application-owned opaque
sessions. Do not choose a vendor merely to close the PRD marker. The application
is authoritative for roles and revocation regardless of provider token lifetimes.

## Required decision evidence and closure

The implementation decision owner is unassigned. Priya Nair is the PRD owner and
the proposed product contact for enrollment and recovery assumptions; this is not
a claim that she accepted this ADR.

Before changing this ADR to accepted:

1. Record the selected provider, tenant/operator ownership, available volunteer
   sign-in channel, enrollment/account-linking procedure, and recovery procedure.
   Check that existing volunteers can use it from their phone browsers.
2. Confirm the hosted constraint and how provider profile/admin interfaces avoid
   exposing volunteer phone numbers to non-coordinators. Prefer storing volunteer
   contact phones only in the application contact table.
3. Demonstrate callback validation and stable subject mapping through the adapter.
   Record provider-specific configuration and chosen session lifetimes. For the
   proposed authorization-code flow, use the protections described in
   [RFC 9700](https://www.rfc-editor.org/rfc/rfc9700.html#section-2.1.1).
4. Prove that app-session revocation denies every old session within 300 seconds
   across instances, including refresh, delayed callbacks, and silent SSO paths.
   A revoked cookie cannot authorize a new session; distinguish explicit fresh
   sign-in from reuse. Measure from the successful revocation commit. Include
   fail-closed behavior during a session-store outage.
5. Document consequences, cost/operations fit, selected option rationale, actual
   reviewer/decision owner and acceptance date, and link integration evidence.
   Reassess ARC-001 readiness; do not silently mark unexecuted tests as passing.

## Impact while unresolved

- **Direct epic commitment blockers:** FR-001 and NFR-001.
- **Integration dependencies:** FR-002 and FR-003 can be decomposed against the
  local principal/session interface, but cannot pass production acceptance without
  identity and revocation.
- **Cross-cutting constraints:** NFR-002 remains coordinator-only phone visibility;
  NFR-003 remains hosted operation of every component. Neither is waived by the
  provider decision or by deferring the roster feature.

No external service is provisioned and no approval is recorded by this document.
