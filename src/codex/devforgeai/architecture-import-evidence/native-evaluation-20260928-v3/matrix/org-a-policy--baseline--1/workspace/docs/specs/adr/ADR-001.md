# ADR-001 — Use mandated Org A identity with revocable application sessions

## Context and authority

[PRD-001](../prd/PRD-001.md) asks for an identity-provider ADR for FR-001 and requires administrator revocation of volunteer sessions within five minutes (NFR-001). [POL-001 SET-01](../policy/POL-001.md) mandates Org A Identity Platform (OIDC), with no product override. It cites organization ADR-104, which is not supplied here. The available authority is the approved vendored policy; no claim is made to have reviewed ADR-104.

The PRD change log's earlier default of no mandated platform is superseded for this assessment by the effective organizational setting. Selecting a provider is therefore constrained, not an unresolved vendor choice.

## Decision

Use **Org A Identity Platform (OIDC)** for volunteer sign-in. Do not implement password authentication or substitute another provider. This part of the decision follows approved policy; the local session design below is proposed and has no recorded approval yet.

Integrate sign-in at the backend using the platform-supported authorization-code flow with PKCE. Map verified issuer/subject to provisioned application principals. Keep product roles and authorization server-side unless the platform contract supplies an authoritative role source that is explicitly adopted.

Issue opaque application session cookies backed by the managed database. Each session records the principal's generation at issuance. Validate that generation on every protected request against the authoritative primary. Administrator revoke-all increments the generation atomically; old sessions become invalid after commit without waiting for an identity token to expire. Fail closed if validation is unavailable. See [ARCH-001 sections 3–4](../architecture/ARCH-001.md) for races, request bounds, access rules and data boundaries.

This application session mechanism does not run a separate identity provider or accept local credentials. It implements product authorization and the PRD's bounded revocation requirement. It does not promise platform-wide SSO logout or blocking future sign-in.

## Considered approaches

| Approach | Disposition | Reason |
|---|---|---|
| Org A identity plus server-validated application sessions | Selected design | Honors mandated authentication and gives the application control of existing-session invalidation. |
| Org A identity with independently valid browser bearer tokens only | Not selected | No supplied platform evidence establishes revocation within five minutes; token validity alone cannot establish the requirement. |
| Local passwords or another identity provider | Ineligible | Conflicts with the non-overridable policy. There is no authorized product exception. |

## Consequences and validation

Every authenticated request requires a database validity check. Database unavailability denies access, and the service must support session cleanup and revocation auditing. This trades an extra authoritative read for a revocation design that does not depend on undocumented platform behavior. Capacity is small enough to begin with one hosted service and database; measure the actual workload before adding caches that could weaken revocation.

GAP-03 in ARCH-001 tracks platform onboarding and integration evidence: volunteer account eligibility, issuer/discovery and client configuration, registered callbacks, supported code flow, claims, account/role provisioning and logout semantics. Verify sign-in and invalid callback rejection in a test tenant. Test multi-device revocation, concurrent session creation, authorization races and failure handling against the 300-second limit. Until then, runtime evidence is **NOT_RUN** and platform integration is **BLOCKED**; the mandated provider choice remains resolved.

Compliance and accessibility gaps GAP-01/GAP-02 also gate epic handoff, including the hosted identity experience. This ADR neither creates those missing requirements nor waives them. If platform capabilities conflict with the requirement, record the conflict for the platform and PRD owners; do not quietly change provider or weaken NFR-001.
