# ADR-002 — Hosted application, sessions and bookings

## Context

[PRD-001](../prd/PRD-001.md) describes approximately 120 volunteers, one coordinator and three daily shifts. There is no on-site server. Booking must not produce an unusable roster through duplicate or excess reservations. Revocation and phone visibility are mandatory shared constraints, even if the coordinator roster feature is deferred.

## Decision

Use a single hosted application with identity/session, booking and roster modules and a hosted relational database. Accept this as the technical architecture baseline for the requested design; this status does not claim stakeholder approval, purchased services or tested implementation. Leave the identity vendor unresolved in [ADR-001](ADR-001.md).

Keep sessions and roles server-authoritative. An opaque browser cookie identifies a database-backed session. Check its generation and current roles on each protected request; an administrator increments the volunteer's generation to revoke existing sessions. Fail closed when authoritative state is unavailable. Serialize protected booking commits against revocation; invalidate restored sessions before reopening service after recovery.

Use a transaction and per-shift lock to enforce capacity, with a unique volunteer/shift booking constraint for retries. Read the primary database for the coordinator's roster, initially using polling instead of push delivery.

Keep phone data separate from general volunteer projections and authorize every contact read for the coordinator role. Administrator is a separate permission for revocation, not an implicit contact reader. Use hosted services for the entire runtime and protect service credentials and backups.

## Alternatives and consequences

| Alternative | Reason not selected |
|---|---|
| Separate booking, roster and authorization microservices | Adds deployment and consistency boundaries without a demonstrated scale requirement |
| Browser directly accessing general-purpose data APIs | Expands the authorization surface and complicates central session revocation and contact projection controls |
| Long-lived self-contained access tokens checked only for signature/expiry | Cannot by itself establish administrator-driven revocation within five minutes |
| Eventually consistent booking writes | Makes last-place capacity and immediate roster reads harder to guarantee |
| WebSocket roster updates | Adds persistent connection authorization/revocation work without a specified push-latency requirement |
| On-site application or database | Conflicts with the whole-product NFR-003 constraint |

The application and database become shared availability dependencies; failure must produce explicit errors, never authorization bypass or false booking success. Per-request authoritative checks and shift locking cost database work but simplify the required invariants at pilot scale. Polling is simpler to operate but leaves a bounded refresh delay chosen during refinement. Hosted provider, language/framework, region and operational objectives remain implementation planning choices; no vendor capability is assumed.

## Verification

The requirement-to-evidence matrix in [ARCH-001](../architecture/ARCH-001.md) defines the acceptance checks. Concurrency, revocation, role/field authorization, local-date handling and hosted deployment must all be tested against the eventual implementation. Architecture acceptance is not runtime verification.
