# ADR-001 — Reuse the current auth service

## Context and authority

[PRD-001](../prd/PRD-001.md) requires volunteer sign-in (FR-001), administrator
revocation effective within five minutes (NFR-001), and hosted services for the
whole product (NFR-003). Its section 12 requests an identity-provider ADR.
On 2026-09-28 the user directed: “For sign-in, reuse our current auth service.”
This accepts the reuse decision; it does not certify undocumented capabilities.

## Decision

Integrate the current auth service through the server-side adapter described in
[ARCH-001](../architecture/ARCH-001.md). Retain that service as the identity and
credential authority. Do not introduce a replacement identity provider or build
a separate password/recovery system. Keep booking/roster authorization in the
application and bind every protected operation to a currently valid session.

Use authoritative session checks on every protected request as the initial
revocation design, with no positive-status application cache. Require an
end-to-end invalidation bound of at most 300 seconds, including upstream
propagation and request processing. Expiry or offline token validation alone
does not establish that bound. Administrator revocation must invalidate all
existing sessions and their refresh paths.

## Integration gate and missing evidence

The supplied repository contains no current-service name, implementation,
protocol, endpoint definitions, session policy, or hosting evidence. These are
unresolved integration details, not assumed service features. Before binding
the adapter, the implementation owner must obtain and test:

| Evidence | Acceptance condition |
|---|---|
| Service contract and test environment | Verified sign-in flow, stable issuer/subject identifiers, credential/session validation and failure semantics |
| Revocation administration contract | Authorized administrator can invalidate every existing volunteer session, including refresh credentials; action is auditable |
| Freshness and propagation behavior | Measured and documented total bound at most 300 seconds, across instances/devices and under failures; no refresh resurrection |
| Hosting topology | The current auth service runs on hosted infrastructure without an on-site dependency |
| Claims and role handling | Application receives only necessary identity data, trusts an authoritative role source, and does not expose phone claims to volunteer browsers |

If the service lacks an authoritative status check, stop implementation of the
affected adapter until an equivalent mechanism is designed and verified. Options
within reuse include adding service-backed session state or a revocation/version
check to the current service. Such an extension needs its own concrete contract
and tests; it is not assumed to exist. If no compatible extension is feasible,
record the conflict against NFR-001/NFR-003 and seek a later scope decision. The
current instruction does not authorize replacing the service or relaxing either
requirement. Architecture documentation can proceed; pilot release cannot pass
these gates without evidence.

## Alternatives and consequences

A new managed identity provider or custom authentication implementation would
duplicate identity infrastructure and conflict with the user's reuse direction.
They are not selected. Pure offline validation with long-lived credentials would
leave revocation unproven and is also not selected.

Reuse preserves the existing account lifecycle and administration workflow, but
introduces a runtime dependency on auth availability and session-check latency.
Failing closed during auth outages may temporarily prevent booking and roster
access. Integration work must establish this service's actual capabilities before
claiming compliance. The PRD identity-provider choice is resolved; the service's
technical compatibility remains explicitly unverified.
