# ADR-001 — Volunteer identity provider

## Context

PRD-001 explicitly requests an identity-provider ADR for FR-001. It specifies
browser sign-in but no provider, existing tenant, email access, credential method,
or enrollment/recovery process. Smartphone access alone does not resolve these.

## Proposed direction and alternatives

Use a hosted identity service behind a server-side adapter, with local application
sessions and roles as specified in [ADD-001](../add/ADD-001.md). Prefer an existing
compatible hosted identity tenant if one exists; otherwise evaluate a managed
provider with a browser redirect protocol such as OIDC. No particular provider
or login method has been selected or validated.

| Option | Benefit | Limitation |
|---|---|---|
| Existing hosted organization identity | May reuse account operations | No tenant or volunteer eligibility is established |
| New managed identity provider | Moves credential lifecycle to a hosted service | Requires usable enrollment/recovery, cost and operational fit to be established |
| Application-owned credentials or custom magic links | Direct control of login experience | Adds credential/recovery/delivery responsibilities; not justified for this pilot |

The application must not depend on provider-wide logout timing to meet NFR-001.
Identity proves who signed in; the local session gate decides whether a request
is still authorized. Phone numbers stay out of identity claims and profiles.

## Resolution evidence

The implementation owner, with product-owner input on volunteer access, records:

1. Selected provider and supported volunteer/staff credential method, enrollment,
   account recovery, and stable external identity mapping. Establish whether an
   existing tenant can serve these users; do not assume email or SMS availability.
2. Current official provider documentation and a hosted callback proof showing
   valid sign-in, rejection of invalid/replayed responses, and safe account mapping.
3. A two-browser demonstration that local revocation rejects old application
   sessions independently of an identity-provider session. Include in-flight
   login completion and refresh paths so they cannot resurrect old sessions.
4. Hosted deployment fit and an operating cost/ownership record for the pilot.
   Confirm the selected flow requires no volunteer phone data in the provider.

Then update this ADR with the decision, alternatives rejected, evidence, and date,
and reassess FR-001 in ADD-001. No provider research, credentials, or integration
evidence is claimed by this document.

## Effect on readiness

FR-001 is BLOCKED for epic definition because its actual sign-in journey is
unresolved. FR-002 and FR-003 may be decomposed against the authenticated-account
contract, and NFR-001 may be decomposed against the local session contract. Their
end-to-end delivery still depends on the eventual provider integration. NFR-002
and NFR-003 remain mandatory selection constraints, not reasons to waive D-01.
