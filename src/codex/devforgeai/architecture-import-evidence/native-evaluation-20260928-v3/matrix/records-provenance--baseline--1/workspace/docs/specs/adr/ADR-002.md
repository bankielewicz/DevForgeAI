# ADR-002 — Hosted modular monolith and transactional booking

## Context and design decision

The pilot has about 120 volunteers and a coordinator, and NFR-003 prohibits an
on-site server dependency. Use a single hosted application and managed relational
database. Separate identity/session, booking, and roster responsibilities in code.
All application data access is server-side. Keep application instances stateless
apart from shared authoritative database state.

Use a database transaction and a per-shift lock for capacity checks and booking
insertion, plus a unique volunteer/shift constraint for retries. Require every
writer that can change availability to follow this protocol. Read roster data
from the primary database to avoid replica lag after successful bookings.

## Alternatives and consequences

Microservices would add deployment and consistency boundaries without a stated
need. Browser-to-database writes would expand the authorization surface. An
eventually consistent booking queue would complicate the promise of booking an
open shift. None is part of this design.

The central database is an availability dependency; failures must be visible and
must not produce false booking confirmations. Managed backups and a restore
exercise are required before rollout. Select a hosting vendor/region and record
retention and recovery settings during the foundation epic. This ADR chooses a
deployment shape, not a purchased service, price, or availability guarantee.

## Verification obligations

Compete for the last place from separate transactions; assert no overbooking.
Retry a committed request whose response was lost; assert one booking. Verify
closed/past shifts reject new bookings and an empty day has a valid empty roster.
Inspect deployment dependencies to show every runtime service is hosted. Verify
backup restoration using synthetic data before the pilot.

The architectural contract is sufficient for epic definition. Runtime evidence
is NOT_RUN because no implementation is present. See
[ADD-001](../add/ADD-001.md) for requirement-level dependencies and assumptions.
