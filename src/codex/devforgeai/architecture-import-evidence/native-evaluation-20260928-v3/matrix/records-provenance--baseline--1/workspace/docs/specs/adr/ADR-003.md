# ADR-003 — Authoritative sessions and coordinator-only contact access

## Context and design decision

NFR-001 requires an administrator to revoke a volunteer's sessions within five
minutes. NFR-002 allows only the coordinator to see volunteer phone numbers.
Both are server-side, cross-cutting constraints.

Issue an opaque local session secret in a protected cookie after verified sign-in;
store only its hash, account ID, expiry, and account session generation. Every
protected request reads authoritative state from the primary database and checks
current roles. Never trust a browser-supplied role or a cached positive decision.

An administrator revokes all existing sessions by atomically incrementing the
target account's generation. Return success after commit and record a security
audit event without secrets or contact values. Old session generations fail on
every instance. Database failures deny protected access. Session refresh must
revalidate the old session; it must never update an old session to a new generation.

At sign-in initiation, associate the attempt with the current local account
generation when known; otherwise retain its server-side initiation time and check
against the account's latest revocation time at completion. Store that revocation
time alongside generation. Serialize session issuance and revocation on the
account row so a concurrent callback cannot create a fresh valid session from a
pre-revocation attempt. Fresh authentication initiated after revocation may create
a new session; permanent account suspension is a separate policy.

Enforce a 60-second maximum protected-request lifetime, including database work,
so work admitted before revocation cannot continue past the five-minute bound.
The implementation must demonstrate actual cancellation, not merely a proxy
timeout while backend work continues. No protected background streams are planned.

Store phone contacts separately from general account data. Only a coordinator
authorization check permits the contact query and projection. A volunteer cannot
read their own stored phone through this product; an administrator needs the
coordinator role to read any phone. An account with both roles is authorized by
its coordinator role. Use `no-store` responses and omit phone values from logs,
traces, analytics, exceptions, and nonproduction fixtures.

## Alternatives and consequences

Provider logout alone would tie the five-minute promise to an unselected external
service. Long-lived self-contained application tokens without an authoritative
revocation check would not implement this design. Checking the database on each
request costs a query and makes it an access-availability dependency; that is an
explicit tradeoff at this pilot's scale.

UI-only phone hiding still exposes the API payload and is rejected. Application
administration must not imply contact access. Infrastructure maintenance access
is separate from product roles: restrict and audit privileged database/backup
access, and do not offer raw contact browsing through routine support tooling.

## Verification obligations

Revoke two active browser sessions; replay each against every protected route
immediately and at/after five minutes. Include session refresh, concurrent login
callbacks, multiple app instances, database outage, and slow in-flight requests.
Prove that unauthorized revocation fails and successful revocation is audited.

Exercise anonymous, volunteer, administrator-only, coordinator, and combined-role
accounts. Inspect raw API responses, server-rendered HTML, errors, caches, and
telemetry for a synthetic phone marker. Only coordinator-authorized contact
responses may contain it. Verify role removal takes effect at the next request.

These obligations are ready to become epic acceptance criteria. Their runtime
status is NOT_RUN; the selected-provider cases depend on ADR-001.
