# ADR-001 — Volunteer identity provider selection

## Status and decision scope

**Proposed; provider selection unresolved.** This records the explicit identity decision requested
by [PRD-001 section 12](../prd/PRD-001.md). No provider is selected, approved, purchased, or assumed
to be mandated. [POL-001](../policy/POL-001.md) explicitly leaves that choice to the product.

The proposed architectural boundary is managed hosted identity plus application-owned sessions,
as defined in [ARC-001](../arc/ARC-001.md). This boundary permits booking and roster epic planning
while preserving the open provider decision. It is not evidence that a vendor meets the PRD.

## Context and options

Volunteers need browser sign-in, but the supplied PRD does not establish existing organization
accounts, available email/SMS channels, enrollment restrictions, recovery needs, a budget, or an
identity operations owner. Assuming any one of these could exclude volunteers from the pilot.

| Option | Fit and tradeoff | Disposition |
|---|---|---|
| Hosted managed identity service, integrated through a server-side adapter | Keeps credential handling outside the application; requires supported volunteer sign-in/recovery channels and viable operating terms | Preferred architectural direction; exact provider and sign-in method pending evidence |
| Existing organization identity tenant, if one exists | Could reuse account administration; volunteer eligibility, provisioning, and account availability are unknown | Candidate only if an existing usable tenant is established |
| Build and operate credential storage/recovery in the application | Adds credential and recovery implementation/operations to the small pilot | Not recommended for this scope; no PRD need justifies that additional responsibility |

No vendor comparison is claimed. Provider documentation and a small integration check will be
needed when actual candidates and sign-in channels are known.

## Selection constraints and closure evidence

The decision owner is the PRD owner, Priya Nair; an identity operator must be named before launch.
Close this ADR by recording a selected provider and sign-in method, the reasons alternatives were
rejected, and the following evidence:

1. Enrollment and recovery work for the intended volunteers on mobile browsers, with an explicit
   account-provisioning model. Confirm whether public registration or an existing-volunteer list
   is intended; do not infer that every person with a successful sign-in may book.
2. Official provider documentation and a test integration show validated identity exchange and a
   stable issuer/subject mapping. Roles remain authoritative in the application database.
3. Existing application sessions can be invalidated centrally within five minutes across instances.
   A provider cookie, token refresh, or replay cannot silently resurrect the revoked application
   session. A new completed sign-in may establish a new session; account suspension is out of scope.
4. Integration does not expose stored phone numbers to volunteers, including through provider
   claims/profile surfaces linked by the product. Omit phone synchronization when it is unnecessary.
5. The service is hosted and its ongoing cost, operating access, configuration, and recovery
   responsibilities are documented for the pilot. No on-site identity infrastructure is required.

Record the decision outcome and review evidence here, then update ARC-001's FR-001 readiness row.
Do not convert this proposal into an accepted decision solely because the architecture is written.

## Consequences and affected requirements

- **FR-001:** blocked for final epic definition until provider and enrollment/sign-in method are
  decided. A bounded discovery task can gather closure evidence now.
- **NFR-001:** its application-session mechanism is defined and ready to attach to all protected
  functional epics. End-to-end verification still depends on the selected provider integration.
- **NFR-002 and NFR-003:** mandatory provider-selection constraints as well as cross-cutting
  application requirements; neither may be deferred or weakened to accommodate a provider.
- **FR-002 and FR-003:** ready for epic decomposition using the stable identity/session contract.
  Their integrated delivery depends on FR-001. Reassess them if a decision changes that contract.
