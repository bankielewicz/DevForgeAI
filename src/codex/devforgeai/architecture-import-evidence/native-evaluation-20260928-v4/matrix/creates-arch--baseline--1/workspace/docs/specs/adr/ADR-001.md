# ADR-001 — Hosted identity provider

## Context and status

[PRD-001](../prd/PRD-001.md) explicitly requires an identity-provider ADR for
FR-001. No provider, existing organization account, volunteer email availability,
budget, or enrollment/recovery process is supplied. NFR-001 additionally requires
administrative session revocation within five minutes. Smartphone access does
not establish an available email account or consent to a particular login method.

**No provider is selected.** This ADR remains proposed and blocks FR-001 and
NFR-001 epic readiness. The user authorized architecture work without questions;
that permits defining contracts and recording gaps, but supplies no evidence for
inventing the missing organizational inputs.

## Alternatives and decision criteria

| Alternative | Fit and unresolved evidence |
|---|---|
| Hosted identity provider through a standards-based adapter | Preferred direction; keeps credential handling outside the application. Must establish suitable volunteer login channels, enrollment, recovery, costs, and session replay behavior. |
| Existing organization identity tenant | Reuse only if one exists and can admit all volunteers with workable account recovery. Neither fact is known. |
| Application-owned passwords on hosted infrastructure | Could satisfy hosting, but adds password storage, recovery and abuse-control responsibilities. Not selected for this small pilot. |

The intended architecture uses provider-independent opaque application sessions,
as described in [ARCH-001](../architecture/ARCH-001.md). Provider authentication
must never bypass the application's revocation or role checks. Avoid using
volunteer phone numbers as public identity/profile attributes; phone access
remains coordinator-only. A phone-based provider integration would require an
explicit privacy review against NFR-002 before selection.

## Closure evidence

Proposed decision owner: Priya Nair (PRD owner), supported by the implementation
lead. This assignment is a recommendation, not a claim of their acceptance.
Resolve the following in this ADR before marking it decided:

1. Record the usable login channel, eligible volunteer enrollment process,
   account recovery policy, and how coordinator/administrator roles are assigned.
2. Name the hosted provider and integration method; verify required capabilities
   against its current official documentation and record deployment/budget fit.
3. Demonstrate mapping of verified issuer/subject to the enrolled volunteer,
   denied unknown users, protected callbacks, and safe session issuance.
4. Demonstrate two signed-in devices and multiple application instances: after
   administrator revocation, every old session fails within 300 seconds. Exercise
   refresh, silent sign-in and callback replay; an old session must not silently
   obtain a new valid product session. Define how fresh authentication may resume
   access and how issuance races with revocation are ordered.
5. Record selected alternative, rejected alternatives, evidence and decision
   owner; update the readiness rows in ARCH-001. Preserve the PRD's original
   open marker until its normal revision workflow updates it.

No provider-specific capability has been verified and no identity proof of
concept has been run. Booking and roster decomposition may proceed against the
defined principal/session interface, with explicit delivery dependencies.
