# ADR-001 — Identity provider selection

## Status and context

Unresolved, blocking FR-001 epic readiness. PRD-001 explicitly marks identity-provider selection as needing an ADR. There is no evidence of an existing organizational identity tenant, volunteer account availability, a supported sign-in method, or an approved provider in the supplied workspace. “Proceed without questions” permits recording this gap; it does not establish those facts.

The required architectural boundary is defined: a hosted identity service produces a verified stable identity through a server-side adapter, and the application issues and validates its own sessions as specified by [ARCH-001](../architecture/ARCH-001.md) and [ADR-002](ADR-002.md). Provider selection remains open. No named vendor is selected or claimed to have been evaluated.

## Alternatives and tradeoffs

| Alternative | Benefits | Unresolved costs or fit |
|---|---|---|
| Existing organization-hosted identity tenant | Reuses existing account operations if available | Tenant existence, volunteer access, external-user support, and coordinator administration are unknown |
| Dedicated hosted identity service | Separates volunteer identities from staff infrastructure | Requires a supported sign-in/recovery method, account setup, service ownership, and cost review |
| Application-managed passwords on hosted infrastructure | Direct control over identity lifecycle | Adds password storage, recovery, abuse prevention, and support responsibilities; not preferred for the pilot |

Prefer a managed hosted identity service with a standard server-side authentication integration. Choose between the first two alternatives after the missing evidence is available. Do not assume all volunteers have email, SMS access, or an existing federated account merely because ASM-01 mentions smartphones. Phone-based authentication also needs a privacy assessment against NFR-002; it is not the default.

## Evidence needed to close this decision

Record the following in a revision of this ADR, with the selection and rationale:

1. The chosen provider, supported mobile-browser sign-in method, available volunteer credentials, and a workable account onboarding and recovery process.
2. Who operates the tenant and provisions volunteer, coordinator, and administrator accounts. Application roles remain locally controlled; administrator status alone does not grant contact access.
3. Provider documentation and a small integration check establishing verified issuer/subject mapping, callback/request validation, rejected invalid or expired results, logout/session behavior, and no unintended phone exposure.
4. Compatibility with application-owned session issuance and revocation, including no silent renewal of revoked sessions; confirmation that every runtime dependency is hosted.
5. Service ownership and acceptable pilot costs/configuration. No budget, regional residency, or procurement approval is inferred from the PRD.

Proposed decision owner: Priya Nair as PRD owner, with an implementation owner to supply the technical evidence. This is an ownership proposal, not a recorded approval or an assignment sent to anyone.

## Requirement effects

| Requirement | Effect while unresolved |
|---|---|
| FR-001 | Direct blocker: provider-specific sign-in behavior and acceptance tests are not defined |
| FR-002, FR-003 | Integrated delivery waits for FR-001; decomposition and local behavior testing can use the stable session/role contract |
| NFR-001 | Epic-ready through authoritative application sessions; selected-provider integration still requires verification |
| NFR-002 | Epic-ready through contact isolation; provider onboarding and claims must also be checked for phone disclosure |
| NFR-003 | Epic-ready as a whole-product constraint; chosen identity service must appear in the hosted deployment inventory |

The marker in the approved PRD remains unresolved. This ADR records the decision gate rather than silently clearing it. No user response is required to complete the architecture and readiness assessment.
