# ADR-002 — Session authority and contact isolation

## Decision

Use application-owned opaque sessions validated against a hosted relational database on every protected operation, plus locally assigned roles and a separately accessed contact record. This is a defined architecture proposal for epic decomposition; stakeholder approval and runtime verification have not occurred.

NFR-001 requires an administrator to revoke signed-in sessions within five minutes. NFR-002 allows only the coordinator to see phone numbers. NFR-003 requires these controls to run on hosted services. The system should enforce these requirements independently of the unresolved identity-provider choice.

## Session enforcement

Store only a hash of the browser's random session credential. A session carries the user's session generation at issuance; the authoritative user record holds the current generation. Session validation requires an active user, an unexpired and unrevoked session, and equal generations. Use primary/strongly consistent reads for authorization, with no positive authorization cache or replica-lag dependency.

An authorized revocation increments the user's generation atomically. Report success only after commit; a failed transaction is a failed revocation. Every session issued under a previous generation becomes invalid across all instances. This targets immediate rejection after commit and is stronger than the PRD's five-minute bound. Record the request and commit times for verification; a revocation request must not be reported successful while queued indefinitely. A failed operation must surface a retryable error.

For race handling, session issuance binds to the generation captured when the sign-in attempt starts and refuses issuance if it has changed. A previously initiated login callback cannot mint a new session after revocation. Existing session cookies cannot silently refresh into a new generation. A deliberate new sign-in can authenticate again; NFR-001 does not request account suspension or identity-provider-wide logout.

For mutations, revalidate session state inside the write transaction and hold a lock on the user authorization record until commit, using the same lock discipline as revocation. Thus a mutation either commits before revocation or observes the revoked generation and fails. Set bounded request/transaction deadlines well below five minutes (proposed pilot default: 30 seconds). For sensitive reads, recheck authorization before returning data. Do not hold long-lived streams with a single initial authorization check. Data already delivered to a browser cannot be recalled; the requirement is enforced on subsequent access, not by claiming remote erasure.

If the authoritative store is unavailable, deny protected access with a service error; never fall back to trusting a cookie or provider token. Log revocation actor, target local ID, timestamp, and outcome without session credentials or contact values.

## Contact enforcement

Only coordinator-authorized application paths may load or return a phone number. Volunteer and administrator-only paths must neither query nor serialize contact records. Use explicit DTO/field allowlists and generic errors. Keep phone values out of telemetry, audit events, URLs, browser preload data, and shared caches. Coordinator data is non-cacheable and cleared from the UI on logout or access failure. Trusted data setup must use coordinator authorization if it displays phone values.

The access rule applies to application users; it does not imply encryption makes database operators technically incapable of accessing data. Restrict and audit infrastructure access and backups, and avoid routine operator exposure. If the intended requirement includes cryptographic exclusion of hosting operators, that is a material scope change requiring a separate design; the current PRD gives no such requirement.

## Alternatives considered

| Alternative | Reason not selected |
|---|---|
| Standalone provider bearer tokens accepted until expiry | Cannot establish the revocation deadline without knowing provider lifetime and revocation behavior |
| Provider revocation API as the application's only control | Couples NFR-001 to an unresolved provider and its propagation guarantees |
| Cached session validation | Adds invalidation and delay failure modes unnecessary at this pilot's scale |
| Phone filtering only in the browser | Sends restricted data to unauthorized users before hiding it |
| Administrator inherits all coordinator permissions | Violates the coordinator-only contact rule for administrator-only users |

## Consequences and verification

Each protected request needs a database authorization read; the database becomes an access-control availability dependency. This is an explicit simplicity tradeoff for the pilot. The identity provider can change behind the adapter without changing booking authorization or the contact rule.

The verification matrix in [ARCH-001](../architecture/ARCH-001.md) requires multi-session and cross-instance revocation tests, adversarial role tests, race tests, and phone-value leakage checks. No implementation exists yet, so those tests are NOT_RUN. These are required acceptance evidence for future epics, not proof supplied by this decision record.
