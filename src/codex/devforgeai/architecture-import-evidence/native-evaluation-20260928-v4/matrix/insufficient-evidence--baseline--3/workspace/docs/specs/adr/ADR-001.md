# ADR-001 — Reuse the current auth service

## Context

[PRD-001 §12](../prd/PRD-001.md) requests an identity-provider decision for FR-001. The user explicitly directs reuse of the current auth service. The workspace contains no code, configuration or contract identifying that service or establishing its capabilities.

## Decision

Reuse the current auth service for volunteer sign-in. Integrate it through the backend adapter defined in [ARCH-001](../architecture/ARCH-001.md), preserving the service's supported login and account-management mechanisms. Do not introduce another provider or a local password database.

The provider-selection decision is accepted on the user's authority. Acceptance does **not** assert technical compatibility or approve the entire architecture. Protocol, endpoints, SDK, stable identity format, session linkage and deployment location remain to be verified from the existing service.

## Required integration properties

- FR-001: establish a verified, stable identity that maps to a provisioned volunteer.
- NFR-001: administrators can revoke all signed-in sessions for a volunteer; protected access, including refresh/replay paths, stops within 300 seconds of successful revocation. The proposed adapter checks authoritative session status on every protected request and fails closed when status is unavailable. Actual propagation and in-flight delays must fit the deadline.
- NFR-002: phone numbers reach only the coordinator-authorized product surface. Auth claims or profile payloads must not bypass application field restrictions.
- NFR-003: the reused service, like every other production component, must run on hosted infrastructure.

## Alternatives and consequences

A new identity provider would contradict the current direction and add migration and operational work. Local password authentication would duplicate the existing service and add credential-management responsibility. Neither is selected.

Reuse keeps credentials and account lifecycle with the existing service. Authoritative request validation introduces a runtime dependency on its latency and availability; an outage blocks protected operations. A single adapter contains protocol-specific details while the application owns booking and roster authorization.

If the service cannot satisfy revocation, privacy or hosting requirements, record the concrete incompatibility and revise the integration design within the reuse constraint. Do not silently weaken a mandatory PRD requirement, assume short-lived tokens prove revocation, or switch providers. Implementation/release of the affected capability remains blocked until compatibility is established. The approved PRD's historical open-question text is unchanged; this ADR records its resolution and remaining technical evidence needs.

## Validation

Use the FR-001 and NFR-001–003 evidence in ARCH-001's acceptance matrix. Capability verification is currently BLOCKED by missing service artifacts; no auth tests have run. This is an architecture decision, not an implementation or deployment claim.
