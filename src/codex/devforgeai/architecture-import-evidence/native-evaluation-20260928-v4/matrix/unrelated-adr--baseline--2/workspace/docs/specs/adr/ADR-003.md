# ADR-003 — Enforce coordinator-only phone access in the backend

## Context and decision drivers

FR-003 needs the coordinator's daily roster. NFR-002 restricts volunteer phone numbers
to the coordinator, including when an administrator is managing sessions. Hiding a field
in a page would leave API responses, logs and other data paths exposed.

## Considered options

1. Backend role checks and separate contact-data access: explicit, testable protection.
2. UI-only hiding: insufficient because callers can inspect responses or invoke APIs.
3. Give all administrators contact access: conflicts with NFR-002 unless they also hold
   the coordinator role.

## Proposed decision

Use explicit `volunteer`, `coordinator` and `administrator` role grants stored server-side.
Default deny; never accept roles from the client. An administrator can revoke sessions,
but can read phone numbers only if separately granted the coordinator role. The same
person may hold multiple roles; neither role automatically implies the other.

Keep phone numbers in `VolunteerContact`, separate from volunteer identity and bookings.
Only a dedicated coordinator contact query may read them. Use separate database permissions
for that query path; ordinary booking, session and roster-name queries cannot read the
contact table. The browser has no direct database access. Database maintenance credentials
are operational secrets, not permissions granted by the application administrator role.

The daily coordinator roster joins committed bookings to volunteer display names; a
coordinator-only contact projection can add phone numbers. All other responses use
explicit allowlists that omit phones, including a volunteer's own profile. Return a
denial before accessing contact data for anonymous, volunteer or administrator-only callers.

Disable shared caching and use `Cache-Control: no-store` for authenticated sensitive
responses. Do not put contact data in URLs, analytics, logs, errors, tokens or browser
persistent storage. Use allowlisted structured logging with no request/response bodies.
ADR-001's 30-day retention remains in force for those redacted application logs.

Roster and contact authorization uses current roles and the session checks of ADR-002
on every request. Privileged roles are provisioned through a restricted operational
procedure; no public role-assignment endpoint or role-management product is added here.

## Consequences and acceptance prerequisites

- Separate query permissions and projections require explicit integration tests.
- Coordinator roster queries can remain small and synchronous at the pilot's scale.
- Confirm who provisions the coordinator and administrator roles, and how existing
  contact records are supplied. These operational inputs must not become public sign-up.
- Phone protection applies across the whole application, including diagnostic paths.

## Confirmation

Carry V-03 and V-05 from [the architecture assessment](../architecture/PRD-001.md#verification-contracts)
into epic acceptance criteria. Test anonymous, volunteer, administrator-only and coordinator
callers against direct endpoints. Verify response bodies, rendered HTML, database query
permissions, caches and logs with a recognizable synthetic phone number.
