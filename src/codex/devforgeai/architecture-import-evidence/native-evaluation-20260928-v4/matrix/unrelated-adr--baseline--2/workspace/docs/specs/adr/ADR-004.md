# ADR-004 — Run one hosted application with a managed relational database

## Context and decision drivers

The product serves about 120 volunteers and three shifts per day. NFR-003 applies to
the whole product: no service can depend on an on-site server. Booking consistency and
session revocation need authoritative shared state, while FR-003 needs a current roster.

## Considered options

1. One hosted application plus managed relational database: few moving parts and shared
   transactions for capacity, bookings and sessions.
2. Separate identity, booking and roster application services: adds distributed-state
   coordination without a requirement demanding those boundaries.
3. Browser-only application accessing a database directly: complicates privileged contact
   access and consistent session revocation enforcement.
4. On-site hosting: incompatible with NFR-003.

## Proposed decision

Deploy a mobile-first web UI and backend as one application on a managed hosting service.
Use hosted PostgreSQL-compatible storage for application state, hosted Auth0 for identity
(ADR-002), and the hosting provider's log service with 30-day retention (ADR-001).
Use managed TLS, secrets and backups. No runtime, identity service, database, log collector
or scheduler depends on equipment at the food bank. Keep staging and pilot data isolated.

One deployable contains identity/session, booking and coordinator modules. The browser
uses only the backend; backend transactions are authoritative. No queue, microservice
split or offline booking is required. Framework choice is deferred to implementation;
it must support these contracts without changing their guarantees.

Define a shift by ID, start/end instants, capacity and an explicit open/closed state.
Proposed interpretation of "open": marked open, not started, and below capacity.
Use one booking per `(shift_id, volunteer_id)` enforced by a unique constraint. Lock the
shift row, recheck openness and remaining capacity, insert the booking, then commit.
Every booking writer must use this transaction. A duplicate retry returns the existing
booking; a full or closed shift returns a conflict without changing the roster. Serialize
any capacity/closure updates using the same lock. No cancellation or waiting list is added.

Read daily rosters from committed bookings in the primary database, grouped by shift and
filtered by the food bank's configured IANA time zone. Store times as UTC instants. The
proposed UI refreshes the visible roster every 30 seconds and provides manual refresh,
showing last successful update time and an error when stale. Do not promise a "live"
latency absent from the PRD; this interval needs confirmation before acceptance.

Shift schedules and initial volunteer data use a restricted operator import for the pilot.
A shift-management UI is not implied by this decision. Validate imports and apply the
same capacity and privacy rules. Pilot import includes Tuesday and Thursday shifts only;
expansion uses the same model and transactions.

## Consequences and acceptance prerequisites

- Transactional booking prevents oversubscription but briefly serializes writes per shift.
- Database unavailability fails protected operations closed; no local/offline success.
- Select the hosting provider, region, budget, operator and backup/restore settings before
  this deployment decision is accepted. Verify 30-day hosted log retention; ADR-001's
  historical "costs nothing extra" claim is not verified for an unselected provider.
- Confirm capacity values, shift import ownership, food bank time zone and roster refresh
  expectation. The user's environment time zone is not evidence of the food bank's zone.
- No numerical uptime, recovery or performance objective has been added to the PRD.

## Confirmation

Carry V-02, V-03 and V-06 from [the architecture assessment](../architecture/PRD-001.md#verification-contracts)
into epic acceptance criteria. Verify last-seat concurrency, retries, local-day boundaries,
hosted deployment inventory, log retention and restore. Test against the real database;
in-memory mocks cannot establish transaction correctness.
