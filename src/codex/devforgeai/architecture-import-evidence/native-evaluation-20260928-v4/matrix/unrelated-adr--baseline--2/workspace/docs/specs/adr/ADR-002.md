# ADR-002 — Use Auth0 sign-in with application-owned revocable sessions

## Context and decision drivers

PRD-001#FR-001 explicitly needs an identity-provider decision. NFR-001 also requires an
administrator to revoke a volunteer's sessions within five minutes. ADR-001 decides only
application log retention; its reference to FR-001 does not settle either question.
About 120 volunteers and no on-site server favor a managed identity service.

## Considered options

1. Auth0 hosted login plus application-owned sessions: separates identity verification
   from the application's immediate revocation enforcement; adds a managed dependency.
2. Another hosted OIDC provider: preserves the same application boundary but requires
   provider selection and onboarding validation.
3. Application-managed credentials: avoids an external identity service but adds
   credential recovery and security operations to this small product.

## Proposed decision

Use Auth0 as a confidential regular web application's OIDC provider. The backend handles
the authorization-code exchange using the provider SDK; validate callback state, nonce,
issuer, audience, signature and expiry. Keep provider credentials and tokens on the server.
Use a secure, HttpOnly, SameSite cookie containing only an opaque application session ID;
store its digest server-side and protect state-changing requests against CSRF.

Bind a pre-provisioned volunteer to the immutable `(issuer, subject)` pair, never a
browser-supplied volunteer ID. Proposed pilot onboarding uses invited accounts with
email/password at the provider; no public registration. Email availability and account
recovery must be validated before this ADR is accepted. Phone numbers are not identity
claims and must not be copied into provider profiles or tokens.

The application owns session records and an integer `session_generation` on each user.
Every protected request reads the authoritative database, checks the session's expiry
and generation, and resolves current roles. No positive authorization cache, read replica,
or provider token may bypass this check. If the database cannot be checked, deny access.

An administrator-only operation atomically increments the target volunteer's generation,
invalidating every existing application session on every instance and device. Acknowledge
success only after commit. Serialize session issuance and revocation on the user row;
reject login attempts started before revocation. Expired or revoked cookies cannot renew
a session. Recheck authorization before a protected write commits or sensitive data is
returned; set request timeouts below five minutes.

The design targets rejection on the first authorization check after commit, stronger than
the PRD's five-minute limit. A failed revocation must show failure rather than success.
Record actor, target internal ID, result and time, without secrets or phone numbers.

Revoking application sessions is distinct from blocking future sign-in. Proposed behavior
requires a fresh provider authentication after revocation, with authentication time later
than the user's revocation boundary. Silent provider SSO must not recreate access from an
old authentication. Permanent account suspension is outside this requirement; confirm
this interpretation when accepting the ADR.

## Consequences and acceptance prerequisites

- A database check on every request costs a round trip but avoids a revocation cache window.
- Provider outage prevents new sign-ins; existing valid sessions use local authorization.
- Confirm volunteer onboarding, provider tenant ownership, recovery procedure and affordable
  plan before acceptance. No price or free-tier entitlement has been assumed.
- Prove fresh-authentication handling in a provider integration spike, including simultaneous
  login/revocation. Proposed coverage is not evidence of a working implementation.

## Confirmation

Carry V-01 and V-04 from [the architecture assessment](../architecture/PRD-001.md#verification-contracts)
into epic acceptance criteria. Test multiple devices and backend instances, old cookies,
login races, unauthorized revocation and database failure. Measure the maximum time from
successful revocation to denial; it must be no more than 300 seconds.
