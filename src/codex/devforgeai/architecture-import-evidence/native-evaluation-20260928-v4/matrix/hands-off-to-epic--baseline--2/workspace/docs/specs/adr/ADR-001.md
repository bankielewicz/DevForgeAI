# ADR-001 — Managed identity for volunteer sign-in

## Context

[PRD-001](../prd/PRD-001.md) explicitly requests an identity-provider ADR for FR-001. It describes approximately 120 volunteers using mobile browsers, but does not establish that they have email accounts, a shared organizational directory, or a supported onboarding/recovery process. No platform is mandated. The service must be hosted; an administrator must invalidate signed-in sessions within five minutes; phone numbers may be visible only to the coordinator.

## Proposed decision

Use hosted Supabase Auth with email/password authentication, provisioned accounts, public signup disabled, and provider-managed password recovery. Keep provider credentials and tokens within the server-only identity adapter. Application roles and enrollment remain in the application database. The provider proves identity; the application decides access.

This is a concrete candidate, not an accepted provider decision. Email access is an unverified prerequisite, so FR-001 remains blocked for epic commitment. The provider-independent interfaces, data model, and security controls in [ARCH-001](../architecture/ARCH-001.md) are sufficient to draft the other epics. They must not claim production login is available.

## Evidence and options

Official documentation checked on 2026-09-28 establishes that Supabase supports email/password sign-in and email-based recovery. It also exposes a setting to disable new signups while allowing existing users to sign in. These capabilities fit the proposed enrollment model, but do not establish volunteer email access, delivery reliability, account ownership, or deployment suitability. Sources: [Password-based Auth](https://supabase.com/docs/guides/auth/passwords), [General configuration](https://supabase.com/docs/guides/auth/general-configuration).

| Option | Assessment |
|---|---|
| Managed Supabase Auth, email/password | Proposed: avoids implementing password storage and supplies a documented sign-in/recovery path. Requires usable volunteer email and a working enrollment/recovery delivery process. |
| Existing organizational identity provider | Prefer reuse if an appropriate directory exists and covers volunteers. No such directory is evidenced in the supplied PRD. Do not presume volunteers have organizational accounts. |
| Phone-based authentication | Could address lack of email but introduces phone handling in identity infrastructure and messaging operations. Requires review against NFR-002 and delivery/cost evidence; not a silent fallback. |
| Application-owned password system | Not selected: adds credential lifecycle and recovery responsibilities without an established need. |

## Revocation and privacy consequences

Supabase states that access tokens of revoked sessions remain valid until expiry. Provider sign-out alone is therefore insufficient evidence for this product's five-minute guarantee. Source: [Signing out](https://supabase.com/docs/guides/auth/signout).

Use application-owned opaque sessions with a primary-database generation check on every protected request, as specified in ARCH-001. The product accepts only these sessions; provider JWTs cannot access booking, roster, or application data directly. Do not exchange previously issued tokens or refresh credentials for new application sessions after revocation. Provider-side logout is supplementary, not the enforcement mechanism for NFR-001. The cost is a database authorization read per request and fail-closed behavior during database outages, appropriate to the pilot's scale.

Do not store volunteer phone numbers in provider profiles or expose them in identity metadata. They belong in the restricted application contact table. Do not provision roles from untrusted provider/client metadata. Any replacement provider must preserve these boundaries and prove the same revocation behavior; changing provider must not weaken NFR-001 or NFR-002.

## Resolution criteria and downstream effects

To resolve this ADR, record evidence for the following; no answer or approval is assumed by this document:

1. Product owner establishes a usable identity identifier and enrollment/recovery process for pilot volunteers and privileged users. If email is unsuitable, select another managed approach and update this ADR before provider-specific stories are committed.
2. Implementation owner demonstrates provisioned-user login and recovery on a representative mobile browser, unknown-user rejection, disabled public signup, and a stable identity-to-application-user mapping in a hosted test environment.
3. Implementation owner establishes hosted provider account ownership and deployable configuration, including recovery delivery and secret handling, then records the selected provider and rationale. No account is provisioned or cost commitment made here.

The unresolved product input blocks FR-001; it does not block drafting provider-independent booking, roster, session enforcement, privacy, or hosting epics. Completion and rollout of those features still depend on working identity integration. Runtime acceptance must include the all-device revocation and role-isolation tests defined in ARCH-001; an accepted ADR alone would not satisfy them.
