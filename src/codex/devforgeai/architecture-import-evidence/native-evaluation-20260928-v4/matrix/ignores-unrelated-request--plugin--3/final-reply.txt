Linux is a **monolithic kernel with loadable modules**: the scheduler, memory manager, filesystems, and device drivers run in kernel space and cooperate through internal interfaces. Applications enter the kernel through system calls; hardware interrupts and memory faults also trigger kernel work.

The three subsystems manage different resources:

| Subsystem | Main responsibility | Main abstractions |
|---|---|---|
| **Scheduler** | Decide which runnable thread gets CPU time | Tasks, scheduling policies, per-CPU run queues |
| **Memory management** | Provide protected virtual address spaces and manage RAM | Virtual memory areas, page tables, physical pages |
| **Virtual file system (VFS)** | Provide a common interface to different filesystems | Files, inodes, directory entries, superblocks |

Their relationships look like this:

```mermaid
flowchart TD
    A[Application threads] -->|System calls| V[VFS and filesystem implementations]
    A -->|Memory access faults| M[Memory management]
    S[Scheduler] -->|Assigns CPU time| A
    V <-->|Cached file data and memory mappings| M
    V -->|Storage requests| D[Device drivers]
    V -->|Block or wake tasks| S
    M -->|Block or wake tasks| S
    D -->|I/O completion allows tasks to wake| S
```

**The scheduler manages execution.** Linux schedules individual threads, represented as kernel tasks. It selects runnable tasks, balances work across CPUs, and performs context switches. A thread waiting for disk I/O usually sleeps, allowing another thread to run. When the I/O finishes, it becomes runnable again; that does not guarantee immediate execution.

Scheduling policy determines which runnable task wins. Modern Linux uses EEVDF for ordinary fair scheduling, alongside policies for real-time and deadline workloads. [Scheduler documentation](https://docs.kernel.org/scheduler/sched-eevdf.html)

**Memory management gives each process an address space.** On typical systems, hardware translates virtual addresses using page tables maintained by the kernel. Threads in the same process normally share that address space. When switching between processes, the kernel also switches the active memory context.

Physical RAM can be allocated on demand: accessing a valid virtual address whose backing page is absent triggers a **page fault**. The kernel may allocate a zero-filled page, load file data, or retrieve swapped-out data. If that requires waiting for I/O, the scheduler runs another task. Under memory pressure, the memory manager reclaims cached pages or swaps eligible anonymous memory when swap is available. [Memory concepts](https://cdn.kernel.org/doc/html/latest/admin-guide/mm/concepts.html)

**The VFS gives filesystems a common interface.** Applications use operations such as `open()`, `read()`, and `write()` whether a file lives on ext4, a network filesystem, or an in-memory filesystem. VFS resolves names, applies access checks, and dispatches operations to the relevant implementation.

Its key objects include an **inode** for a filesystem object, a **dentry** connecting a name to an inode, a **file object** representing an open instance, and a **superblock** describing a filesystem instance. [VFS documentation](https://docs.kernel.org/filesystems/vfs.html)

A typical buffered file read shows how they fit together:

1. A running thread calls `read(fd, buffer, size)`. The kernel finds the open file and dispatches its read operation.
2. The filesystem checks the **page cache**, RAM holding cached file contents. This is a central connection between filesystems and memory management.
3. If the requested data is ready in the cache, the kernel copies it into the application’s buffer.
4. If storage access is needed, the kernel arranges I/O. The thread may sleep while the scheduler runs another task.
5. I/O completion makes the data available and wakes the waiting thread. When scheduled again, it finishes the read.

With **`mmap()`**, file contents instead appear directly in the process’s virtual address space. Accessing an absent page invokes memory management and the filesystem to supply it, generally through the same page cache used by buffered reads. Shared writable mappings can dirty those cached pages, which the kernel later writes back to storage. [Memory management overview](https://cdn.kernel.org/doc/html/latest/admin-guide/mm/index.html), [page cache documentation](https://cdn.kernel.org/doc/html/latest/admin-guide/mm/concepts.html)
