# ADR-002 — Managed identity with application-owned, revocable sessions

## Context and decision drivers

PRD-001 explicitly leaves the identity provider undecided. About 120 volunteers need browser sign-in; administrators must invalidate all of a volunteer's sessions within five minutes. ADR-001 settles logging only. A valid identity-provider token alone must not authorize application access after revocation.

## Considered options

1. Managed identity through OpenID Connect, with database-backed application sessions: separates credential handling from application authorization and makes revocation locally enforceable; adds a provider dependency and a database check.
2. Managed identity with browser-held tokens accepted until expiry: simpler session storage, but token expiry and refresh behavior complicate the five-minute guarantee.
3. Application-managed passwords: fewer vendors, but requires the team to own credential storage, recovery, and abuse controls.

## Proposed decision

Recommend **Auth0 for identity, using a confidential web application and Authorization Code Flow**, with an application-owned session boundary. Auth0 documents this flow for regular web applications; the provider choice remains proposed, with no claim that a tenant, suitable plan, or volunteer login method has been confirmed. [Auth0 flow documentation](https://auth0.com/docs/get-started/authentication-and-authorization-flow/authorization-code-flow), checked 2026-09-28.

- The backend handles the code exchange using a maintained OIDC library, validates issuer, audience, signature, expiry, state and nonce, and uses PKCE. Tokens and secrets stay on the server.
- Map `(issuer, subject)` to an internal volunteer record. Use that record's roles; never trust a client-supplied user ID or role. Proposed enrollment is coordinator-provisioned accounts for the existing volunteer list, without public self-registration.
- Issue a random opaque session cookie with `Secure`, `HttpOnly`, and `SameSite=Lax`; persist only its hash, user ID, generation and expiry. Apply CSRF protection to mutations. Proposed absolute lifetime is 12 hours, subject to usability review.
- Every protected request checks the session and the user's current session generation and roles against the primary database. No authorization cache or replica reads. Fail closed on lookup failure.
- An administrator-only operation atomically increments the target user's session generation. Return success only after commit. Every older session is then rejected on its next request; no five-minute background job or provider logout dependency is involved.
- Serialize session creation and revocation on the user record. Login attempts record the generation when started; reject a callback if that generation changed. Revocation also requires fresh provider authentication before a new session can be issued, preventing an existing provider SSO cookie from silently restoring access. New deliberate sign-in is permitted; account suspension is a separate, unrequested feature.
- Recheck authorization inside booking transactions and before returning protected roster data. Proposed request deadline is 30 seconds, bounding requests already executing when revocation commits below the five-minute limit. Do not introduce persistent authenticated streams without a revocation design.
- Log sign-in outcomes and revocation events using internal IDs and correlation IDs under ADR-001; exclude tokens, cookies, credentials, callback query strings, and phone numbers.

## Consequences and unresolved evidence

Revocation is independent of provider access-token lifetime and works across application instances. The database becomes a dependency of every protected request. Identity-provider outages prevent new sign-ins; already valid application sessions can continue if the database is healthy.

Before acceptance, confirm Auth0 tenant ownership, affordable plan, supported fresh-authentication behavior, and a login/recovery method usable by the volunteers. Email ownership is not established by the PRD; email-based enrollment must not be silently assumed. Priya Nair is the proposed decision owner, not a recorded approver. This ADR does not close the PRD's identity marker until accepted.

## Confirmation

Epic tests must cover valid/invalid callbacks, unknown volunteers, unauthorized role escalation, two active devices, cross-instance revocation, a concurrent login callback, an existing provider SSO cookie, direct API requests with a provider token, and database failure. All old sessions must fail no later than 300 seconds after successful revocation, including boundary tests at 299 and 300 seconds. Establish failing tests before implementation.
