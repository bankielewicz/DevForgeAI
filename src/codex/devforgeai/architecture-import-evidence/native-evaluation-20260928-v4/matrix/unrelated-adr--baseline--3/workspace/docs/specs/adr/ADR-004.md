# ADR-004 — Hosted modular web application with a transactional database

## Context and decision drivers

The whole product must run on hosted services. The pilot serves about 120 volunteers and three warehouse shifts per day. Booking correctness, a current roster and enforceable authorization matter more than independent service scaling. ADR-001 already requires 30 days of application logs in the hosting provider's log service.

## Considered options

1. One hosted web application, managed PostgreSQL, managed identity and provider logging: small operational surface and one transactional source of truth.
2. Microservices with separate booking and roster stores: additional deployments and consistency work without a requirement for independent scaling.
3. An on-site server: conflicts with NFR-003 and is rejected.

## Proposed decision

Use a mobile-first, same-origin web application with internal identity/session, booking and coordinator modules, deployed as one service. Use managed PostgreSQL for application data and sessions; access it only from the backend over a protected connection. Use managed identity under ADR-002. Store secrets in the hosting platform's secret facility; separate pilot/test data and credentials. No application component depends on a machine at the food bank.

Bookings and roster reads share the primary transactional database. Lock the shift row, check that it is open and has remaining capacity, and insert a booking in one transaction. Enforce `UNIQUE(shift_id, volunteer_id)` and foreign keys in the database. A repeated request for the same booking returns the existing result; concurrent requests for the final place cannot both succeed. Do not announce success before commit. The coordinator roster reads committed bookings directly, avoiding a second roster store or queue.

Proposed meaning of an open shift: coordinator-published, not yet started, and below its configured positive capacity. A shift has an explicit start/end time and a configured food-bank timezone. Initial shifts and volunteer records may be provisioned through a controlled import; this does not authorize building a scheduling console. These domain assumptions need product validation before booking stories are finalized.

## Hosting selection and existing-decision compatibility

The deployment pattern is defined; a hosting vendor and plan are **not selected**. Selection must demonstrate managed database durability and restore, protected database connectivity, secrets, HTTPS, and the accepted 30-day provider-log retention. Do not silently replace ADR-001 with shorter retention or external-only logging.

Render is an evaluated candidate because it offers web services and managed PostgreSQL. Its documented native log retention is 7 days on Hobby, 14 on Pro, and 30 on Scale/Enterprise. Thus a low-tier Render deployment cannot be assumed compatible with ADR-001. [Render service types](https://render.com/docs/service-types), [Render log retention](https://render.com/docs/logging), checked 2026-09-28. No pricing or affordability conclusion has been established.

ADR-001's statement that logging costs nothing extra lacks a named provider/plan in the available documents. Retain its accepted decision, record this unresolved assumption, and select a compatible affordable plan or obtain an explicit superseding decision. This is a product-wide architecture gate through NFR-003, affecting every functional requirement.

## Consequences and confirmation

A single service and database simplify consistent bookings, session revocation and roster reads. Database failure prevents booking and protected access; the UI must report unavailability rather than success or an empty roster. Proposed recovery includes managed backups, a tested restore and application rollback; no unsupported availability, RPO or RTO promise is introduced.

Before acceptance, record the provider, plan, budget owner and evidence of 30-day logging compatibility. Before release, verify simultaneous last-place bookings, duplicate retries, failed commits, timezone date boundaries, roster freshness, a restart without data loss, restore to an isolated environment, HTTPS and secret handling. Confirm all production components are hosted. Runtime checks remain pending implementation.
