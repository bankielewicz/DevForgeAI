# ADR-003 — Enforce coordinator-only phone access on the server

## Context and decision drivers

The coordinator needs the daily roster; volunteer phone numbers must be visible only to the coordinator. Administrator session-revocation privileges do not imply coordinator privileges. Even a volunteer's own phone number is excluded from volunteer-facing responses under the literal PRD requirement.

## Considered options

1. Separate contact data and explicit server authorization: enforceable and testable at every data boundary; requires careful query and response design.
2. Return full volunteer objects and hide fields in the UI: exposes numbers in network responses and does not meet NFR-002.
3. Per-field encryption as the only control: protects storage but does not establish who may receive decrypted responses.

## Proposed decision

Keep `VolunteerContact(volunteer_id, phone_number)` separate from the public application profile. Only the coordinator-authorized query may join this table. Use explicit response field lists, never generic model serialization. The browser has no direct database access.

The volunteer API returns shift details and the caller's own bookings, without phone fields. The coordinator roster endpoint returns booked names and, where needed, contact numbers after a current server-side role check. An administrator without the coordinator role cannot use that endpoint or read phone numbers. Role changes are visible on the next request under ADR-002.

Send authenticated responses with `Cache-Control: no-store`; do not persist roster responses in browser storage or shared caches. Exclude phone numbers from logs, analytics, traces, error reports, identity-provider profiles, and exports. New export features require the same authorization policy. No exports are added by this decision.

The application service can process contacts, but interactive database access, backups and restore tooling must be restricted to designated custodians. Infrastructure custody is a trust boundary, not an extra product role that may browse phone numbers. If NFR-002 intends to prevent even hosting operators from accessing plaintext, that requires a separate key-management decision; this proposal interprets visibility as application and routine operational disclosure.

## Consequences

Authorization is centralized and response leakage can be tested. Separating data reduces accidental disclosure but does not replace role checks. Previously viewed information cannot be withdrawn from a person's memory or screenshots; after role revocation the service denies subsequent reads.

## Confirmation

Use a planted phone number to test anonymous, volunteer, administrator-only, coordinator, and combined-role requests. Inspect HTML, JSON, errors, logs and cache headers. Only coordinator-authorized responses may include it. Test direct endpoint calls, changed record IDs and coordinator-role removal. Confirm the operational access interpretation with the decision owner before acceptance; do not weaken the PRD wording.
