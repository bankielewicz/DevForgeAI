# ADR-001 — Volunteer sign-in identity provider

## Context and status

[PRD-001](../prd/PRD-001.md) explicitly leaves the identity provider for FR-001 open. [POL-001](../policy/POL-001.md) mandates none. The supplied evidence does not establish that volunteers have email addresses, an existing organizational identity, a preferred login method, or a funded provider account. Smartphone access alone does not establish any of these.

This ADR is proposed and the concrete provider decision remains unresolved. Creating an ADR does not resolve the PRD's NEEDS ADR marker. FR-001 is blocked for epic readiness until the decision is completed. No questions were asked, as requested; this is a recorded evidence gap rather than a request to pause other work.

## Architectural direction

Use a hosted identity service through a server-side adapter, mapping a verified stable external subject to an internal User. Keep application sessions and authorization local as specified in [ARC-001](../architecture/ARC-001.md). This allows a five-minute revocation guarantee without relying on provider access-token expiry or logout propagation. The selected integration must not require phone numbers in general application identity responses.

## Alternatives to evaluate

| Alternative | Fit | Unresolved evidence / tradeoff |
|---|---|---|
| Managed identity service with its own volunteer accounts | Does not require an existing organization identity; limits custom credential handling. Preferred category to investigate. | Must establish supported volunteer identifiers, recovery, onboarding usability, cost, hosted operation, and protocol validation. No vendor capability has been assumed verified. |
| Federation with an existing organization identity service | Could reuse established enrollment and recovery if all volunteers already have accounts. | No such service or volunteer membership is evidenced; adopting this unconditionally could exclude volunteers. |
| Application-owned credentials or one-time links | Gives control of the user journey. | Adds credential/recovery or message-delivery responsibilities not justified by the current pilot evidence; not the default direction. |

## Decision completion criteria

The eventual decision record must name a provider and login/enrollment/recovery method, record alternatives and rationale, and supply evidence for:

1. A representative volunteer can enroll, sign in, recover access, and sign out in a mobile browser without an unsupported identifier assumption.
2. Server-side integration validates the provider's authentication response and maps identities without trusting client claims or accidentally linking different users.
3. All application requests use the authoritative local session check; revoked application sessions cannot silently refresh back into valid sessions. Test multiple sessions and the five-minute bound.
4. Phone data remains limited to coordinator-authorized application responses; provider-required contact collection is evaluated for compatibility with NFR-002.
5. The service is hosted, with documented account ownership and feasible pilot cost/operation. Confirm actual capabilities against the selected provider's current official documentation and a small integration exercise.

Proposed product decision owner: Priya Nair (the PRD owner); a technical delivery owner still needs designation. No acceptance or assignment by either owner is asserted here.

## Consequences and affected readiness

FR-001 remains BLOCKED. NFR-001's local session design is ready for epic decomposition, while its provider integration verification remains dependent on this ADR. FR-002 and FR-003 can be decomposed against the local authenticated-user contract but cannot be released before working sign-in exists. NFR-002 and NFR-003 constrain any provider selected. Choosing a provider that requires bypassing the local session authority would require revisiting the architecture and readiness assessment.
