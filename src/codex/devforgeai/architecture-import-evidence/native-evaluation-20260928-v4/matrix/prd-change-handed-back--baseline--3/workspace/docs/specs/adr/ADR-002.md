# ADR-002 — Hosted application and data boundary

## Context

[PRD-001](../prd/PRD-001.md) describes about 120 volunteers, three daily warehouse shifts, mobile browsers, coordinator rosters, restricted phone visibility, and no on-site server. There is no existing implementation to extend. [POL-001#SET-02](../policy/POL-001.md) additionally requires compliance and accessibility coverage for this internal product.

## Proposed decision

Deploy one application with separate identity, booking, and roster modules on a hosted runtime. Use a managed relational database for users, roles, application sessions, shifts, and bookings. Host secrets, logging, and backups as well. Provider and region remain open pending compliance constraints; no vendor capability or organization approval is assumed.

Keep bookings and rosters on the same transactional store. Serialize capacity-changing operations for each shift and enforce unique volunteer/shift bookings in the database. A booking succeeds only after commit; the roster reads committed results. This avoids introducing a separate eventually consistent roster projection for the pilot.

Enforce authentication and explicit role checks at the server for every operation. Separate phone data from generic user projections; permit retrieval only to the coordinator role. An administrator's revocation capability does not grant phone access. Exclude phone data from generic payloads, telemetry, and unauthorized export paths. Avoid a browser-accessible database interface.

## Alternatives and tradeoffs

- Separate booking, identity-adapter, and roster services: adds deployment and cross-service consistency work with no demonstrated need at the stated scale. Defer.
- Browser writes directly to a shared database: introduces a different authorization boundary without an existing architecture or verified rules. Prefer one server boundary.
- On-site deployment: conflicts with NFR-003. Rejected.
- Shared spreadsheets as the primary application store: no supplied evidence of enforceable transactional capacity and phone-access controls. Not selected.

A single application keeps deployment and transaction reasoning simple but requires the application and database to be available for bookings. Managed services reduce on-site responsibilities; they do not remove the need to specify access controls, recovery, retention, or accessibility.

## Acceptance evidence still required

Resolve ARCH-001 GAP-03 through GAP-07, including approved quality requirements and operational definitions. Review the design against the resolved identity contract in ADR-001. Implement and verify ARCH-001 V-02/03/05/06/07/08. Concurrency, authorization, deployment, recovery, and accessibility checks are **NOT_RUN**. This ADR remains **proposed**.
