# ADR-001 — Mandated identity platform and personal Google sign-in

## Context

PRD-001 explicitly requests an identity ADR for FR-001. Its NFR-004 requires
personal Google accounts. POL-001 SET-01 mandates Org A Identity Platform (OIDC),
with no product override. The platform's cited ADR-104 is not supplied. These
requirements are potentially compatible through federation, but compatibility
has not been established.

## Decision boundary

The platform choice is already constrained by policy: the application must use
Org A Identity Platform. This ADR does not reopen that selection or approve an
exception. The **proposed** integration is personal Google authentication federated
through Org A, with the application trusting only Org A's OIDC issuer. Whether the
platform supports that route is pending evidence. Do not implement a direct Google
fallback while the decision is blocked.

The application maintains revocable opaque sessions and checks authoritative
revocation state on every protected operation as described in
[ARC-001](../architecture/ARC-001.md). This local authorization/session state does
not replace the organization's authentication service or create product passwords.
Provider session logout alone is insufficient evidence for the five-minute
application-session revocation requirement.

## Options and disposition

| Option | Disposition |
|---|---|
| Personal Google federation through Org A OIDC | Proposed, conditional on platform evidence; could satisfy both constraints. |
| Direct Google OIDC or another product-selected authentication provider | Excluded by non-overridable SET-01, even if it satisfies NFR-004. |
| Org A accounts without personal Google sign-in | Does not satisfy the current NFR-004; requires an approved PRD change. |
| Product credentials/password database | Excluded by SET-01 and outside the PRD. |

## Evidence required to resolve

The organization platform owner must provide authoritative configuration guidance
and demonstrate a personal Google account signing in through Org A, including
stable issuer/subject identifiers and a supported volunteer admission/role path.
Verify callback validation, rejection paths, multiple-session revocation within
300 seconds, and that old sessions cannot regain access from stale tokens. Record
the integration evidence and review outcome before marking this ADR accepted.

If the platform cannot support personal Google accounts, record that incompatibility
and obtain an approved requirement change from the PRD owner or a formal policy
change through the organization policy owners. The architecture cannot silently
weaken either approved input. FR-001 and dependent FR-002 remain blocked meanwhile.
FR-003 is not directly constrained to Google accounts, but still requires a resolved
coordinator identity/role path and the shared quality gate.

## Consequences

No independent identity-provider selection is needed or authorized. Federation
availability and platform onboarding are delivery dependencies. Hosted application
sessions make revocation enforceable independently of provider token lifetime,
with the operational cost of an authoritative state read on protected requests.
This document is a proposed integration ADR, not proof of platform capability or
organizational approval.
