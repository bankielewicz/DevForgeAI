# ADR-001 — Identity provider for volunteer sign-in

## Status and context

**Proposed; provider not selected.** This records the explicit NEEDS ADR marker
in [PRD-001](../prd/PRD-001.md), section 12. There is no evidence of an existing
identity tenant, volunteer email access, usable login method, recovery process,
or hosting budget. Smartphone access itself is an open PRD assumption. A vendor
choice without these inputs would conceal unresolved product behavior.

## Options

| Option | Benefit | Limitation / evidence needed |
|---|---|---|
| Existing hosted organization identity service | Reuses operational ownership if such a service exists. | Establish whether it exists and whether all volunteers can enroll, sign in and recover access. |
| Dedicated hosted identity service | Separates identity operations from the food bank's application. | Evaluate volunteer login methods, recovery, hosted integration, cost and operator ownership against actual needs. |
| Application-managed credentials | Full control of login flow. | Adds credential storage, recovery and abuse-handling responsibility; no requirement justifies this scope now. |

## Proposed direction and fixed integration boundary

Prefer a hosted identity service behind a backend adapter. Select between the
first two options only after the missing evidence is available. No particular
vendor, email-only flow, SMS flow or existing organization account is assumed.

The adapter must validate the provider's authentication result and yield a
stable issuer/subject identity. The application maps it to an active local
principal and creates its own opaque session. Local role assignment controls
permissions; do not place phone numbers in provider claims or application
tokens. Provider tokens alone never authorize booking, roster or revocation
routes. See [ARCH-001](../architecture/ARCH-001.md) for the session contract.

Application-side session revocation is intentionally independent of provider
logout. Existing app cookies become invalid on every instance after generation
change. The integration must not silently refresh a revoked app session from a
cached provider token; a new login flow is required. Whether that flow forces
credential entry or permits provider SSO must be explicit in the final ADR.
NFR-001 requires invalidating existing sessions, not permanently disabling the
account or necessarily invalidating all provider sessions.

## Closure criteria

1. Record actual volunteer credential/access needs and the enrollment/recovery
   route, with evidence from the product owner or existing operational records.
2. Name the provider, login method and operational owner; document alternatives,
   hosted deployment compatibility, cost assumptions and relevant provider docs.
3. Demonstrate a small integration that validates identity, safely links a local
   principal and creates the application session without exposing phone data.
4. Demonstrate old app-cookie rejection after administrative revocation, across
   instances, within five minutes; specify re-login and provider SSO behavior.
5. Update this ADR's decision and status and re-evaluate FR-001 readiness.

Priya Nair is the PRD's named owner and the proposed contact for product inputs;
no review or approval by her is claimed. The engineering owner is unassigned.
This is a bounded decision spike, not a request to build full sign-in now.

## Consequences and affected requirements

FR-001 is blocked for epic decomposition until the provider and user flow are
defined. FR-002 and FR-003 can be decomposed against the stable local principal
contract; their release still depends on functioning sign-in. NFR-001 can be
designed and tested with adapter fixtures because application session checks
own revocation. NFR-002 constrains identity payloads and NFR-003 requires hosted
identity alongside the rest of the product. No requirement is waived by this ADR.
