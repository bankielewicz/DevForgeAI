# ADR-001 — Hosted identity provider and session integration

## Status

**Open; no concrete identity provider selected.** This records the explicit decision requested in PRD-001 §12. It does not constitute approval of a vendor, authentication method, or enrollment policy. FR-001 remains blocked for implementation-epic extraction. The bounded provider evaluation below can be planned immediately.

## Context

[PRD-001](../prd/PRD-001.md) requires volunteer sign-in, administrator revocation of signed-in sessions within five minutes, coordinator-only phone visibility, and hosted services throughout the product. It does not supply a provider, existing identity directory, account enrollment/recovery workflow, or required volunteer credential type. In particular, sign-in must not assume email ownership or phone-based login for every volunteer.

[ARCH-001](../architecture/ARCH-001.md) defines application-owned sessions and roles. Feature modules consume a provider-independent principal. Server-side revocation can be implemented independently, but the selected provider must not let old authentication silently recreate revoked access.

## Options

| Option | Fit | Unresolved evidence |
|---|---|---|
| Managed identity provider through a server-side standards-based adapter | Preferred direction: hosted identity lifecycle with a small application boundary | Concrete provider, supported volunteer credentials, fresh-authentication behavior, enrollment/recovery, cost and operator access |
| Hosted application platform with integrated identity and data services | Potentially fewer services to operate | Same authentication evidence, ability to keep application roles authoritative, isolation of contact data and privileged credentials |
| Custom authentication service on hosted compute | Can satisfy off-site hosting in principle | Adds credential storage, recovery and abuse-prevention responsibilities; not justified by this small pilot's stated needs |

No vendor capabilities or prices have been evaluated, so this ADR makes no vendor-specific claim. The recommended direction is managed hosted identity plus durable application sessions; the concrete selection is deliberately not represented as complete.

## Resolution work and decision criteria

The implementer responsible for identity should produce a candidate comparison and integration proof against these gates:

1. Identify usable volunteer credentials and an enrollment, account-linking, and recovery process. Link immutable external issuer/subject identifiers to internal accounts. Explain how the initial approximately 120 volunteer records enter the system and how account duplication is prevented. Do not assume an existing directory that has not been supplied.
2. Demonstrate hosted server-side sign-in with replay protection and verifiable identity responses. Pin the chosen protocol/SDK configuration, callback allowlist and server-held secrets in the implementation design.
3. Prove the application-session revocation contract: existing sessions fail at every protected endpoint within five minutes, including across replicas. Demonstrate that a pre-revocation provider session, token refresh, or callback cannot create a fresh application session without authentication after the revocation barrier. Define logout and provider-outage behavior.
4. Show that application roles, not self-selected provider profile attributes, grant coordinator or administrator capability. Sign-in screens, profile screens, recovery screens, support tools and operational roles must not expose volunteer phone numbers to anyone except the coordinator. If the provider requires exposing phone numbers in its user profile or admin console, omit phone collection there or reject that configuration.
5. Record hosted topology, pricing assumptions for the pilot, production operator access, and credential/recovery ownership. Validate capabilities against the selected provider's official documentation and a disposable hosted integration; retain dated references and test results.

Resolve this ADR by naming the provider and credential flow, recording the chosen option and rejected alternatives, and linking the evidence for all gates. Record unresolved product-policy decisions explicitly if evaluation reveals them; do not invent user approval. Then update the readiness matrix and decompose FR-001 with the linked security acceptance criteria.

## Consequences until resolution

- The identity implementation epic is blocked; a provider-evaluation task is ready.
- Booking and roster may be decomposed against ARCH-001's principal and authorization contracts. Their integrated delivery depends on completed identity, and their acceptance tests must include the real provider before release.
- Shared application-session, role and hosted-storage work may proceed independently. NFR-001's end-to-end acceptance remains blocked by provider evidence even if local revocation unit tests pass.
- No source PRD requirement, priority, approval state, or open question is changed by this ADR.
