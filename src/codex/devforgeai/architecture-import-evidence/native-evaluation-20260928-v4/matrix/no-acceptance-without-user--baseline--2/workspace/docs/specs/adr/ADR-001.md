# ADR-001 — Identity provider for volunteer sign-in

## Status and scope

**Proposed; provider decision unresolved.** This records PRD-001's explicit
`[NEEDS ADR: identity provider for volunteer sign-in; affects FR-001]` marker.
Creating this record does not resolve that marker. FR-001 remains blocked for
epic definition until a provider and its sign-in approach are selected.

Related design: [ARCH-001](../architecture/ARCH-001.md). Suggested decision owner:
Priya Nair with the implementation lead; no approval by either is asserted.

## Context

The PRD requires mobile-browser sign-in for around 120 volunteers, hosted services,
administrator revocation within five minutes, and coordinator-only visibility of
phone numbers. It does not name an existing identity tenant, usable sign-in channels,
an enrollment/recovery process, provider budget, or who provisions privileged users.
Choosing email links, SMS, passwords or organizational SSO without these inputs would
settle product behavior that the PRD leaves open.

## Options to evaluate

| Option | Fit / tradeoff | Evidence needed |
|---|---|---|
| Reuse an existing hosted identity tenant through a standard redirect protocol | Could centralize identity administration; only useful if volunteers can be enrolled and supported there. | Confirm a tenant exists, external volunteer eligibility, mobile flow and operating cost. |
| Dedicated hosted authentication provider | Separates volunteer identities from staff accounts; introduces provider configuration, recovery and cost decisions. | Confirm suitable sign-in channels, enrollment controls, stable subject mapping, mobile accessibility, support and cost. |
| Application-managed credentials on hosted infrastructure | Gives control over account behavior; adds password/recovery security and operating responsibilities. | Demonstrate why managed alternatives cannot meet needs and identify an operational owner before considering this option. |

No vendor capability or price is asserted here. A provider-specific decision needs
current official documentation and an integration experiment. Prefer a managed
identity service if it meets the criteria; that preference is not a provider selection.

## Fixed integration constraints

- Map verified external subject identifiers to approved application accounts. Do
  not derive roles from untrusted browser fields or auto-enroll unknown identities.
- Keep phone numbers out of browser-visible identity claims and general profiles.
  A selected authentication channel must preserve NFR-002; phone-based sign-in
  cannot be assumed compatible without settling its visibility behavior.
- Establish opaque application sessions after authentication. APIs validate these
  sessions against the local session store on every protected request. A valid
  provider token cannot bypass application revocation.
- Record sign-in attempt start times server-side and reject callbacks that cross
  a revocation boundary before issuing in the current session generation. Define the fresh sign-in path after
  revocation without requiring provider-wide logout to satisfy NFR-001.
- All production authentication dependencies must be hosted, consistent with
  NFR-003. Privileged application roles are provisioned explicitly.

## Exit evidence

1. Record a named provider, chosen channel, enrollment/recovery behavior, privileged
   account provisioning, responsible operator and alternatives rejected with reasons.
2. Verify current provider documentation for the required callback/protocol behavior,
   stable subject IDs and mobile flow; record links and relevant constraints/costs.
3. Demonstrate a thin hosted sign-in → application session → revocation flow,
   including attempted use of a still-valid provider credential after local revocation.
4. Demonstrate that unknown identities receive no permissions and identity responses
   do not expose volunteer phone numbers to non-coordinators.
5. Update this ADR's decision/status and ARCH-001's FR-001 readiness based on that
   evidence; then reconcile the PRD's open marker through its normal revision process.

Until then, session, booking, privacy and roster modules may be scoped and verified
against a test identity adapter, but no end-to-end sign-in or release readiness is
claimed. This unresolved decision does not erase NFR-001 or make NFR-002/NFR-003
optional for any epic.
