# ADR-002 — Sessions and contact access

## Decision for the planning baseline

Use opaque application sessions in a Secure, HttpOnly, SameSite cookie. Persist only the secret's hash, principal, generation, and expiration on the server. Validate sessions and current roles against primary database state on every protected request. Server-side session invalidation and restrictive cookie handling follow [OWASP session-management guidance](https://cheatsheetseries.owasp.org/cheatsheets/Session_Management_Cheat_Sheet.html). This ADR is proposed architecture, not an approval or completed security test.

An administrator revokes all sessions for a volunteer by atomically incrementing the principal's session generation. Session creation serializes with this update. Old cookies cannot authenticate, refresh themselves, or exchange a provider token into a replacement session. An explicit new sign-in is allowed; permanent suspension is separate behavior. No positive authorization cache, read-replica lag, or offline authorization is permitted in the pilot design. Store failure denies protected operations. This enforces revocation at the next check and avoids dependence on the still-undecided provider's token lifetime.

Keep coordinator and administrator permissions separate and locally managed. Only the coordinator permission authorizes a phone-bearing response. Contact data uses a separate table/projection and is excluded from all ordinary profile and volunteer responses, including self-profile. Apply the same authorization to server rendering and API access; suppress contact data in operational output and shared/browser caches.

## Alternatives and consequences

Self-contained browser bearer tokens would require short lifetimes or a separate revocation check; provider logout alone provides no demonstrated five-minute bound here. Client-only field hiding cannot enforce privacy. Both approaches are rejected for this baseline.

Per-request database checks couple protected access to database availability and add one authorization lookup. At the stated pilot scale, that tradeoff is preferable to distributed revocation caches. Provider choice stays replaceable behind a verified-principal adapter. Operations need secure role provisioning and audited access to stored contact data. Exact session idle/absolute timeouts belong in session stories and must not weaken administrative revocation.

## Verification and coverage

NFR-001: multi-device/multi-instance revocation, 300-second boundary, issuance races, store failure, and direct-token bypass tests (ARCH-001 V-04).
