# ADR-001 — Volunteer identity provider

## Context and unresolved decision

PRD-001 explicitly requires an ADR for the provider behind FR-001. The supplied evidence does not identify an existing identity tenant, available volunteer credentials, email coverage, budget, or recovery operator. **No provider has been selected.** This ADR remains proposed and blocks FR-001 epic readiness; it must not be represented as accepted or implemented.

## Options and selection direction

| Option | Benefit | Unresolved cost or risk |
|---|---|---|
| Existing hosted organization identity service | Reuse account administration if available | No evidence that volunteers have accounts or that external enrollment is suitable |
| Dedicated hosted identity service | Purpose-built enrollment and recovery choices | Need evidence for volunteer usability, administration, cost, and supported protocol |
| Application-managed passwords | Direct control of sign-in | Adds credential storage/recovery responsibilities; not selected for this small pilot |

Plan for a hosted identity service behind an adapter, provisionally using OpenID Connect authorization code flow. Its verified issuer and subject map to an existing local principal. The protocol defines authentication and token validation, but does not select a vendor or prove volunteer access. See [OpenID Connect Core](https://openid.net/specs/openid-connect-core-1_0.html). Provider-specific integration must validate issuer, audience, signature, expiry, state/nonce, and browser binding using a maintained library; require PKCE support during selection.

## Evidence required to close

The product owner coordinates identification of an available service and usable sign-in/enrollment/recovery method. The implementer records the chosen service and verifies mobile-browser sign-in, stable identity mapping, callback validation, staff/admin authentication, provisioning, and an operational recovery path. Record cost/hosting fit and whether verified contact claims could violate coordinator-only phone visibility. Do not request or copy phone claims into browser tokens.

Validate that the provider can establish a new local session without allowing a revoked application session or provider bearer token to bypass the application checks in [ADR-002](ADR-002.md). Provider logout is not relied upon for the five-minute application revocation requirement. Update this ADR with the choice, alternatives, evidence, and affected readiness rows before releasing the FR-001 epic for implementation.

## Impact

Direct blocker: FR-001. NFR-001, NFR-002, and NFR-003 constrain selection. Their architecture can be planned now; provider-integrated verification remains pending. FR-002 and FR-003 have stable local principal and authorization contracts for epic decomposition, but cannot ship with stub authentication. This distinction does not waive any PRD requirement.
