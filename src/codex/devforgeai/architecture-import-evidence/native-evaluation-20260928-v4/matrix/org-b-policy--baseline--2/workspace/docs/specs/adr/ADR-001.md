# ADR-001 — Volunteer identity provider and local-session boundary

## Status and context

**Proposed; provider selection unresolved.** This records the open decision
explicitly requested by PRD-001 section 12. It does not assert approval or clear
that marker. No policy mandates an identity vendor. The source documents do not
identify existing volunteer accounts, access to email or other credentials,
an available identity tenant, operating budget, or account-recovery ownership.

Sign-in must work in mobile browsers for approximately 120 volunteers. Application
sessions must be revocable by an administrator within five minutes, and phone
numbers must be visible only to the coordinator. See
[ARCH-001](../architecture/ARCH-001.md) for the application contracts and the
separation of coordinator and administrator permissions.

## Proposed direction

Use a hosted managed identity provider through an OpenID Connect adapter, with
application-owned opaque sessions and authoritative per-request revocation.
Choose the concrete provider and credential/enrollment method after establishing
that volunteers can actually use them. Do not assume that volunteers have an
organization account, can receive email links, or may expose their phone number
as an identity claim. Phone contact data stays within the coordinator-authorized
application projection.

The application session mechanism is deliberately independent of provider token
lifetimes. Provider token revocation alone is not evidence that NFR-001 is met.
An external token must never bypass the local session-generation check. A later
provider choice that cannot satisfy this boundary requires an architecture
revision before FR-001 becomes ready.

## Alternatives

| Approach | Advantages | Tradeoffs and disposition |
|---|---|---|
| Managed external identity with local application sessions | Delegates credential handling and recovery; preserves application-controlled revocation | Proposed direction; concrete provider, volunteer eligibility and recovery flow still need evidence |
| Existing organization identity tenant with local sessions | Could reuse account administration if accessible to volunteers | No tenant or volunteer entitlement is evidenced; evaluate only if confirmed |
| Application-managed credentials on hosted infrastructure | Complete control over sign-in behavior | Adds credential security, recovery, and abuse-control responsibilities; not preferred for this small pilot without a demonstrated need |
| Provider tokens directly authorizing application APIs | Removes a local session layer | Not selected: a self-contained token can remain usable unless every authorization path has an effective revocation check |

These are architectural alternatives, not claims about any vendor's current
features, pricing, or suitability. No external vendor research has been treated
as completed.

## Closure criteria and ownership

Priya Nair, the PRD owner, is the proposed product decision owner; an assigned
implementer should supply the technical evidence. No review or approval has been
recorded. Close this decision by recording:

1. The selected hosted identity provider and supported sign-in method, including
   volunteer eligibility, account provisioning, and an owned recovery process.
2. Evidence that the pilot's volunteers can access the credential channel, with
   no unapproved expansion into phone-based identity or account self-registration.
3. A validated mobile sign-in/callback integration, stable subject mapping, and
   rejection of invalid authentication responses.
4. Evidence that app-owned sessions enforce the five-minute bound for all
   existing sessions and all protected routes, including after provider-token
   refresh and during authorization-store failure.
5. Acceptable hosting/cost and contact-data handling for the pilot, documented
   tradeoffs, and an explicit review outcome with the actual reviewer/date.

The unresolved provider choice blocks **FR-001** from epic readiness. It does not
block definition of booking and roster epics against the local-session contract;
those epics must carry their authentication integration dependency and all
cross-cutting NFR criteria. This distinction does not permit releasing a product
without sign-in.

## Consequences

Local sessions add a database read to protected operations and make that store
part of the availability boundary. They provide one enforceable revocation rule
across identity vendors. Managed identity still requires a verified onboarding
and recovery process; it is not an automatic solution to volunteer access.
The proposed choice will need revisiting if the provider cannot support the
adapter contract or introduces contact-data exposure outside coordinator access.
