Linux has a **monolithic, modular kernel**: scheduling, memory management, filesystems, and drivers run together in privileged kernel space. They communicate through internal function calls and shared data structures; many components can be loaded as modules.

These three subsystems manage different parts of a program’s execution:

| Subsystem | Main responsibility | Key abstractions |
|---|---|---|
| **Scheduler** | Decide which runnable thread gets a CPU, and when | Tasks, priorities, per-CPU run queues |
| **Memory management** | Provide protected virtual address spaces and manage physical RAM | Page tables, memory mappings, physical pages |
| **Virtual file system (VFS)** | Provide a common interface to different filesystems | Open files, inodes, directory entries, filesystem instances |

Their relationships look like this:

```mermaid
flowchart TB
    A[Application threads] -->|System calls| V[VFS]
    A -->|Memory access and page faults| M[Memory management]
    S[Scheduler] -->|Chooses which threads execute| A
    V <-->|Cached file data and file mappings| M
    V --> F[Filesystem implementation]
    F --> D[Storage or network drivers]
    M <-->|Blocking and wakeups| S
    F <-->|Blocking and wakeups| S
```

**The scheduler provides execution time.** Linux schedules individual threads, including kernel threads. It tracks which are runnable, chooses among them according to scheduling policy, and balances work across CPUs. When a thread blocks waiting for data or a lock, another can run. Waking a thread makes it eligible to run; it does not necessarily run immediately.

Scheduling policies differ: ordinary tasks use fair scheduling, while real-time and deadline tasks have separate policies. Modern Linux fair scheduling uses EEVDF to balance CPU entitlement and responsiveness. [Kernel scheduler documentation](https://docs.kernel.org/scheduler/sched-eevdf.html)

**Memory management provides the address space in which execution happens.** Each process normally has its own virtual address space; threads within that process share it. Page tables translate virtual addresses into physical memory and enforce access permissions.

Memory is often supplied on demand. Accessing a valid mapping whose page is not yet present causes a **page fault**: the kernel may allocate RAM, load file data, or retrieve swapped data. Under memory pressure, it can reclaim cached pages or swap eligible anonymous memory. A page fault therefore may finish quickly or require an I/O wait. [Memory management concepts](https://docs.kernel.org/admin-guide/mm/concepts.html)

**The VFS provides a common file interface.** Applications use operations such as `open()`, `read()`, and `write()` whether a file lives on ext4, another local filesystem, or a network filesystem. The VFS resolves paths, coordinates access checks, and dispatches operations to the appropriate implementation.

Its main objects include an **inode** for a filesystem object, a **dentry** linking a name to that object, and a **file object** representing an open instance, including its offset and access mode. A process’s file descriptor refers to that open file object. [VFS overview](https://docs.kernel.org/filesystems/vfs.html)

The strongest connection between filesystems and memory management is the **page cache**: RAM containing file data. Ordinary buffered reads and writes use it, and typical file-backed `mmap()` mappings expose those same cached pages through a process’s virtual address space. [Page cache documentation](https://docs.kernel.org/mm/page_cache.html)

Consider a thread reading a regular file whose data is not cached:

1. **VFS:** `read(fd, buffer, size)` resolves the descriptor to an open file and invokes its read operation.
2. **Memory management and filesystem:** The read path allocates page-cache memory and requests the missing data through the filesystem and storage driver.
3. **Scheduler:** If the thread must wait, it sleeps, allowing another runnable thread to use the CPU.
4. **I/O completion:** When the data arrives, completion handling wakes the waiting thread.
5. **Scheduler and memory management:** Once scheduled again, the thread resumes the read path, which copies the cached data into its user-space buffer.

For `mmap()`, a memory access can trigger a similar sequence through a page fault, with the resulting page mapped into the process instead of copied into a read buffer.

The relationship also works in reverse: memory pressure can trigger cache reclamation and file writeback, which creates I/O and changes which threads are runnable. Consequently, a program’s performance depends on how **CPU availability, memory availability, and file access interact**.
