# ADR-001 — Hosted identity provider for volunteer sign-in

## Context and status

[PRD-001](../prd/PRD-001.md) explicitly leaves the provider unresolved. It does
not establish whether volunteers have email accounts, an existing organizational
identity, a preferred sign-in method, a provider budget, or an enrollment/recovery
process. Phone numbers must be visible only to the coordinator; a phone-based
login must not be assumed acceptable. No provider has been selected, purchased,
configured, or capability-tested. This record captures the decision gap rather
than asserting an accepted decision without evidence.

## Proposed boundary

Use a hosted identity service with a server-side adapter and application-owned
opaque sessions as specified in [ARCH-001](../architecture/ARCH-001.md).
Keep application roles, contact data, and session revocation in the application
database. Provider tokens alone must not authorize booking or roster requests.
This separates NFR-001's five-minute revocation requirement from provider token
lifetimes. NFR-003 rules out an identity server operated on food-bank premises.

## Alternatives to evaluate

| Option | Benefit | Evidence still needed |
|---|---|---|
| Managed consumer identity with hosted login | Outsources credential handling and recovery | Supported volunteer sign-in channels, mobile usability, enrollment controls, recovery behavior, cost, and privacy characteristics. |
| Existing organizational identity service | Could reuse existing accounts and administration | Whether it exists and covers all volunteers, external-user support, administration burden, and recovery. |
| Custom credential service on hosted infrastructure | Full control of flows | Would require owning credential security and recovery; no supplied requirement justifies this additional pilot scope. Not the proposed direction. |

## Decision exit criteria

1. Identify supported volunteer sign-in channels and an enrollment route for the
   existing volunteer directory; do not silently assume every volunteer has email
   or an organizational account. Establish who handles lost access.
2. Select a named hosted provider and protocol based on verified documentation,
   pilot cost, and supported deployment configuration. Record alternatives and
   tradeoffs here. Provider evaluation is pending; this document makes no vendor
   capability claims.
3. Exercise valid and invalid login, stable identity mapping, logout, expiry,
   recovery, and replay protection in a hosted test environment. Ensure recovery
   cannot link a person to another volunteer's bookings or grant privileged roles.
4. Demonstrate that application revocation invalidates all older application
   sessions on multiple instances within 300 seconds, including attempted refresh
   or renewal with old application credentials. Define provider logout/fresh-login
   behavior explicitly; session revocation is not an account-suspension feature.
5. Verify that identity responses, claims exposed to the browser, recovery flows,
   logs, and administrative application screens do not reveal volunteer phone
   numbers to a non-coordinator.
6. Record the selected option, evidence, unresolved limitations, and decision
   owner/date; update this ADR's status and ARCH-001's FR-001 readiness together.
   Priya Nair is the PRD owner; no architecture approval by her is implied here.

## Impact on epic definition

FR-001 remains BLOCKED for a delivery epic because its provider-specific sign-in,
enrollment, and recovery behavior cannot yet be specified. Identity discovery
and a provider proof can be scoped now. FR-002 and FR-003 are READY for epic
definition against the provider-independent principal/session contract, with
FR-001 explicitly recorded as a delivery dependency. NFR-001's application
mechanism, NFR-002's access boundary, and NFR-003's hosted topology are defined;
they remain mandatory shared acceptance criteria regardless of provider choice.
