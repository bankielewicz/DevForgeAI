# ADR-003 — Phone-number privacy

## Context and decision

NFR-002 says phone numbers are visible only to the coordinator. Treat this as a
server-enforced data-access rule applying throughout the product. Hiding a UI
field does not meet it. Even a volunteer's own phone is excluded from volunteer
responses under the literal requirement. An administrator-only grant gives no
phone access; a person holding both roles receives it through the coordinator grant.

Store optional phone numbers separately from ordinary volunteer/profile records.
Only the coordinator-authorized roster/contact query joins that table. Use explicit
response field allowlists and current database roles before querying and serializing
contact data. Booking, sign-in, session revocation and generic user lookup responses
never include phone fields. Do not put phones in identity claims, URLs, exception
messages, metrics, audit events or request/response logs. No public export or
contact-editing endpoint is implied by the PRD.

Authenticated pages and APIs use `Cache-Control: no-store`; prohibit CDN/shared
caching and offline service-worker caching of private responses. The client clears
roster state on logout or authorization failure. Each refresh reauthorizes the
coordinator. Previously delivered data cannot be recalled, but role removal denies
all subsequent phone reads without waiting for session expiry.

Database access uses least-privilege service accounts; operational access is
restricted and audited. Hosting operators and backups are part of the trusted
operational boundary (A-05), not application roles that receive a phone UI. Test
fixtures use synthetic data. Contact import must be coordinator-authorized and
must not echo phones into operational logs. Storage and backup encryption supplement
access control; they do not replace it.

## Alternatives and consequences

| Alternative | Assessment |
|---|---|
| Return phones to everyone, hide the column | Leaks through network responses and browser state; fails NFR-002. |
| Give all administrators implicit contact access | Violates coordinator-only access for administrator-only users. |
| Separate contact service | Could isolate data further but adds operational overhead without a pilot requirement. |
| Separate storage projection within the application (selected) | Keeps the access boundary testable with one deployment; every new data surface must reuse the authorization and projection rules. |

NFR-002 is ready for epic decomposition. Before delivery, test anonymous, volunteer,
administrator-only, coordinator and combined grants through direct HTTP requests;
scan rendered HTML, bodies, errors, logs and cache behavior using synthetic phone
canaries. A phone privacy failure blocks delivery of the affected feature even if
the roster displays correctly. These runtime tests remain NOT_RUN.
