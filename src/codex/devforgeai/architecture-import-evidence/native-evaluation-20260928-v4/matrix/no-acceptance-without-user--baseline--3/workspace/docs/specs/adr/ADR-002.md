# ADR-002 — Hosted application and consistent booking

## Context and decision

Three daily shifts and about 120 volunteers need a phone-friendly website and
coordinator roster. NFR-003 requires hosted operation for the entire product.

Use one hosted modular application with managed PostgreSQL as the authoritative
store for shifts, bookings, contacts, roles and sessions. Identity authentication
is hosted separately per [ADR-001](ADR-001.md). Deploy all runtime dependencies,
secrets, logs, backups and automation on hosted services. No local food-bank server
or persistent workstation is required. Hosting vendor and framework selection
belong to the foundation epic and must satisfy these contracts.

All booking writers lock the shift row in a transaction before checking capacity
and inserting. Enforce unique volunteer/shift pairs and foreign keys in the
database. Capacity updates use the same lock. The coordinator reads the primary
database with no event queue or eventually consistent roster projection. Define
the exact operations and failure responses as in
[ARCH-001](../architecture/ARCH-001.md).

Use fixed published shift records for the pilot, seeded by a controlled setup
process. A full scheduling administration product is not inferred from booking.
Use timed HTTP refresh for the roster; real-time streaming is unnecessary for the
proposed 30-second refresh interval and complicates session revocation.

## Alternatives and consequences

| Alternative | Assessment |
|---|---|
| Microservices and event-driven roster | Adds deployment boundaries and consistency lag without a requirement or scale justification. |
| Browser writes directly to hosted storage | Makes authorization, contact projections and concurrent capacity control harder to keep in one enforceable boundary. |
| On-site server | Conflicts with the explicit whole-product hosting requirement. |
| Hosted application and relational transactions (selected) | Small operational footprint and a shared consistent roster, with the database as an availability dependency. |

The platform epic must verify hosted database transaction behavior, bounded request
execution, backups and restore procedures. Test capacity races against the actual
database, not mocked counts. Reject unsafe capacity changes. No numeric uptime,
throughput or recovery commitment is invented. FR-002, FR-003 and NFR-003 are ready
for epic decomposition; runtime and infrastructure verification remain NOT_RUN.
