# ADR-001 — Identity and revocable sessions

## Context

PRD-001 explicitly requests an identity-provider ADR for FR-001. NFR-001 also
requires an administrator to revoke all a volunteer's signed-in sessions within
five minutes. Provider selection alone does not establish this guarantee.

## Decision

Select Auth0 hosted login with a database email/password connection for the pilot.
Use OIDC authorization-code flow with PKCE through the web application's server.
Provision known volunteers, with no public registration and no automatic grants
from an email domain. Use the provider for credentials and recovery; store product
identity links and roles locally. Email access and tenant suitability are explicit
validation tasks A-01 in [ARCH-001](../architecture/ARCH-001.md), not known facts.

Auth0 documents authorization-code login for regular web applications and managed
database authentication. These sources establish feasibility, not deployed proof:
[authorization-code flow](https://auth0.com/docs/get-started/authentication-and-authorization-flow/authorization-code-flow/add-login-auth-code-flow)
and [database connections](https://auth0.com/docs/authenticate/database-connections)
(consulted 2026-09-28). No pricing, region or availability guarantee is assumed.

After validated authentication, issue a cryptographically random opaque cookie;
store only its hash in PostgreSQL. Cookie attributes are Secure, HttpOnly,
SameSite=Lax, host-only and Path=/; rotate on login. Set an eight-hour absolute
expiry as a pilot design default. Do not request offline access or expose provider
tokens to browser storage. Local APIs accept only local sessions.

Every protected request checks the primary database for session existence, expiry,
enabled user, matching session generation and current role. No positive authorization
cache or asynchronous replica is permitted. Authorization-store failure denies
access; it does not extend cached authorization.

The administrator action locks the target user and increments its session
generation, records a revocation cutoff timestamp and writes an audit event in one
transaction. The committed generation invalidates every earlier session on every
application instance. Acknowledge success only after commit. Repeated revocation
is safe. A failed transaction reports failure, never a queued success.

Define t0 as the durable revocation commit. New protected requests after t0 reject
old sessions immediately, giving no propagation delay against the 300-second
requirement. Recheck session validity inside booking mutations; serialize that
check and commit against revocation using the user-row lock. Bound other protected
requests to 30 seconds and use no long-lived authenticated streams: a response
already authorized before t0 cannot continue beyond the five-minute bound. A
revocation cannot retract information already delivered to a browser.

Provider SSO must not silently turn a revoked cookie into a new local session.
New local sessions require fresh provider authentication using `max_age=0` and
server-side validation of `auth_time` against the login attempt and revocation
cutoff. Use one-use, expiring state/nonce, bind the callback to the initiating
browser, and compare against the latest cutoff while holding the same user lock
used by revocation. Reject ambiguous timestamp ordering and restart login; do not
relax the cutoff with clock-skew allowances. Monitor server clock alignment.
Concurrent callback/revocation either creates a session that is then invalidated,
or requires authentication after the cutoff. A new deliberate login is permitted;
revocation is not permanent account suspension.

Auth0 documents server validation of `auth_time` and limitations with federated
providers; the pilot uses its database connection rather than assuming an upstream
social provider forces reauthentication. See
[reauthentication guidance](https://auth0.com/docs/authenticate/login/max-age-reauthentication)
(consulted 2026-09-28). Provider-session logout is optional defense in depth and
is not on the required revocation path.

## Alternatives and consequences

| Alternative | Assessment |
|---|---|
| Application-managed passwords | Avoids identity vendor, but adds credential storage, recovery and abuse-control work outside a small pilot's core function. |
| Self-hosted identity server | Adds identity operations; on-site hosting violates NFR-003, and cloud self-hosting is unnecessary operational work here. |
| Provider JWTs accepted directly until expiry | Does not by itself prove administrative revocation within five minutes; requires an additional revocation check or rigorously bounded token/refresh strategy. |
| Hosted identity plus local opaque sessions (selected) | Keeps credential handling managed and revocation deterministic, at the cost of a primary-database check per request and local session storage. |

Provider outage blocks new login but need not invalidate unexpired local sessions.
Database outage blocks protected work. This is an intentional security/availability
tradeoff at pilot scale. Account migration, email suitability and hosting cost
remain operational risks. FR-001 and NFR-001 are ready for epic design with the
verification cases in ARCH-001; provider integration and timing tests remain NOT_RUN.
