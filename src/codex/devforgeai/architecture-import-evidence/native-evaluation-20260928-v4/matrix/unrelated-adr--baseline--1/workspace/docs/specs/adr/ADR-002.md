# ADR-002 — Use managed Cognito sign-in with application sessions

## Context and drivers

PRD-001 explicitly leaves the identity provider undecided. About 120 volunteers need
mobile browser access; there is no existing application or identity integration in this
workspace. ADR-001 governs logging, not identity selection. Avoid operating password
storage and keep phone numbers out of identity profiles (NFR-002).

## Options and proposed decision

Recommend Amazon Cognito user pools with managed login, email/password accounts, and
the authorization-code flow with PKCE. This fits the AWS hosting proposal in ADR-005.
Supabase Auth is a viable managed alternative but introduces another provider into that
deployment. Application-owned passwords avoid provider coupling but add credential
recovery and security operations. Social-only login assumes volunteers have suitable
external accounts; the PRD supplies no evidence for that assumption.

Use a confidential server-side callback with exact registered redirects, single-use
state, nonce, and PKCE validation. Validate issuer, audience, signature, expiry and token
use before mapping the stable provider subject to a local volunteer. Require an active,
provisioned local account; disable public registration. Request only identity/email
claims and do not store phone numbers in Cognito.

The callback creates the opaque application session defined by ADR-003. Provider tokens
stay on the server and are discarded after the exchange; application APIs accept only
application sessions. Use managed login's `prompt=login` for fresh authentication.
Passwords and recovery remain with Cognito; no password-handling endpoint is added to
the application. Initial account invitations are an operational provisioning step,
not a new volunteer-registration feature.

## Consequences and unresolved assumptions

- Managed credentials reduce application responsibilities but introduce identity-service
  availability, account recovery, configuration and billing dependencies.
- Email availability and an operator for invitation/recovery are unverified; A-01 in
  the architecture must be resolved before FR-001 is treated as ready.
- Eight-hour application sessions and fresh authentication on expiry are proposed
  defaults in ADR-003, not requirements already approved by the PRD owner.

## Confirmation evidence required

Identity integration tests must show successful invited-user sign-in on a mobile browser,
denial for an unprovisioned subject, invalid/replayed callbacks and wrong issuer/audience,
usable recovery, and no passwords, provider tokens or phone numbers in logs or browser
storage. The opaque application-session cookie is the only browser credential retained.
Test provider outage without granting access. These tests have not been run.

## Sources and status

Provider capabilities checked 2026-09-28: [Cognito authorization endpoint](https://docs.aws.amazon.com/cognito/latest/developerguide/authorization-endpoint.html)
and [JWT validation](https://docs.aws.amazon.com/cognito/latest/developerguide/amazon-cognito-user-pools-using-tokens-verifying-a-jwt.html).
Managed login supports PKCE and forced re-authentication; the classic hosted UI does
not support the same `prompt` behavior. Deployment must use the managed login version.
