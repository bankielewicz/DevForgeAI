# ADR-003 — Enforce session revocation through shared application state

## Context and proposed decision

NFR-001 requires an administrator to revoke a volunteer's signed-in sessions within
five minutes. This applies to every protected route, including booking and roster reads.
Use opaque random session cookies and a shared session store, checked on every request.
JWT signature verification alone cannot establish revocation. A short token lifetime
alone also leaves refresh, cache and clock-skew failure modes.

Store only the hash of a high-entropy cookie value, user ID, authentication epoch,
creation/expiry times and individual revocation state. Set `Secure`, `HttpOnly`,
`SameSite=Lax`, host-only scope and an eight-hour absolute lifetime with no sliding
renewal. Apply CSRF tokens and origin validation to business/admin mutations; their GET
routes never mutate. The authentication callback uses the state/nonce checks in ADR-002.
TTL cleanup is housekeeping, not the mechanism for denying expired sessions.

The local user record holds roles, an active flag, `session_epoch`, and
`revoked_before`. Every request transactionally reads the session and user from the
primary regional store and checks expiry, active status, role, individual revocation
and matching epoch. Do not cache positive authorization results at the gateway,
application or CDN. Store errors fail closed with a service-unavailable response.

An administrator-only endpoint atomically increments the volunteer's epoch and records
the revocation cutoff plus an audit event. A success response means the write committed;
failure must be shown as failure and be safely retryable. All old application sessions
then fail their next check. Session creation conditionally writes against the current
epoch and requires provider `auth_time` strictly after the cutoff. Authentication in
the same clock second is conservatively rejected and retried. Old provider cookies or
refresh tokens cannot silently recreate application access; there is no token-to-session
API outside the validated fresh-login callback.

For booking, repeat the user epoch/active checks as conditions inside the booking
transaction. Bound protected request execution to 30 seconds. Requests admitted before
revocation may finish within that bound; subsequent requests must fail. This leaves
substantial margin below 300 seconds without depending on asynchronous propagation.
Revocation ends sessions; disabling future sign-in is a separate operation and is not
silently added to NFR-001.

## Alternatives and consequences

Stateless bearer tokens simplify reads but do not alone meet the revocation guarantee.
Per-instance denylists fail across instances and restarts. Shared state adds a read and
a dependency to every protected request; an outage sacrifices availability to preserve
authorization. Administrator and coordinator are distinct capabilities (ADR-004).

## Confirmation evidence required

Create multiple sessions for one volunteer on different browsers and application
instances. Revoke them once, measure from the administrator's request, and assert that
all protected operations reject those sessions no later than 300 seconds. Also test
revocation/login and revocation/booking races, replay, store outage, expiry, individual
logout, an unaffected volunteer, and denial of revocation by a non-administrator.
Record timestamps and responses; this design is not measured compliance evidence.
