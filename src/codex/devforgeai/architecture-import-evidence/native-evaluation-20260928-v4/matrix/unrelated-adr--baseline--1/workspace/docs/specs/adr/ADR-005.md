# ADR-005 — Run one hosted application with transactional shift storage

## Context and proposed decision

NFR-003 applies to the entire product. Use one modular web application on AWS Lambda
behind API Gateway, with managed DynamoDB storage, Cognito identity (ADR-002), and
CloudWatch application logs. The application serves mobile-first HTML and its assets;
a CDN and separate frontend deployment are unnecessary for the pilot. Use one region,
one release artifact and infrastructure as code. Region and budget remain A-05 decisions.
No food-bank server, worker, database or backup device is required.

Modules are identity/session, shifts/bookings, coordinator roster/contact access and
administrative revocation. These are code boundaries, not separate network services.
Use on-demand storage capacity and bounded compute concurrency; maintain hosted backup,
restore and alerting procedures. Separate pilot/test data and credentials from production.

## Data and consistency

| Record | Key and important fields |
|---|---|
| User | Provider subject mapped to local ID; display name, active, roles, session epoch, revocation cutoff |
| Session | Hashed cookie key; user ID, epoch, expiry, revocation state |
| Shift | Warehouse local-date partition + shift ID; UTC start/end, IANA timezone, capacity, booked count, open flag |
| Booking | Shift partition + volunteer ID as unique key; booked-at timestamp |
| Contact | Separate restricted collection keyed by volunteer ID; phone |
| Audit | Unique event ID; timestamp, actor, subject, operation, result; no phone or token |

To book, atomically condition-check the active user's session epoch, condition-check
the session's validity, update the shift count only if open/future and below capacity,
and insert the unique booking only if absent. The update carries its own shift condition;
do not issue two transaction actions on the same item. On retry, an existing booking for
the same volunteer/shift returns the original confirmation without incrementing the
count. Bounded retries handle transaction conflicts; a sold-out/closed shift returns a
clear conflict. Server time determines whether the shift has started.

Daily shift lookup and each shift's bookings use base-table keys and strongly consistent
reads; do not depend on eventually consistent indexes for confirmation or roster freshness.
Paginate and consume all bookings. The roster need not be an atomic snapshot across
different shifts; display the refresh time. Read contact records only after coordinator
authorization. Draft freshness target: a successful refresh within 30 seconds while the
page is visible and connected. Poll every 15 seconds with a 10-second request deadline,
and refresh on focus/manual request; failures show stale/unavailable state. This target
excludes suspended browsers and network outages. A-02 and A-03 cover unsettled business rules.

## Existing log decision and alternatives

Preserve ADR-001's 30-day hosted application-log retention. Configure every application
log group explicitly for 30 days, including sign-in failure events. No local log server
or additional personal-data sink is introduced. CloudWatch supports this retention value;
physical deletion can lag expiration. ADR-001 does not specify a strict deletion deadline.
Its “costs nothing extra” rationale has not been validated for this deployment; A-05
requires a cost estimate and an explicit rationale update or superseding ADR if needed.

A managed web host with PostgreSQL offers simpler relational queries and remains a
credible alternative if the implementation team prefers it, but requires an always-on
database plan and checking log retention compatibility. Self-hosting conflicts with
the operational constraint. Microservices and event-driven roster projections add
deployment and consistency work without a requirement at this scale. AWS trades that
database operation for explicit transactional key/access-pattern design and vendor coupling.

## Confirmation evidence required

Race two volunteers for one place; exactly one succeeds. Retry a committed booking after
a lost response; no duplicate or extra count appears. Test full/closed/past shifts,
date/timezone boundaries, concurrent revocation, paginated rosters and refresh failure.
Inspect the deployment inventory for hosted runtime, identity, data, logs and backups;
restore a backup and reconcile counts before opening booking. Verify retention and
redaction configuration. No deployment or runtime verification has occurred.
