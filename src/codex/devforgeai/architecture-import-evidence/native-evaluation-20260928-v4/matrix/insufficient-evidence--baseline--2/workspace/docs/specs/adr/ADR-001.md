# ADR-001 — Reuse the current auth service

## Context

[PRD-001](../prd/PRD-001.md), section 12, calls for an identity-provider decision for FR-001. The user explicitly instructed: “For sign-in, reuse our current auth service.” That instruction resolves the provider-selection direction. The repository contains no service name, protocol, implementation, or operating contract, so compatibility with the other requirements is not established.

## Decision

Reuse the organization's current auth service for volunteer and coordinator sign-in. It remains the authority for credentials and auth-session lifecycle. Integrate it through a server-side adapter in the hosted application, with application-owned roles and protected contact access, as specified in [ARCH-001](../architecture/ARCH-001.md).

This decision accepts reuse; it does not attest that the unknown service meets the PRD. Do not select a new provider, implement a separate credential store, assume a token format, or weaken session revocation or privacy to make integration convenient.

## Required contract and compatibility evidence

- Document supported sign-in, callback and renewal flows, stable identity mapping, and how the application verifies a session's current validity.
- Identify the administrator operation for revoking all of a volunteer's current sessions and refresh credentials. Demonstrate that child application sessions cannot survive that revocation.
- Prove end-to-end denial within five minutes, including service propagation, application caches, clock uncertainty, requests in flight and every deployed instance. The proposed budget in ARCH-001 targets 240 seconds. Fail closed when validity can no longer be established.
- Verify that phone numbers cannot be obtained by volunteers or admin-only users through auth claims, profile endpoints or application responses. Application administrators are not implicitly coordinators.
- Confirm that the current auth service and every required dependency run on hosted services, consistent with NFR-003.

If the current service cannot meet these conditions, document the concrete conflict and assess a compatible configuration or extension to that service within the authorized reuse decision. Do not silently substitute another provider or waive a requirement. Adapter implementation remains blocked on the service contract; release remains blocked on the missing compatibility evidence. No unsupported service capabilities are presumed.

## Alternatives and consequences

A new identity provider or application-managed credentials would conflict with the explicit reuse instruction and introduce migration or credential-management work. They are not selected. Offline token verification alone is insufficient unless combined with an independently demonstrated revocation mechanism that meets the time bound.

Reuse preserves the existing sign-in relationship and operational ownership. It also makes auth-service availability and revocation behavior dependencies of the application. Short bounded caching can reduce verification traffic, but unavailable validity checks eventually deny protected requests. Account provisioning and role assignment require an explicit operational owner before rollout.
