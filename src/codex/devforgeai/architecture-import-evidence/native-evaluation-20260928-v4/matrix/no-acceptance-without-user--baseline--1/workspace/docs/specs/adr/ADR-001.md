# ADR-001 — Volunteer identity integration

## Context and status

[PRD-001](../prd/PRD-001.md) explicitly requires an identity-provider ADR for FR-001. It does not identify an existing organization account system, a usable email/SMS channel for every volunteer, enrollment/recovery rules, budget, or vendor. Smartphone access alone does not establish any of these. No provider is selected or procurement implied in this document.

## Proposed direction

Use a hosted identity provider behind a backend adapter, favoring a standard OIDC authorization-code flow with PKCE. Keep local user IDs, roles, and application sessions independent of the provider. Map identity by verified issuer and subject, never by an unverified email claim or a phone number supplied by the browser. Default to coordinator-approved enrollment of known volunteers; how enrollment and recovery work remains unresolved.

The application's own session control follows [ADR-002](ADR-002.md). Do not assume that a provider logout endpoint or access-token expiration alone satisfies the five-minute application-session revocation requirement.

## Alternatives and tradeoffs

| Approach | Benefit | Cost or unresolved fit |
|---|---|---|
| Hosted standards-based identity provider | Clear authentication boundary; local authorization remains portable | Requires choosing a provider, sign-in channel, account lifecycle, and operating cost after checking fit |
| Identity bundled with a hosted application platform | May reduce setup and account integration work | Must still meet local session revocation and coordinator-only contact access; provider coupling needs review |
| Application-owned credentials and recovery | Direct control over account behavior | Adds credential storage and recovery operations outside the pilot's core workflow; not selected for this design |

This is an architectural comparison, not a current vendor capability evaluation. No claim is made that an unverified service satisfies the requirements.

## Evidence required to resolve

The technical owner and product owner must record:

1. Named provider and supported sign-in method, with current official documentation and a small integration demonstration.
2. Evidence that intended volunteers can use that method, including enrollment and recovery; no assumption that phone records imply SMS-based sign-in or that every volunteer has email.
3. Verified callback handling, issuer/subject mapping, unknown-account rejection, and server-managed role provisioning. Identity claims cannot grant coordinator or administrator privileges automatically.
4. Behavior of provider sessions during application revocation and fresh sign-in. Every existing application session must remain invalid after revocation; no silent renewal through an old application session.
5. Hosted deployment fit, permitted data handling, account ownership, budget, and provider outage behavior.
6. Linked test evidence for the selected integration and explicit decision status/author. Review whether the adapter contract or dependent acceptance criteria changed.

Until this record is completed, ADR-001 remains proposed and **FR-001 is BLOCKED for epic readiness**. Provider-independent session, contact-access, and roster planning can proceed against the principal contract in [ARCH-001](../architecture/ARCH-001.md). No user question is necessary to record this boundary honestly.
