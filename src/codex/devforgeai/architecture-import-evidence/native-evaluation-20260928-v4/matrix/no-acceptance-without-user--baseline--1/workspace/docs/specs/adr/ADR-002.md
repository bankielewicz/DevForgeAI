# ADR-002 — Authoritative application sessions

## Decision scope

Accepted as a technical design decision in this architecture pass, not as evidence of stakeholder sign-off, implementation, or a passing runtime test. This choice is independent of the unresolved identity-provider selection in [ADR-001](ADR-001.md).

## Context

NFR-001 requires an administrator to revoke a volunteer's signed-in sessions, with revoked sessions stopping within five minutes. Provider-token lifetimes and distributed process memory cannot be the only revocation authority. The pilot is small enough to use the same transactional database for users, session state, and bookings.

## Decision

Issue a cryptographically random opaque application session token after verified sign-in; store only its hash. A session records the local user's session generation at issue time and an expiry. On every protected request, read the session and current user state from the authoritative database. Require an active user, unexpired/unrevoked session, and matching generation. Resolve current roles server-side; do not cache a positive authorization result between requests.

An administrator's revoke-all action increments the target user's generation transactionally. All earlier sessions then fail validation across all application instances. Audit success in the same transaction, and acknowledge it only after commit. Serialize session issuance and revocation using the user row so concurrent operations have a definite order: a session issued before revocation is invalidated; a genuinely new validated sign-in after it may create a new session. Retries of revocation can increment the generation again safely. Individual logout revokes only the current session.

Fail closed if authoritative state cannot be checked. Enforce bounded request execution (30-second design target), revalidate authorization at protected data access or write commit, and reauthorize retries. No long-lived stream or queued request can keep an old authorization indefinitely. The bound must remain below the PRD's 300 seconds even under concurrency and dependency failure.

## Alternatives

- Self-contained tokens without server checks leave revocation coupled to token expiry and renewal behavior. They do not provide the chosen immediate local invalidation contract.
- A distributed revocation cache introduces propagation and outage policies that this pilot does not need.
- Provider-only logout ties the application requirement to an undecided provider and may leave independently issued application sessions valid.

## Consequences

Each protected request incurs an authoritative database lookup. Database availability becomes a prerequisite for protected operations, a deliberate cost of avoiding stale authorization. This fits the single-backend design and works across hosted instances without sticky sessions. Index token hashes and user IDs; never log raw cookies or tokens.

The administrator permission does not grant access to phone numbers. Revocation does not delete accounts, cancel bookings, or prohibit a new sign-in. Any broader suspension policy needs a separate product decision.

## Required verification

- Establish two or more sessions for one volunteer and route requests across separate application instances. Revoke as an administrator and prove every old session is rejected within 300 seconds of the committed action, including reads and booking writes.
- Verify a volunteer/coordinator without administrator authority cannot revoke sessions; a failed/rejected revocation reports no success.
- Exercise concurrent session creation, revocation, and booking to verify the serialization order and bounded in-flight behavior.
- Disconnect the authoritative database and verify protected requests fail closed, with no cached fallback or session refresh bypass.
- Verify individual logout, expiry, role removal, token hashing, and a legitimate fresh sign-in after revocation.

These are future implementation checks. No executable application exists in the repository to run them yet.
