# ADR-001 — Reuse the current auth service

## Context

[PRD-001](../prd/PRD-001.md) leaves the identity provider open for FR-001.
The user directed: "For sign-in, reuse our current auth service."
NFR-001 additionally requires administrator session revocation to take effect
within five minutes; NFR-003 requires the entire product to run on hosted services.
No auth implementation or documentation was supplied in this workspace.

## Decision

Reuse the current auth service as the volunteer identity and sign-in authority.
This decision is accepted on the user's instruction; implementation feasibility
and security compliance have not been verified. Do not select a new provider or
build a parallel password system. Integrate through the application auth adapter
defined in [ARCH-001](../architecture/ARCH-001.md).

Obtain the existing service's sign-in, stable identity, session validation,
administrator revocation, refresh, and hosting contracts before implementing the
adapter. Prove the five-minute end-to-end revocation bound. Prefer authoritative
validation without positive caching; consider a shared application session
registry only if the actual administrator workflow and all session creation paths
can enforce the same bound. A token signature or local logout is not sufficient.

## Alternatives and consequences

Replacing the provider or building credential authentication would conflict with
the user's instruction and is not selected. The auth adapter permits the booking
and roster modules to depend on a small internal principal contract while the
existing protocol is integrated. Local authorization still controls coordinator
phone access; auth administration alone grants no contact access.

Reuse does not establish that the current service meets NFR-001 or is hosted.
Missing evidence is a release blocker, not grounds to waive requirements. If the
service cannot meet these constraints directly or through a complete application
session integration, record the conflict and revise this architecture with an
explicit resolution before release. No replacement service is implicitly authorized.

## Verification

Verify real sign-in, invalid-session rejection, stable identity mapping, and
administrator revocation across all devices and refresh paths within 300 seconds.
Verify hosted operation of the dependency. Current status: BLOCKED pending the
service contract and a runnable integration. See the requirement evidence matrix
in ARCH-001 for the remaining acceptance checks.
