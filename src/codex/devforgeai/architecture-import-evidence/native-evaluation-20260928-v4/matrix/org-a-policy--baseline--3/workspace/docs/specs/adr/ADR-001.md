# ADR-001 — Adopt mandated Org A identity; centrally validate application sessions

## Context and authority

[PRD-001](../prd/PRD-001.md) requests sign-in and administrator revocation effective within five minutes. Its identity-provider question and original “no mandated platforms” default conflict with [POL-001 SET-01](../policy/POL-001.md), which mandates Org A Identity Platform (OIDC), forbids overrides and cites external organization ADR-104.

The mandate is authoritative from the supplied policy. ADR-104 itself was not supplied and has not been reviewed. This local ADR records the product's adoption and proposed application session design; it does not replace, recreate or approve the organization's ADR. `proposed` refers to the local integration design; the provider mandate is already approved policy.

## Decision

Use Org A Identity Platform for credential authentication and recovery. Register this hosted application as an OIDC client using the organization's supported integration. Propose a server-side authorization-code flow with PKCE and validated callbacks, subject to the actual integration contract. Do not build password handling or choose a competing identity vendor.

Use opaque application session cookies with authoritative hosted database state. Every protected request validates the current session generation. An administrator revokes a volunteer's existing application sessions by atomically changing that generation. Fail closed if validation state is unavailable, recheck protected writes transactionally, and bound in-flight requests. See [ARC-001 §5.1](../architecture/ARC-001.md#51-sign-in-and-revocation--fr-001-nfr-001) for the complete proposed contract.

## Alternatives and consequences

| Alternative | Disposition |
|---|---|
| Product-owned credentials or another identity provider | Rejected by POL-001 SET-01; not an available product tradeoff. |
| Accept a long-lived application token solely by signature | Rejected for this design: it supplies no application-state check to invalidate an existing session within the required bound. |
| Depend only on unspecified provider logout/revocation | Not selected: those capabilities and their timing are unverified. Obtain the contract under GAP-01 before deciding provider-side behavior. |
| Centrally validated application sessions | Proposed: explicit revocation control across instances, with one database validation dependency per protected request and fail-closed availability behavior. |

The application owns authorization and application-session state, not identity credentials. Account suspension and identity-provider SSO termination are distinct from invalidating an existing application session. If organizational policy requires additional revocation behavior, integrate it; do not relax the PRD's five-minute bound.

## Evidence needed and affected readiness

GAP-01 in ARC-001 requires the authoritative Org A integration instructions, client onboarding, subject/provisioning contract, role authority, supported session boundary, and a successful test-client exercise. Prove that every targeted revoked session stops authorizing requests within 300 seconds, including concurrent and multi-instance cases. FR-001 and NFR-001 remain blocked for design finalization until this evidence exists. No provider features, organizational acceptance or runtime compliance are asserted by this ADR.
