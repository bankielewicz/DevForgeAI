# ADR-001 — Inherit Org A identity platform

## Context and authority

[PRD-001](../prd/PRD-001.md) section 12 requests a provider decision for FR-001.
[POL-001#SET-01](../policy/POL-001.md) already mandates Org A Identity Platform (OIDC), with no
product override. The policy cites organizational ADR-104, which was not supplied. This local
record inherits the mandate from the vendored policy; it does not reproduce or replace ADR-104.
Its proposed status concerns the local integration design, not whether the mandate is optional.

## Decision

Use Org A Identity Platform for every sign-in. The hosted backend is the OIDC relying party.
Use authorization code flow, with PKCE as an integration requirement, exact registered redirect
URIs, state/nonce correlation, and a maintained OIDC library. Validate signatures, issuer,
audience, expiry and nonce before binding the issuer/subject pair to an active enrolled user.
Confirm provider support/configuration during integration; do not fall back to a different IdP.

Issue an opaque application session after successful validation, as specified by
[ADR-002](ADR-002.md). Keep identity tokens and any required provider credentials server-side.
Request only identity claims needed to identify the user; do not request phone claims. Assign
application roles through trusted provisioning, not arbitrary identity profile fields. Never
merge accounts solely on a matching email address. The app stores no passwords and implements
no password recovery; provider-owned authentication handles those concerns.

The [OIDC Core specification](https://openid.net/specs/openid-connect-core-1_0.html) is the
protocol reference for code flow, ID-token validation and subject identity. It does not prove
that Org A's deployment supports the proposed configuration or that its login UI is accessible.

## Alternatives and consequences

Product-managed credentials and another commercial identity provider are excluded by policy,
not evaluated as available product choices. A browser-only bearer-token design would put more
session enforcement at the client boundary; the backend session design gives this product a
single authorization and revocation point.

The product depends on Org A for new sign-ins and enrollment. Existing local sessions remain
subject to local revocation and expiry. Obtain issuer metadata, client registration, enrollment
mapping and supported configuration as delivery prerequisites. Do not infer a five-minute
revocation guarantee from OIDC itself. G-02 must cover the hosted login journey as well.

## Coverage and verification

Direct coverage: PRD-001#FR-001. Related constraints: NFR-001 session revocation, NFR-002 data
minimization and NFR-003 hosted identity. See [ARC-001](../architecture/ARC-001.md), V-01/V-04/V-05/
V-06/V-08. Integration checks are NOT_RUN; effective epic readiness remains BLOCKED by G-01/G-02.
