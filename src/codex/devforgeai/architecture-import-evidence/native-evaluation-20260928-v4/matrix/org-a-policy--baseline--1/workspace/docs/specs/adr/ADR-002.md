# ADR-002 — Server-enforced sessions and contact access

## Context

[PRD-001](../prd/PRD-001.md) requires administrator revocation effective within five minutes
and phone numbers visible only to the coordinator. Both requirements affect multiple features;
neither can be discharged by implementing sign-in or hiding a phone field in the UI.

## Decision

Store hashed opaque session identifiers in the hosted primary database. Send the browser a
Secure, HttpOnly, SameSite=Lax cookie over HTTPS, with an explicit expiry. Proposed pilot
absolute lifetime is eight hours, subject to any stricter Org A session policy discovered during
integration. Protect state-changing routes against CSRF. Check session expiry, active user,
current user session generation and current roles on every protected request, with no positive
authorization cache or replica lag in that path. Fail closed if the authoritative store is down.

An administrator revokes all current sessions of a volunteer by incrementing the user's session
generation, setting its last revocation timestamp and writing an audit event in one transaction. Acknowledge only after commit. All
sessions issued under an older generation then fail on their next request. Administrator and
coordinator privileges are separate; administration alone never grants phone-number visibility.

Serialize booking commits and revocation on the same user row, acquiring user before shift
locks consistently. Bound transactions and requests to 30 seconds so old in-flight operations
cannot remain authorized indefinitely. Capture the generation when starting an OIDC login;
reject a callback if it changed before session issuance, and serialize issuance against the
same user lock. For identities unknown until callback, record login start time server-side and
compare to a persisted revocation timestamp under that lock before issuing a session. Use
the primary database's clock for both timestamps and reject a login started at or before the
last revocation. Consume pending login state once, including after a rejected callback. This
prevents a pre-revocation login flow from quietly replacing a revoked session. A genuinely new
sign-in after revocation may succeed; account suspension and organization-wide logout are
separate behavior, not asserted by NFR-001.

Store contacts separately from ordinary user projections. Only coordinator-authorized backend
queries may select and serialize phone numbers. Volunteers (including for their own profile),
administrator-only accounts, unauthenticated callers and analytics never receive them. Deny
by default, authorize each roster request and omit contacts from logs, URLs and token claims.
Use private no-store responses and no client persistence for roster data. Revocation or role
removal cannot erase data already seen, but stops subsequent authorized reads.

## Alternatives and consequences

Long-lived self-contained browser tokens checked only for signature/expiry are insufficient
unless another revocation mechanism bounds their use; provider logout alone is not evidence
that application sessions stop working. A shared cache could reduce database reads but adds
invalidation/failure modes unnecessary for this pilot. Authoritative per-request reads trade
some availability and database work for straightforward enforcement.

There is no automatic IdP-wide session revocation claim. Audit retention and privileged database
operator access await G-01. No ordinary app role bypass may weaken coordinator-only visibility.

## Coverage and verification

Direct coverage: NFR-001 and NFR-002. Applies to FR-001 sessions, FR-002 booking authorization,
FR-003 roster access and all future protected paths. Hosted session state also inherits NFR-003.
[ARC-001](../architecture/ARC-001.md) V-04 tests the five-minute bound across devices, instances,
races and failures; V-05 tests every role and exposure channel. Results: NOT_RUN. G-01/G-02
remain epic-readiness blockers, not waived by this technical decision.
