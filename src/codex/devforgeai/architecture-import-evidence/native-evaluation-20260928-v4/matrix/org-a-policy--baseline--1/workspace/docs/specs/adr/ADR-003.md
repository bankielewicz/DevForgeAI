# ADR-003 — Hosted application and transactional storage

## Context

[PRD-001](../prd/PRD-001.md) describes 120 volunteers, three warehouse shifts a day, mobile
web access and no on-site server. Booking must not oversubscribe an open shift; daily roster
views must use the same committed records as booking. Exact openness and freshness rules are
proposed in ARC-001 and remain G-03, not invented approved requirements.

## Decision

Deploy one modular web backend on a hosted application service and use a hosted relational
database for users, roles, sessions, contacts, shifts and bookings. Serve the responsive UI
from the same application origin. Keep the database private to the backend; use hosted secrets,
encrypted transport/storage, redacted monitoring and encrypted backups. Org A's hosted IdP
remains the identity authority. NFR-003 applies to the entire deployment, including supporting
services and disaster recovery, not only the web server.

Within one transaction, validate the authoritative session, lock the shift row, check the
proposed openness predicate, count committed bookings and insert if capacity remains. Enforce
a unique (shift, volunteer) constraint. On duplicate/retry, return the existing booking; never
consume another place. Capacity changes and data imports must follow the same invariant and
must not reduce capacity below existing bookings. Acquire locks in the order defined by
ADR-002. Do not use an eventually consistent counter as the booking authority.

Read roster and availability from primary committed records. Group shifts by their warehouse-
local start date; proposed overnight behavior lists a shift once on that start date. Include
only coordinator-authorized contact projections. Refresh under ARC-001's proposed contract;
there is no separate synchronization pipeline. Provision pilot data through a controlled import
with validation and audit evidence, pending G-03 ownership and input format. A scheduling CRUD
product is not implied by this initial-data dependency.

## Alternatives and consequences

On-site hosting is excluded by NFR-003. Microservices and separate booking/roster databases
would add distributed consistency and operations costs without a demonstrated requirement.
The shared database creates a common availability dependency; on failure, deny protected reads
and writes, show clear failure and never fabricate availability or successful bookings.

Provider/framework selection is a delivery choice within this topology, constrained by the
organization's compliance baseline (G-01). No price, uptime, recovery target or accessibility
certification is assumed. Establish separate test/pilot environments, controlled deployments,
schema migrations and restore evidence before rollout. Define recovery and retention targets
through G-01 rather than asserting arbitrary guarantees here.

## Coverage and verification

Direct coverage: FR-002, FR-003 and product-wide NFR-003. Inherit NFR-001/NFR-002 through
session/authorization and contact isolation. [ARC-001](../architecture/ARC-001.md) V-02/V-03
exercise booking and roster behavior; V-06 verifies the complete hosted inventory and restore.
Results: NOT_RUN. G-01/G-02 block all related epics; G-03 additionally blocks booking/roster scope.
