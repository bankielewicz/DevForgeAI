# Gaps, boundaries, and delivery

## Resolve only the blocked dependency

Classify gaps as missing input, contradictory requirement, missing decision, unavailable capability, denied operation, or changed input. Record exact source references, affected requirements/slices, why work cannot proceed, and the minimum decision, input, permission, or capability needed. Ask a precise question when a material decision cannot be derived. Continue independent permitted work; do not replace a gap with an optimistic assumption, vague TODO, or fake interface.

Optional analysis services can be replaced with ordinary terminal discovery. A required project authority cannot be replaced: discover its real interface, preserve actual response evidence, and stop affected protected operations when unavailable. An editable status or Python observation cannot authorize a transition or acceptance.

Use already supplied authorization. Ordinary implementation through QA permits reversible product edits and checks in scope; it does not authorize every command mentioned by a specification. Deployment, publication, merge, operational installation, startup configuration, and irreversible migrations require corresponding authorization. Do not alter requirements to bypass a failing check. Preserve unrelated files, prior attempts, and another actor's changes.

If permissions or tooling prevent a check, retain ERROR or NOT_RUN with the actual reason. Unknown job outcomes need inspection before retry. Use [evidence-resume.md](evidence-resume.md) before resuming or yielding unfinished work.

## Report actual delivery

Use [delivery template](../assets/delivery.md). State selected scope, actual artifacts/changed paths, source-qualified requirement accounting, exact candidate identity, executed checks and metrics, defects/gaps, unperformed platform/native/visual checks, and the next safe action. Planning/subset completion must be labeled as that selected scope, never whole-product completion.

Before marking an output requirement VERIFIED or overall development COMPLETE, reread its original destination selection and read back each promised file at its actual path. Record required versus actual paths and the supporting observation. A wrong root, missing file, altered path component, unavailable required location or unresolved selection conflict leaves the requirement unverified and the task PARTIAL or BLOCKED. Passing product tests, valid hashes at a different location, absence of a generic default directory, and self-authored preservation flags do not satisfy destination verification. Preserve all earlier attempts and explain any remaining correction.

Choose one overall development status:

| Status | Meaning |
| --- | --- |
| COMPLETE | Every selected deliverable and mandatory acceptance check has current supporting evidence and no required work remains. This is a development result. |
| PARTIAL | Useful selected work is delivered; required implementation or verification remains. |
| BLOCKED | No remaining selected work can proceed without a specific missing decision, permission, input, or capability. |

For individual checks use PASS, FAIL, ERROR, NOT_RUN, or NOT_APPLICABLE with evidence or reason. NOT_APPLICABLE requires a scope reason and cannot conceal unavailable required platforms. Implemented features with unperformed required QA are not overall COMPLETE. Required failures, regressions, and unresolved flakiness remain visible even if aggregate metrics meet numeric floors.

Report external framework acceptance separately: an actual current authority response with its locator/digest, or NOT_EVALUATED. Do not claim protected acceptance from development COMPLETE, successful Python evidence, or a fabricated receipt. Distinguish implementation, static checks, native execution, and acceptance so a reader can see precisely what remains.
