# Explicit adoption and specification revision

Read this reference only for explicit adoption, a validator adoption handoff, or a revision with an adopted lineage. Adoption records observed bytes and management selection. It supplies no historical authorship, skill-quality verdict, revision authority, installation, or compiled-Rust qualification.

## Intake and ownership

Resolve the selected project and exact existing `src/agents/skills/<name>/` target. V1 supports one Codex development package. Never adopt or mutate operational `.agents`, `.claude`, `.codex`, or personal skill directories. An operational source first needs an explicitly authorized ordinary development copy with before/after identity and byte readback. An invalid existing skill name is a recorded defect; preserve the directory and resolve any future identity in the revision specification.

Record the actual current user instruction, reviewed origin specification, and explicit managed file list. You may inventory a proposed list but may not approve it from file presence. User approval of a concrete complete list suffices. Preserve session authorization already covering these exact bytes; ask only for unresolved selection or changed proposals. Validation-only requests and `status: approved` documents supply no mutation/adoption authorization. Revision requires its own behavior, destination and managed-change authorization; one instruction can explicitly cover both operations but the records remain distinct.

Inspect selected prior evidence before capture. A valid successful generated baseline selects regeneration. Missing, corrupt, conflicting, or wrong-byte known history is an evidence error. Preserve it and obtain explicit acknowledgement before adoption after known failed history. A failed revision of a valid baseline keeps that baseline and cannot be bypassed by adopting again. Do not infer absence of history solely from absence of a convenient pointer file.

## Capture, evaluate, publish

Allocate a fresh `docs/plan/skill-adoptions/<name>/<run-id>/` evidence directory. Preserve every failed capture and publication attempt. Keep a bounded candidate root containing `evidence/` and the disjoint `destination/` after-observation snapshot. Within evidence, capture the complete permitted target in a separate snapshot directory and copy the reviewed specification. Enforce existing traversal, link/junction, excluded-boundary, 2,000-file and 32-MiB limits before reading or copying. Never change target bytes during adoption.

All evidence references are normalized paths relative to the selected candidate root, not absolute read locators. Original resolved paths identify the capture. Preserve that relative layout when carrying lineage evidence into a later bounded root; do not rewrite historical record bytes or rebase only some references. Snapshot immutability is a workflow convention; rehash every use.

Use `adoption-record.json` schema `1`, `record_kind: adoption`, with the required fields in [adoption-evidence.schema.json](../evals/adoption-evidence.schema.json). In addition to the adoption specification's identity/partition/reference fields, `managed_manifest` locates the separately stored manifest and `origin_spec_input` records `{resolved_path,bytes,sha256}`. Both complete and managed manifests have `{schema_version:"1",files:[{path,bytes,sha256}]}`; rows and partition lists are sorted, unique, normalized, and disjoint. The partition union is the complete permitted snapshot. Authorization is `{instruction,target_root,managed_manifest_sha256,origin_spec_sha256}`. `historical_origin` is always `unknown`. `known_defects` optionally records observed defects without blocking accurate custody. Preserve selected prior and quality evidence through their actual path/hash references; do not relabel failed quality checks as passed.

Re-read the live target and original specification. `source_readback` references a preceding JSON observation containing `{schema_version:"1",run_id,target_root,before,after,spec_before_sha256,spec_after_sha256,outcome}`. Before/after use size/hash rows; an unchanged capture uses `outcome: UNCHANGED`. Drift produces `SOURCE_CHANGED`, no active adoption pointer, and a retained incomplete attempt.

Prepare a request `{operation:"adopt",record:{...}}` containing captured identity, snapshot/spec/manifests, managed paths, authorization, and readback. `retained_user_paths` and `recording_state` may be omitted for the helper to compute. Run:

```text
python -B -X utf8 "<builder>/scripts/build_evidence.py" adoption-plan --snapshot-root "<candidate-root>" --request "evidence/adoption-request.json"
```

The helper writes observed JSON to stdout only. Exit 0 is a valid observation; 1 is a byte/evidence mismatch with an INCOMPLETE proposal; 2 is usage/access/structural error. It does not publish or establish user consent. Save the successful output as `evidence/adoption-record.json`. `recording_state: ADOPTED` describes custody after preliminary comparison, not final evaluation or publication. Do not emit `result: COMPLETE`, generated ownership, or fabricated builder history for adoption.

Run explicit `adoption-v1` cases with `adoption_consistency` params `{evidence:"evidence",destination:"destination"}`. The final JSONL is outside candidate-root and linked by the report, avoiding a self-reference. The grader compares the complete capture, managed subset, source/spec observations, selected references and after snapshot; quality defects do not invalidate accurate recording. Read back evaluator inputs and output. Freeze the evaluated record bytes even if the final evaluation fails; record that failure in the separate report.

After success, recheck live target/spec and all captured inputs immediately before pointer publication. Write a new external pointer in this run's evidence directory with `{schema_version:"2",run_id,target_name,origin:{kind:"adopted",path,sha256},baseline:[{path,sha256}]}`. Origin references the exact evaluated record; baseline is exactly the managed snapshot hashes. Read back the pointer and retain its actual bytes plus any previous pointer. Do not overwrite another run's evidence. Publication/readback failure is `PUBLICATION_INCOMPLETE`; a standalone ADOPTED record cannot start revision. This ordinary file publication provides no package-wide atomicity or protected admission.

## Validator input packets

Read the selected validator report, findings, proposed specification, target snapshot, management proposal, and review policy. Recheck their actual references and current target. `builder_readiness: READY` is an observation, never authority or provenance. If necessary, normalize a selected packet into the bounded `handoff` input shape in the schema: identity, target/managed/spec digests, `review_policy: review-before-repair`, actual `review_state`, selected report/findings/spec references, and readiness. Preserve the raw packet as a selected reference; this normalization does not replace review. Missing authorization or unresolved review stops dependent work while leaving a concrete proposal available. No automatic repair/revalidation loop is added.

## First and later specification revisions

Read [regeneration.md](regeneration.md) and [spec-build.md](spec-build.md). A verified published adoption pointer supplies **A** as the first B. Capture complete C independently; stage N and complete candidate checks before editing. Use the ordinary schema-1 `mode: spec_build` contract, binding the newly authorized specification and selected handoff. Keep adoption and revision instructions distinct.

Use provenance and revision-plan schema `2`: replace `prior_build` with `prior_origin:{kind:adopted|generated,path,sha256}` and add `adoption_origin:{path,sha256}`. Other fields retain their existing meanings. First-revision managed rows use `ownership: adopted`; newly generated paths use `generated`; unrelated C-only paths remain `retained_user`. These labels do not expand authority. A new occupied unowned path conflicts even with identical bytes. Required N artifacts must exist; modified obsolete managed files conflict. Absence differs from empty bytes. Generated ownership must be justified by the approved contract.

The helper's schema-aware `revision-plan` previews only verified origins and unchanged C/after snapshots. Before the first write recheck the complete current target against C; recheck each affected path immediately before mutation. Stop on drift or write failure, retain actual changed paths and after bytes as PARTIAL, and keep the same origin for retry. `retry_of` may link a retained PARTIAL or CONFLICT schema-2 plan with the identical prior-origin reference. Do not promise rollback.

Evaluate delivered bytes using `revision-spec-v2`, run structural/script/task checks, and read back actual delivery. An APPLIED plan may initially have no advancement. Only successful checks/readback permit COMPLETE schema-2 provenance and a new generated-origin pointer identifying N, which may differ from delivered retained edits. Re-evaluate final pointer accounting; retain failed publication evidence without advancing dependent work. Subsequent revisions use that last successful N as B and keep the original adoption reference. Schema-1 generated lineages continue unchanged.

Use the same bounded root layout for the original adoption and selected previous generated evidence. Graders rehash referenced record, baseline and observation bytes. Static evidence cannot independently prove user intent, chronology, or that a pointer snapshot was actually published; command receipts and independent task trials establish those observed workflow steps. Report recording, publication, quality, revision authorization, generated delivery, fresh revalidation, Rust qualification and installation separately.
