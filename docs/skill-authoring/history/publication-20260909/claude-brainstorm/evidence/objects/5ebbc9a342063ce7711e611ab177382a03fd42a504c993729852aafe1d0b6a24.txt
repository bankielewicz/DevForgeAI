## CHG-039 — the first-action failure, and what it does not license me to claim

R10's `CLOCK.json` describes the clock as taken "before any packet or assignment file was
read" while, in the same object, disclosing three preceding tool calls — one of which read
`CLAUDE-BRAINSTORM.md`. Those two statements are not compatible. The rule requires an
actual UTC observation as the first tool action, before any file read. **R10 did not meet
it.** That stands as reported; it is not repaired retroactively.

### What is withdrawn

R10's correction went on to claim the deviation "shortens this allocation rather than
extending it", and that the recorded start was late "by at most a few minutes". **Both
claims are withdrawn.** Neither is supported:

- The true first-work time is **unknown**. Nothing observed it. Without it there is no
  measured interval between it and the 19:19:29Z observation, so no bound — "a few
  minutes" or otherwise — can be placed on the deviation.
- Starting the clock later and then adding fixed 100- and 120-minute offsets moves both
  cutoffs *later* relative to the unrecorded earlier work. That is the opposite of a
  shortened allocation. R10 asserted the favourable reading of its own error.
- The true total duration and the original first-work-relative cutoffs are therefore
  also **unknown**.

### What is not asserted in their place

No overrun is inferred. No replacement or backdated timestamp is invented. The observed
19:19:29Z clock remains what it is — an actual observation, just not the first action —
and the unknown quantities stay unknown.

## CHG-040 — an invalid timestamp, labelled rather than altered

R10's external receipt carries:

```
"issued_at_utc": "2026-09-07T19:49:52.%f+00:00"
```

The literal `%f` was never expanded. The cause was `time.strftime("...%f...")`: `%f` is a
`datetime` directive and `time.strftime` does not implement it, so it passed through as
text. Re-read in this run, the field still does not parse —
`datetime.datetime.fromisoformat` raises `Invalid isoformat string`.

**That field is invalid**, and the exact fractional second of the R10 receipt issuance is
**unknown**. The whole-second portion of the string is not independently corroborated by
this correction and is not asserted here. The original bytes are not altered: a receipt is
custody evidence, and editing it to look correct would destroy the thing it is evidence
of. Byte-custody validity — R10's receipt did verify byte-for-byte — says nothing about
whether a field inside it is meaningful.

Every timestamp in the R11 run is produced by
`datetime.datetime.now(datetime.timezone.utc).isoformat()`, and every timestamp field is
parsed back with `fromisoformat` before closure.

## CHG-041 — counts and the overbroad verification instruction

### The counts

R10's records described "21 modified" against 25 selected files, which is wrong, and the
handoff carried a further stale variant. Recomputed in this run from R10's own
`SOURCE-MAP.json`:

| Quantity | Count |
| --- | --- |
| Selected R10 control files | 25 |
| Modified | 13 |
| Preserved unchanged | 12 |
| Added | 8 |
| **Final control tree** | **33** |

13 + 12 = 25 selected; 13 + 8 = **21 changed-or-added files**. That 21 is where the wrong
figure came from: it was reported as though 21 of the 25 selected files had been modified.
13 were.

independent states with their own evidence requirements, and no volume of no-model
observation touches them. R11 executes none of them either.
