# Recording rules: envelope, session, and honest reporting

Read this while filling artifact frontmatter, or when one of the awkward conditions below occurs. The governing sources are the DevForgeAI artifact contract and execution contract; this file distills only the parts a brainstorming session actually hits. When a runtime is supplying phase context, `managed-runtime.md` covers what it checks and what it publishes; the envelope rules here apply either way.

## Envelope fields

Every artifact this skill writes carries the `devforge.artifact/v1` envelope from the template. What to put in each field:

| Field | What goes here |
| --- | --- |
| `artifact_id` | `IDEAS-001`, `HANDOFF-001`. An externally selected output identity governs this field: where a managed contract, a task brief or the user names the artifact ID for this output, write that ID. Local allocation - the next unused number in the project's store - is what you do when no identity was selected, not a preference to weigh against one that was. Never reuse an ID for different content, and never allocate a substitute for a selected ID that is missing or that conflicts with what already occupies the destination: that is a `missing_inputs` entry and a blocked dependent write, exactly like a selected path you cannot use. |
| `revision` | `1` for a new ledger. Revising an existing ledger increments its revision and keeps the same `artifact_id`. A selected revision governs the envelope the same way a selected ID does: a contract binding `IDEAS-004` at revision 2 is checked for exactly that revision, so do not renumber it to agree with a local count, and do not carry a different one forward from the file you read. |
| `status` | `draft` while the user is still exploring. Only the user's actual adoption moves anything toward `accepted`. |
| `created_at_utc` | The real current UTC time for this revision. |
| `producer.skill_revision` | The SHA-256 of this skill's installed `SKILL.md` - one file's installed bytes. Name that scope where you write it: a plugin version covers whatever a manifest says and can be identical across two different drafts, and a placeholder check is about placeholders and vouches for neither. They are not interchangeable, and a later reader cannot recover which one a bare 64-character string was. A managed runtime binds the installed resource identities itself, so take the value from the context it gives you rather than assembling your own check. If no observable value reaches you, write `unknown` - not a plausible-looking digest. |
| `execution_ref` | The authority-selected session record's ID and revision (`SESSION-001@1`) plus where its bytes actually live. Only from a record you were given - usually there is none; see below. |
| `upstream` | Real inputs you consumed: an existing ledger, a change request. Each entry needs `artifact_id`, `revision`, `store`, `path`, `sha256`, and the `sections` you actually used - the target's own section names. Name the ones your work came from; if it came from the whole document, name the sections that document has. Omit the key only when the target has no stable sections at all. The target must carry its own `artifact_id` and `revision` and they must match; a file with no envelope is evidence, not upstream. See *Locators that resolve* below, and *Binding the ledger in the handoff* for the one entry a managed brainstorm handoff is required to carry. |
| `evidence` | Sources you actually retrieved: URL, retrieval date, version if relevant, and the claim it supports. A raw file you read - a log, an export, someone's notes - belongs here too, with the locator it actually has and marked as a raw file, rather than being dressed up as an artifact it is not. |
| `supersedes` | The prior revision you replaced, with its digest, and the locator where those bytes are still readable - which is not the path you just overwrote. Preserve them before writing; see *Locators that resolve*. |
| `decision_ref` | `null` until the user adopts something. This field is the difference between a proposal and a commitment. The adoption can come from what the user says here or from an earlier instruction of theirs that still stands and covers this change; when it is the latter, name that record and its revision, so the basis is visible rather than implied. A document's own `accepted` status, an unrelated decision reference, or the discovery of an archived revision is none of these things. |
| `missing_inputs` | Everything required that you could not resolve. This is the correct home for gaps. |

Placeholders (`{{...}}`) are the template's, not yours. A required field still holding one means the artifact is a draft.

## Locators that resolve

A reference is only as good as the bytes it resolves to. Three things go wrong often enough to be worth naming.

**`store` is a small vocabulary, not free text.** Use `project` for the consuming project's own artifact tree and `authority` for an external assignment/authority store you were given. Words like `project filesystem` or an absolute host path are not members of that vocabulary and tell a later reader nothing about which root to resolve against. Give `path` relative to the selected store's root, so the same reference still works from another checkout.

**A superseded revision needs somewhere to live.** Naming revision 1 and its digest while revision 2 now occupies that exact path produces a reference that resolves to the wrong content - and it is worse than a missing reference, because it looks checkable. Copy the prior bytes to a stable authorized location first, confirm the copy hashes to the digest you are about to cite, and cite the copy. A populated `supersedes` field is not by itself preservation. Neither is a copy that exists only inside some harness or evaluation directory the artifact's reader has no path to: if the bytes are not reachable from the locator you wrote, the reference is still broken.

**Identifiers you cannot resolve are `missing_inputs` entries.** If the prior bytes were already gone, or the archive location is not yours to write, or a stable ID for something simply does not exist yet, say that. Inventing an ID or citing a locator you did not check is the failure this section exists to prevent.

**`sections` names actual sections.** The key exists so a reader can find the part of the target you relied on. `sections: "all"` looks like a claim and resolves to nothing: it cannot be checked, it says nothing about what you used, and it passes every check by having no content to disagree with.

For `upstream` - the causal inputs your work actually came from - name the target's real sections: the ones you drew on, and if you drew on the whole document, the ones it has. Reading all of a source is not a reason to say less about it than reading half of it, and "I used everything" is recorded by listing everything, not by leaving the field empty. Omission is honest in exactly one case: the target has no stable sections to name. Say so in `missing_inputs` then, so a later reader can tell an unsectioned source from an unstated one. Never manufacture a heading the target does not have; a row, a table cell or a document title is not a section.

`supersedes` points at a prior revision rather than at a passage, so it is not asked for a `sections` claim at all. If you make one anyway, it has to resolve like any other.

**An artifact reference has to name an artifact.** `upstream` and `supersedes` assert that a particular artifact, at a particular revision, is what lives at that locator - so the target needs its own envelope with an `artifact_id` and a `revision`, and both have to match what you wrote. A target with no envelope is not an artifact; it is a file. That is fine, and often useful, but it belongs in `evidence`, marked as the raw file it is, keeping the locator it actually has. What it must not do is arrive as an artifact reference with the identity fields quietly left blank, because then nothing disagrees with anything and the reference passes by being empty.

After the last write, resolve every reference you made, including the repeated ones. The same digest usually appears more than once - an output table row, a resume or custody line, an invalidation condition, a continuation note - and correcting only the primary occurrence leaves a document that contradicts itself. Read each occurrence against the actual file.

## Binding the ledger in the handoff

On the ordinary brainstorm path the handoff is not merely *about* the ledger, it is derived
from it, and the envelope has to say so. The handoff's `upstream` carries exactly one
unambiguous entry for the completed ledger, and every one of these has to be the real
current value:

| Key | Value |
| --- | --- |
| `artifact_id` | The ledger's own `artifact_id`, as written in the ledger you just saved - the selected one where an identity was selected. |
| `revision` | The ledger's own revision, as an integer, not a string. |
| `store` | `project`. |
| `path` | The ledger's selected destination, relative to that store's root - the path the bytes are actually at. |
| `sha256` | The digest of the finished ledger bytes, complete and lowercase. |
| `sections` | Ledger headings you actually relied on: real headings present in that ledger, named exactly. |

One entry, not two: a second reference naming the same ledger by ID or by path makes the
binding ambiguous, and ambiguity is refused the same way an absent binding is. Other
upstream entries - a change request, an earlier ledger you consumed - stay as they are, and
each still needs a well-typed `revision` of its own.

The ledger's digest usually appears twice, in this entry and in the outputs row, and the two
are separate claims. The row records what the handoff produced; the `upstream` entry records
what the handoff came from, which is what a managed runtime checks at Focus after reading the
ledger bytes itself. A correct output row does not satisfy that check, and neither does a
digest that was true one edit ago - so bind this entry from the finished ledger, and if the
ledger changes afterwards, rehash and update both places.

Two cases carry no such entry, for the same reason: there is no ledger. A routed
handoff-only task is one - Explore and Record are `NOT_APPLICABLE` there, the selected
outputs are the handoff alone, and no binding is expected or invented to look complete. A
session where the ledger genuinely could not be written is the other; that belongs in
`missing_inputs`, with the dependent claim blocked rather than bound to a file that is not
there.

## Digests and their order

An artifact never contains its own complete-byte digest. Writing one is impossible to keep true anyway - inserting the digest changes the bytes it describes.

Hash in dependency order: finish the ledger, hash it, then reference that digest from the handoff. If something needs the handoff's own digest, compute it after the handoff is complete and keep it in an external record - never back inside the handoff. The handoff does not appear in its own outputs table.

Who holds that external record depends on the session. Under a managed runtime, the runtime publishes the receipt, reads it back, verifies it against the current bytes and returns its locator and digest itself; do not write one, and do not announce one on its behalf. With no runtime, the external record is your message to the user, and it describes unverified drafts.

Whichever record holds it, deliver that digest whole: all 64 characters and the exact path, in the message the user actually receives - not `2df6ddc4...` and not left behind in a tool result they will never scroll to. A truncated digest cannot be checked against anything, which is the entire purpose of quoting one, and the elided middle is where a substitution would hide. Compute it as the last thing you do: if any further edit lands after the hash, the receipt describes bytes that no longer exist, and the honest repair is to rehash and say so - not to publish the earlier number.

## When no session record exists

This is the normal case for someone with a new idea, and it is not an error. What it is *not* is evidence that you are the only writer. The absence of a record proves nothing about ownership in either direction, and "no record, therefore bootstrap mode, therefore I may write" is exactly the inference the execution contract rules out.

Bootstrap mode is available to an *observably assigned* single writer. Before dependent writes, establish two things and record what you actually observed:

1. **Authorization.** The user's own request is the scope. Write what they asked for, where they asked for it. A task you inferred is not authorization.
2. **Collision evidence.** Look before writing, at the actual target path: an assignment or session record naming a different owner, a write fence that excludes your target, or another branch or worktree claiming it. Any of those puts you in the competing-ownership case below rather than in bootstrap mode. An existing artifact produced by a session that is not yours is a *prompt to check*, not collision evidence by itself - almost every ledger you inherit was written by someone else. Look for whether that other assignment is still live, as the competing-ownership section describes, and weigh it against your own.

Having looked and found nothing is a genuine observation and is worth recording as one. Not having looked is not the same thing, and must not be written as if it were.

Record it as it is:

```yaml
execution_ref: null
missing_inputs:
  - "session assignment: no record found; wrote under the user's direct request after
     checking the target path for competing ownership evidence and finding none"
```

Do not invent a `SESSION-001`, do not invent a base commit SHA, and do not run `git init` or commit the user's work to manufacture a baseline. A worker-authored session ID proves nothing about ownership - assignment records come from the external authority, not from you.

If the user does supply a session record, use its ID and revision and respect the write fence it declares.

## Competing ownership

The trigger is any ownership evidence naming someone else for what you are about to write. It does not have to be a Git collision, and there does not have to be a second process actually running. Any of these is enough on its own:

- An assignment or session record that names a different owner for the target project, directory, or write fence.
- A write fence that permits some paths but not the one you were asked to write.
- A branch, worktree, or lease claim held by another session.
- An existing artifact in the target whose producer is a session that is not yours **and** whose assignment is still live - see the paragraph below before treating this one as a collision.

A synthetic or fixture assignment record still counts while you are operating under it. So does one with `base commit: null` and no repository - ownership is asserted by the record, not by Git.

**Past authorship is not a current claim.** Artifacts are meant to be revised, and almost every ledger you inherit was written by some earlier session. If the only thing you have is a different `producer` or `execution_ref` in an old document, you have history, not a competing owner - stopping there would make every artifact permanently unrevisable by anyone but its first writer, which is the opposite of what a durable ledger is for. Look for evidence that the other assignment is *active*: a fence that still names that owner for this path, a session record that has not been superseded or released, a lease or worktree claim, an assignment you were handed that says so. Weigh it against your own: if you hold a current authorization naming this target, that is the one that governs, and you revise the older producer's ledger normally - recording the real `supersedes` chain and leaving their attribution intact rather than rewriting it as yours. When the two genuinely conflict, or when you cannot tell whether the other assignment is still live, that uncertainty is itself the collision condition: stop the dependent writes and report what you read and where, rather than resolving it in your own favour.

When you find one: stop the writes that depend on that target and report the collision, naming exactly what you observed and the path you read it from. Then:

- Do not delete, reset, revert, or force past anyone's work.
- Do not switch branch, directory, or filename to make the write land somewhere else. A path that happens to be writable but was not assigned to you is not a fallback - taking it is the failure this rule exists to prevent, not a workaround for it.
- Do not ask the conflict away by re-reading the record until it says something more convenient.

What you can still do: everything that does not write into the contested target. If you were given an explicitly permitted report or outbox directory, writing your report there is allowed and is not an escape path - it is the declared delivery route. Say what you would have written and what you observed, so the rightful owner can pick it up. Both sessions' work is preserved; the operator resolves the ownership.

## Stale inputs

If an upstream artifact's current bytes no longer match the revision and digest you referenced, you have a staleness condition, not a silent upgrade. Either use the preserved referenced version or report the staleness - never relabel newer bytes as the old revision. The same applies when the installed skill, base commit, or candidate changed under you: mark the affected prior evidence stale and say what needs re-running.

## Checks that could not run

A check outcome is exactly one of `PASS`, `FAIL`, `NOT_RUN`, `COULD_NOT_RUN`, or `NOT_APPLICABLE`. Those five strings are the whole vocabulary for that field. Write the bare value and nothing else - no suffix, no "then repaired", no "at time of writing". A reader scanning a column of outcomes should be able to tell what happened without parsing prose, and a qualifier welded onto the value destroys that. Everything you want to add - what happened first, what changed, what the scope was - belongs in the evidence or scope column beside it, where there is room for it and where it does not corrupt the value.

The absence of an error is not `PASS`.

When something could not run, record `COULD_NOT_RUN` with the actual cause: tool absent, permission denied, no network, capability not implemented. Then block only the claim that depended on it; brainstorming itself continues with the uncertainty written down.

`NOT_APPLICABLE` is narrower than it looks. It means the check genuinely does not apply to this artifact - you are asked about a package helper and there is no package. It does **not** mean "required, but nothing can do it". No available tool judges whether the ideas are good or the attributions faithful, and that observation is still required; it is simply unperformed. Record it `NOT_RUN`, or `COULD_NOT_RUN` naming what would have been needed. Marking it `NOT_APPLICABLE` reads as "out of scope", which quietly retires an obligation the user is in fact still owed.

Note that no available check validates brainstorming quality. `devforge check` inspects structural policy and provenance and explicitly does not certify semantic behavior. Do not describe a structural pass as evidence that the ideas are sound.

## Finishing a handoff in the right order

A handoff describes the state at the moment it was written, and that is the only state it can honestly describe. So write it as of then - including checks that are genuinely `NOT_RUN` at that point, with the reason in the scope column - then save it, read it back, and deliver its digest outside the document.

Let the prose agree with those rows. It is easy to write "the ledger was saved and verified and its digest delivered" while the table beside it correctly records the verification as `NOT_RUN`, because the sentence is describing the plan and the table is describing the facts. A reader takes the sentence. Write the narrative in the tense the work is actually in - what is written, what remains to be checked, and by whom - so the document does not contradict itself in two registers.

What not to do is go back afterwards and edit the completed handoff to record the check you have since run, or to insert its own digest. Both change the bytes the digest you just published describes, so the receipt stops being true the moment you write it. If a later result matters enough to record, it belongs in your message to the user or in a new revision that supersedes this one - not retrofitted into a document that already claims to be final.

## Where things are stored

An externally selected destination - named by a managed runtime, a task brief, or the user -
governs where an artifact is actually written. The paths below are the defaults for when
nothing was selected, and the project may have adopted a different map, which replaces them
in the same sense:

- `docs/devforge/ideas/` - idea ledgers
- `docs/devforge/handoffs/` - handoffs
- `docs/devforge/changes/` - change requests

A default never overrides a selection, and a collision at a selected path is a condition to
report rather than grounds to write elsewhere - relocating leaves the checked path empty.

These are project paths. This skill's own bundled resources - the `assets/` templates and
the `references/` files - resolve against the installed `SKILL.md` directory instead, which
is usually neither inside the consuming project nor the current shell directory.

Never claim a file is saved until you have observed its path and bytes.
