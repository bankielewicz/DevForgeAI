But does it work reliably — across varied prompts, in edge cases, better than no skill at all? Running structured evaluations (evals) answers these questions and gives you a feedback loop for improving the skill systematically.\nL26: ##\nL27: \nL28: cite3†​ L29: \nL30: Designing test cases\nL31: \nL32: A test case has three parts:\nL33: \nL34:   * Prompt: a realistic user message — the kind of thing someone would actually type.\nL35:   * Expected output: a human-readable description of what success looks like.\nL36:   * Input files (optional): files the skill needs to work with.\nL37: Store test cases in `evals/evals.json` inside your skill directory:\nL38: evals/evals.json\nL39: \nL40:     `{\nL41:       \"skill_name\": \"csv-analyzer\",\nL42:       \"evals\": [\nL43:         {\nL44:           \"id\": 1,\nL45:           \"prompt\": \"I have a CSV of monthly sales data in data/sales_2025.csv. Can you find the top 3 months by revenue and make a bar chart?\",\nL46:           \"expected_output\": \"A bar chart image showing the top 3 months by revenue, with labeled axes and values.\",\nL47:           \"files\": [\"evals/files/sales_2025.csv\"]\nL48:         },\nL49:         {\nL50:           \"id\": 2,\nL51:           \"prompt\": \"there's a csv in my downloads called customers.csv, some rows have missing emails — can you clean it up and tell me how many were missing?\",\nL52:           \"expected_output\": \"A cleaned CSV with missing emails handled, plus a count of how many were missing.\",\nL53:           \"files\": [\"evals/files/customers.csv\"]\nL54:         }\nL55:       ]\nL56:     }\nL57:     `\nL58: Tips for writing good test prompts:\nL59:   * Start with 2-3 test cases. Don’t over-invest before you’ve seen your first round of results. You can expand the set later.\nL60:   * Vary the prompts. Use different phrasings, levels of detail, and formality. Some prompts should be casual (“hey can you clean up this csv”), others precise (“Parse the CSV at data/input.csv, drop rows where column B is null, and write the result to data/output.csv”).\nL61:   * Cover edge cases. Include at least one prompt that tests a boundary condition — a malformed input, an unusual request, or a case where the skill’s instructions might be ambiguous.\nL62:   * Use realistic context. Real users mention file paths, column names, and personal context. Prompts like “process this data” are too vague to test anything useful.\nL63: Don’t worry about defining specific pass/fail checks yet — just the prompts and expected outputs. You’ll add detailed checks (called assertions) after you see what the first run produces.\nL64: ##\nL65: \nL66: cite4†​ L67: \nL68: Running evals\nL69: \nL70: The core pattern is to run each test case twice: once with the skill and once without it (or with a previous version). This gives you a baseline to compare against.\nL71: ###\nL72: \nL73: cite5†​ L74: \nL75: Workspace structure\nL76: Organize eval results in a workspace directory alongside your skill directory. Each pass through the full eval loop gets its own `iteration-N/` directory. Within that, each test case gets an eval directory with `with_skill/` and `without_skill/` subdirectories:\nL77: \nL78:     `csv-analyzer/\nL79:     ├── SKILL.md\nL80:     └── evals/\nL81:         └── evals.json\nL82:     csv-analyzer-workspace/\nL83:     └── iteration-1/\nL84:         ├── eval-top-months-chart/\nL85:         │   ├── with_skill/\nL86:         │   │   ├── outputs/       # Files produced by the run\nL87:         │   │   ├── timing.json    # Tokens and duration\nL88:         │   │   └── grading.json   # Assertion results\nL89:         │   └── without_skill/\nL90:         │       ├── outputs/\nL91:         │       ├── timing.json\nL92:         │       └── grading.json\nL93:         ├── eval-clean-missing-emails/\nL94:         │   ├── with_skill/\nL95:         │   │   ├── outputs/\nL96:         │   │   ├── timing.json\nL97:         │   │   └── grading.json\nL98:         │   └── without_skill/\nL99:         │       ├── outputs/\nL100:         │       ├── timing.json\nL101:         │       └── grading.json\nL102:         └── benchmark.json         # Aggregated statistics\nL103:     `\nL104: The main file you author by hand is `evals/evals.json`. The other JSON files (`grading.json`, `timing.json`, `benchmark.json`) are produced during the eval process — by the agent, by scripts, or by you.\nL105: ###\nL106: \nL107: cite6†​ L108: \nL109: Spawning runs\nL110: \nL111: Each eval run should start with a clean context — no leftover state from previous runs or from the skill development process. This ensures the agent follows only what the `SKILL.md` tells it. In environments that support subagents (Claude Code, for example), this isolation comes naturally: each child task starts fresh. Without subagents, use a separate session for each run. For each run, provide:\nL112:   * The skill path (or no skill for the baseline)\nL113:   * The test prompt\nL114:   * Any input files\nL115:   * The output directory\nL116: Here’s an example of the instructions you’d give the agent for a single with-skill run:\nL117: \nL118:     `Execute this task:\nL119:     - Skill path: /path/to/csv-analyzer\nL120:     - Task: I have a CSV of monthly sales data in data/sales_2025.csv.\nL121:       Can you find the top 3 months by revenue and make a bar chart?\nL122:     - Input files: evals/files/sales_2025.csv\nL123:     - Save outputs to: csv-analyzer-workspace/iteration-1/eval-top-months-chart/with_skill/outputs/\nL124:     `\nL125: For the baseline, use the same prompt but without the skill path, saving to `without_skill/outputs/`. When improving an existing skill, use the previous version as your baseline. Snapshot it before editing (`cp -r <skill-path> <workspace>/skill-snapshot/`), point the baseline run at the snapshot, and save to `old_skill/outputs/` instead of `without_skill/`.\nL126: ###\nL127: \nL128: cite7†​ L129: \nL130: Capturing timing data\nL131: \nL132: Timing data lets you compare how much time and tokens the skill costs relative to the baseline — a skill that dramatically improves output quality but triples token usage is a different trade-off than one that’s both better and cheaper. When each run completes, record the token count and duration:\nL133: \nL134: timing.json\nL135: \nL136:     `{\nL137:       \"total_tokens\": 84852,\nL138:       \"duration_ms\": 23332\nL139:     }\nL140:     `\nL141: In Claude Code, when a subagent task finishes, the cite8†task completion notification†platform.claude.com includes `total_tokens` and `duration_ms`. Save these values immediately — they aren’t persisted anywhere else.\nL142: ##\nL143: \nL144: cite9†​ L145: \nL146: Writing assertions\nL147: \nL148: Assertions are verifiable statements about what the output should contain or achieve. Add them after you see your first round of outputs — you often don’t know what “good” looks like until the skill has run. Good assertions:\nL149: \nL150:   * `\"The output file is valid JSON\"` — programmatically verifiable.\nL151:   * `\"The bar chart has labeled axes\"` — specific and observable.\nL152:   * `\"The report includes at least 3 recommendations\"` — countable.\nL153: Weak assertions:\nL154:   * `\"The output is good\"` — too vague to grade.\nL155:   * `\"The output uses exactly the phrase 'Total Revenue: $X'\"` — too brittle; correct output with different wording would fail.\nL156: Not everything needs an assertion. Some qualities — writing style, visual design, whether the output “feels right” — are hard to decompose into pass/fail checks. These are better caught during cite10†human review . Reserve assertions for things that can be checked objectively. Add assertions to each test case in `evals/evals.json`:\nL157: evals/evals.json\nL158: \nL159:     `{\nL160:       \"skill_name\": \"csv-analyzer\",\nL161:       \"evals\": [\nL162:         {\nL163:           \"id\": 1,\nL164:           \"prompt\": \"I have a CSV of monthly sales data in data/sales_2025.csv. Can you find the top 3 months by revenue and make a bar chart?\",\nL165:           \"expected_output\": \"A bar chart image showing the top 3 months by revenue, with labeled axes and values.\",\nL166:           \"files\": [\"evals/files/sales_2025.csv\"],\nL167:           \"assertions\": [\nL168:             \"The output includes a bar chart image file\",\nL169:             \"The chart shows exactly 3 months\",\nL170:             \"Both axes are labeled\",\nL171:             \"The chart title or caption mentions revenue\"\nL172:           ]\nL173:         }\nL174:       ]\nL175:     }\nL176:     `\nL177: ##\nL178: \nL179: cite11†​ L180: \nL181: Grading outputs\nL182: Grading means evaluating each assertion against the actual outputs and recording PASS or FAIL with specific evidence. The evidence should quote or reference the output, not just state an opinion. The simplest approach is to give the outputs and assertions to an LLM and ask it to evaluate each one.\nL183: For assertions that can be checked by code (valid JSON, correct row count, file exists with expected dimensions), use a verification script — scripts are more reliable than LLM judgment for mechanical checks and reusable across iterations.\nL184: grading.json\nL185: \nL186:     `{\nL187:       \"assertion_results\": [\nL188:         {\nL189:           \"text\": \"The output includes a bar chart image file\",\nL190:           \"passed\": true,\nL191:           \"evidence\": \"Found chart.png (45KB) in outputs directory\"\nL192:         },\nL193:         {\nL194:           \"text\": \"The chart shows exactly 3 months\",\nL195:           \"passed\": true,\nL196:           \"evidence\": \"Chart displays bars for March, July, and November\"\nL197:         },\nL198:         {\nL199:           \"text\": \"Both axes are labeled\",\nL200:           \"passed\": false,\nL201:           \"evidence\": \"Y-axis is labeled 'Revenue ($)' but X-axis has no label\"\nL202:         },\nL203:         {\nL204:           \"text\": \"The chart title or caption mentions revenue\",\nL205:           \"passed\": true,\nL206:           \"evidence\": \"Chart title reads 'Top 3 Months by Revenue'\"\nL207:         }\nL208:       ],\nL209:       \"summary\": {\nL210:         \"passed\": 3,\nL211:         \"failed\": 1,\nL212:         \"total\": 4,\nL213:         \"pass_rate\": 0.75\nL214:       }\nL215:     }\nL216:     `\nL217: ###\nL218: \nL219: cite12†​ L220: \nL221: Grading principles\nL222:   * Require concrete evidence for a PASS. Don’t give the benefit of the doubt. If an assertion says “includes a summary” and the output has a section titled “Summary” with one vague sentence, that’s a FAIL — the label is there but the substance isn’t.\nL223:   * Review the assertions themselves, not just the results. While grading, notice when assertions are too easy (always pass regardless of skill quality), too hard (always fail even when the output is good), or unverifiable (can’t be checked from the output alone). Fix these for the next iteration.\nL224: For comparing two skill versions, try blind comparison: present both outputs to an LLM judge without revealing which came from which version. The judge scores holistic qualities — organization, formatting, usability, polish — on its own rubric, free from bias about which version “should” be better. This complements assertion grading: two outputs might both pass all assertions but differ significantly in overall quality.\nL225: ##\nL226: \nL227: cite13†​ L228: \nL229: Aggregating results\nL230: \nL231: Once every run in the iteration is graded, compute summary statistics per configuration and save them to `benchmark.json` alongside the eval directories (e.g., `csv-analyzer-workspace/iteration-1/benchmark.json`):\nL232: benchmark.json\nL233: \nL234:     `{\nL235:       \"run_summary\": {\nL236:         \"with_skill\": {\nL237:           \"pass_rate\": { \"mean\": 0.83, \"stddev\": 0.06 },\nL238:           \"time_seconds\": { \"mean\": 45.0, \"stddev\": 12.0 },\nL239:           \"tokens\": { \"mean\": 3800, \"stddev\": 400 }\nL240:         },\nL241:         \"without_skill\": {\nL242:           \"pass_rate\": { \"mean\": 0.33, \"stddev\": 0.10 },\nL243:           \"time_seconds\": { \"mean\": 32.0, \"stddev\": 8.0 },\nL244:           \"tokens\": { \"mean\": 2100, \"stddev\": 300 }\nL245:         },\nL246:         \"delta\": {\nL247:           \"pass_rate\": 0.50,\nL248:           \"time_seconds\": 13.0,\nL249:           \"tokens\": 1700\nL250:         }\nL251:       }\nL252:     }\nL253:     `\nL254: The `delta` tells you what the skill costs (more time, more tokens) and what it buys (higher pass rate). A skill that adds 13 seconds but improves pass rate by 50 percentage points is probably worth it. A skill that doubles token usage for a 2-point improvement might not be.\nL255: Standard deviation (`stddev`) is only meaningful with multiple runs per eval. In early iterations with just 2-3 test cases and single runs, focus on the raw pass counts and the delta — the statistical measures become useful as you expand the test set and run each eval multiple times.\nL256: ##\nL257: \nL258: cite14†​ L259: \nL260: Analyzing patterns\nL261: \nL262: Aggregate statistics can hide important patterns. After computing the benchmarks:\nL263:   * Remove or replace assertions that always pass in both configurations. These don’t tell you anything useful — the model handles them fine without the skill. They inflate the with-skill pass rate without reflecting actual skill value.\nL264:   * Investigate assertions that always fail in both configurations. Either the assertion is broken (asking for something the model can’t do), the test case is too hard, or the assertion is checking for the wrong thing. Fix these before the next iteration.\nL265:   * Study assertions that pass with the skill but fail without. This is where the skill is clearly adding value. Understand why — which instructions or scripts made the difference?\nL266:   * Tighten instructions when results are inconsistent across runs. If the same eval passes sometimes and fails others (reflected as high `stddev` in the benchmark), the eval may be flaky (sensitive to model randomness), or the skill’s instructions may be ambiguous enough that the model interprets them differently each time. Add examples or more specific guidance to reduce ambiguity.\nL267:   * Check time and token outliers. If one eval takes 3x longer than the others, read its execution transcript (the full log of what the model did during the run) to find the bottleneck.\nL268: ##\nL269: \nL270: cite10†​ L271: \nL272: Reviewing results with a human\nL273: Assertion grading and pattern analysis catch a lot, but they only check what you thought to write assertions for. A human reviewer brings a fresh perspective — catching issues you didn’t anticipate, noticing when the output is technically correct but misses the point, or spotting problems that are hard to express as pass/fail checks. For each test case, review the actual outputs alongside the grades.\nL274: Record specific feedback for each test case and save it in the workspace (e.g., as a `feedback.json` alongside the eval directories):\nL275: feedback.json\nL276: \nL277:     `{\nL278:       \"eval-top-months-chart\": \"The chart is missing axis labels and the months are in alphabetical order instead of chronological.\",\nL279:       \"eval-clean-missing-emails\": \"\"\nL280:     }\nL281:     `\nL282: \nL283: “The chart is missing axis labels” is actionable; “looks bad” is not. Empty feedback means the output looked fine — that test case passed your review. During the cite15†iteration step , focus your improvements on the test cases where you had specific complaints.\nL284: ##\nL285: \nL286: cite15†​ L287: \nL288: Iterating on the skill\nL289: \nL290: After grading and reviewing, you have three sources of signal:\nL291:   * Failed assertions point to specific gaps — a missing step, an unclear instruction, or a case the skill doesn’t handle.\nL292:   * Human feedback points to broader quality issues — the approach was wrong, the output was poorly structured, or the skill produced a technically correct but unhelpful result.\nL293:   * Execution transcripts reveal why things went wrong. If the agent ignored an instruction, the instruction may be ambiguous. If the agent spent time on unproductive steps, those instructions may need to be simplified or removed.\nL294: The most effective way to turn these signals into skill improvements is to give all three — along with the current `SKILL.md` — to an LLM and ask it to propose changes. The LLM can synthesize patterns across failed assertions, reviewer complaints, and transcript behavior that would be tedious to connect manually. When prompting the LLM, include these guidelines:\nL295:   * Generalize from feedback. The skill will be used across many different prompts, not just the test cases. Fixes should address underlying issues broadly rather than adding narrow patches for specific examples.\nL296:   * Keep the skill lean. Fewer, better instructions often outperform exhaustive rules. If transcripts show wasted work (unnecessary validation, unneeded intermediate outputs), remove those instructions. If pass rates plateau despite adding more rules, the skill may be over-constrained — try removing instructions and see if results hold or improve.\nL297:   * Explain the why. Reasoning-based instructions (“Do X because Y tends to cause Z”) work better than rigid directives (“ALWAYS do X, NEVER do Y”). Models follow instructions more reliably when they understand the purpose.\nL298:   * Bundle repeated work. If every test run independently wrote a similar helper script (a chart builder, a data parser), that’s a signal to bundle the script into the skill’s `scripts/` directory. See cite16†Using scripts for how to do this.\nL299: ###\nL300: \nL301: cite17†​ L302: \nL303: The loop\nL304: \nL305:   1. Give the eval signals and current `SKILL.md` to an LLM and ask it to propose improvements.\nL306:   2. Review and apply the changes.\nL307:   3. Rerun all test cases in a new `iteration-<N+1>/` directory.\nL308:   4. Grade and aggregate the new results.\nL309:   5. Review with a human. Repeat.\nL310: Stop when you’re satisfied with the results, feedback is consistently empty, or you’re no longer seeing meaningful improvement between iterations.\nL311: The cite18†`skill-creator`†github.com Skill automates much of this workflow — running evals, grading assertions, aggregating benchmarks, and presenting results for human review.\nL312: \nL313: cite19†Optimizing descriptions cite16†Using scripts \n"
