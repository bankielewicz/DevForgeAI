The result is vague, generic procedures (“handle errors appropriately,” “follow best practices for authentication”) rather than the specific API patterns, edge cases, and project conventions that make a skill valuable. Effective skills are grounded in real expertise. The key is feeding domain-specific context into the creation process.\nL51: ###\nL52: \nL53: cite4†​ L54: \nL55: Extract from a hands-on task\nL56: \nL57: Complete a real task in conversation with an agent, providing context, corrections, and preferences along the way. Then extract the reusable pattern into a skill. Pay attention to:\nL58:   * Steps that worked — the sequence of actions that led to success\nL59:   * Corrections you made — places where you steered the agent’s approach (e.g., “use library X instead of Y,” “check for edge case Z”)\nL60:   * Input/output formats — what the data looked like going in and coming out\nL61:   * Context you provided — project-specific facts, conventions, or constraints the agent didn’t already know\nL62: ###\nL63: \nL64: cite5†​ L65: \nL66: Synthesize from existing project artifacts\nL67: \nL68: When you have a body of existing knowledge, you can feed it into an LLM and ask it to synthesize a skill. A data-pipeline skill synthesized from your team’s actual incident reports and runbooks will outperform one synthesized from a generic “data engineering best practices” article, because it captures your schemas, failure modes, and recovery procedures. The key is project-specific material, not generic references. Good source material includes:\nL69:   * Internal documentation, runbooks, and style guides\nL70:   * API specifications, schemas, and configuration files\nL71:   * Code review comments and issue trackers (captures recurring concerns and reviewer expectations)\nL72:   * Version control history, especially patches and fixes (reveals patterns through what actually changed)\nL73:   * Real-world failure cases and their resolutions\nL74: ##\nL75: \nL76: cite6†​ L77: \nL78: Refine with real execution\nL79: \nL80: The first draft of a skill usually needs refinement. Run the skill against real tasks, then feed the results — all of them, not just failures — back into the creation process. Ask: what triggered false positives? What was missed? What could be cut? Even a single pass of execute-then-revise noticeably improves quality, and complex domains often benefit from several.\nL81: Read agent execution traces, not just final outputs. If the agent wastes time on unproductive steps, common causes include instructions that are too vague (the agent tries several approaches before finding one that works), instructions that don’t apply to the current task (the agent follows them anyway), or too many options presented without a clear default.\nL82: \nL83: For a more structured approach to iteration, including test cases, assertions, and grading, see cite24†Evaluating skill output quality .\nL84: ##\nL85: \nL86: cite7†​ L87: \nL88: Spending context wisely\nL89: \nL90: Once a skill activates, its full `SKILL.md` body loads into the agent’s context window alongside conversation history, system context, and other active skills. Every token in your skill competes for the agent’s attention with everything else in that window.\nL91: ###\nL92: \nL93: cite8†​ L94: \nL95: Add what the agent lacks, omit what it knows\nL96: Focus on what the agent wouldn’t know without your skill: project-specific conventions, domain-specific procedures, non-obvious edge cases, and the particular tools or APIs to use. You don’t need to explain what a PDF is, how HTTP works, or what a database migration does.\nL97: \nL98:     `<!-- Too verbose — the agent already knows what PDFs are -->\nL99:     ## Extract PDF text\nL100: \nL101:     PDF (Portable Document Format) files are a common file format that contains\nL102:     text, images, and other content. To extract text from a PDF, you'll need to\nL103:     use a library. pdfplumber is recommended because it handles most cases well.\nL104: \nL105:     <!-- Better — jumps straight to what the agent wouldn't know on its own -->\nL106:     ## Extract PDF text\nL107: \nL108:     Use pdfplumber for text extraction. For scanned documents, fall back to\nL109:     pdf2image with pytesseract.\nL110: \nL111:     ```python\nL112:     import pdfplumber\nL113: \nL114:     with pdfplumber.open(\"file.pdf\") as pdf:\nL115:         text = pdf.pages[0].extract_text()\nL116:     ```\nL117:     `\nL118: Ask yourself about each piece of content: “Would the agent get this wrong without this instruction?” If the answer is no, cut it. If you’re unsure, test it. And if the agent already handles the entire task well without the skill, the skill may not be adding value. See cite24†Evaluating skill output quality for how to test this systematically.\nL119: ###\nL120: \nL121: cite9†​ L122: \nL123: Design coherent units\nL124: Deciding what a skill should cover is like deciding what a function should do: you want it to encapsulate a coherent unit of work that composes well with other skills. Skills scoped too narrowly force multiple skills to load for a single task, risking overhead and conflicting instructions. Skills scoped too broadly become hard to activate precisely.\nL125: A skill for querying a database and formatting the results may be one coherent unit, while a skill that also covers database administration is probably trying to do too much.\nL126: ###\nL127: \nL128: cite10†​ L129: \nL130: Aim for moderate detail\nL131: \nL132: Overly comprehensive skills can hurt more than they help — the agent struggles to extract what’s relevant and may pursue unproductive paths triggered by instructions that don’t apply to the current task. Concise, stepwise guidance with a working example tends to outperform exhaustive documentation. When you find yourself covering every edge case, consider whether most are better handled by the agent’s own judgment.\nL133: ###\nL134: \nL135: cite11†​ L136: \nL137: Structure large skills with progressive disclosure\nL138: The cite25†specification recommends keeping `SKILL.md` under 500 lines and 5,000 tokens — just the core instructions the agent needs on every run. When a skill legitimately needs more content, move detailed reference material to separate files in `references/` or similar directories. The key is telling the agent when to load each file.\nL139: “Read `references/api-errors.md` if the API returns a non-200 status code” is more useful than a generic “see references/ for details.” This lets the agent load context on demand rather than up front, which is how cite25†progressive disclosure is designed to work.\nL140: ##\nL141: \nL142: cite12†​ L143: \nL144: Calibrating control\nL145: \nL146: Not every part of a skill needs the same level of prescriptiveness. Match the specificity of your instructions to the fragility of the task.\nL147: ###\nL148: \nL149: cite13†​ L150: \nL151: Match specificity to fragility\nL152: Give the agent freedom when multiple approaches are valid and the task tolerates variation. For flexible instructions, explaining why can be more effective than rigid directives — an agent that understands the purpose behind an instruction makes better context-dependent decisions. A code review skill can describe what to look for without prescribing exact steps:\nL153: \nL154:     `## Code review process\nL155: \nL156:     1. Check all database queries for SQL injection (use parameterized queries)\nL157:     2. Verify authentication checks on every endpoint\nL158:     3. Look for race conditions in concurrent code paths\nL159:     4. Confirm error messages don't leak internal details\nL160:     `\nL161: Be prescriptive when operations are fragile, consistency matters, or a specific sequence must be followed:\nL162: \nL163:     `## Database migration\nL164: \nL165:     Run exactly this sequence:\nL166: \nL167:     ```bash\nL168:     python scripts/migrate.py --verify --backup\nL169:     ```\nL170: \nL171:     Do not modify the command or add additional flags.\nL172:     `\nL173: \nL174: Most skills have a mix. Calibrate each part independently.\nL175: ###\nL176: \nL177: cite14†​ L178: \nL179: Provide defaults, not menus\nL180: \nL181: When multiple tools or approaches could work, pick a default and mention alternatives briefly rather than presenting them as equal options.\nL182: \nL183:     `<!-- Too many options -->\nL184:     You can use pypdf, pdfplumber, PyMuPDF, or pdf2image...\nL185: \nL186:     <!-- Clear default with escape hatch -->\nL187:     Use pdfplumber for text extraction:\nL188: \nL189:     ```python\nL190:     import pdfplumber\nL191:     ```\nL192: \nL193:     For scanned PDFs requiring OCR, use pdf2image with pytesseract instead.\nL194:     `\nL195: ###\nL196: \nL197: cite15†​ L198: \nL199: Favor procedures over declarations\nL200: A skill should teach the agent how to approach a class of problems, not what to produce for a specific instance. Compare:\nL201: \nL202:     `<!-- Specific answer — only useful for this exact task -->\nL203:     Join the `orders` table to `customers` on `customer_id`, filter where\nL204:     `region = 'EMEA'`, and sum the `amount` column.\nL205: \nL206:     <!-- Reusable method — works for any analytical query -->\nL207:     1. Read the schema from `references/schema.yaml` to find relevant tables\nL208:     2. Join tables using the `_id` foreign key convention\nL209:     3. Apply any filters from the user's request as WHERE clauses\nL210:     4. Aggregate numeric columns as needed and format as a markdown table\nL211:     `\nL212: This doesn’t mean skills can’t include specific details — output format templates (see cite18†Templates for output format ), constraints like “never output PII,” and tool-specific instructions are all valuable. The point is that the approach should generalize even when individual details are specific.\nL213: ##\nL214: \nL215: cite16†​ L216: \nL217: Patterns for effective instructions\nL218: \nL219: These are reusable techniques for structuring skill content. Not every skill needs all of them — use the ones that fit your task.\nL220: ###\nL221: \nL222: cite17†​ L223: \nL224: Gotchas sections\nL225: The highest-value content in many skills is a list of gotchas — environment-specific facts that defy reasonable assumptions. These aren’t general advice (“handle errors appropriately”) but concrete corrections to mistakes the agent will make without being told otherwise:\nL226: \nL227:     `## Gotchas\nL228: \nL229:     - The `users` table uses soft deletes. Queries must include\nL230:       `WHERE deleted_at IS NULL` or results will include deactivated accounts.\nL231:     - The user ID is `user_id` in the database, `uid` in the auth service,\nL232:       and `accountId` in the billing API. All three refer to the same value.\nL233:     - The `/health` endpoint returns 200 as long as the web server is running,\nL234:       even if the database connection is down. Use `/ready` to check full\nL235:       service health.\nL236:     `\nL237: Keep gotchas in `SKILL.md` where the agent reads them before encountering the situation. A separate reference file works if you tell the agent when to load it, but for non-obvious issues, the agent may not recognize the trigger.\nL238: \nL239: When an agent makes a mistake you have to correct, add the correction to the gotchas section. This is one of the most direct ways to improve a skill iteratively (see cite6†Refine with real execution ).\nL240: ###\nL241: \nL242: cite18†​ L243: \nL244: Templates for output format\nL245: When you need the agent to produce output in a specific format, provide a template. This is more reliable than describing the format in prose, because agents pattern-match well against concrete structures. Short templates can live inline in `SKILL.md`; for longer templates, or templates only needed in certain cases, store them in `assets/` and reference them from `SKILL.md` so they only load when needed.\nL246: \nL247:     `## Report structure\nL248:     Use this template, adapting sections as needed for the specific analysis:\nL249: \nL250:     ```markdown\nL251:     # [Analysis Title]\nL252: \nL253:     ## Executive summary\nL254:     [One-paragraph overview of key findings]\nL255: \nL256:     ## Key findings\nL257:     - Finding 1 with supporting data\nL258:     - Finding 2 with supporting data\nL259: \nL260:     ## Recommendations\nL261:     1. Specific actionable recommendation\nL262:     2. Specific actionable recommendation\nL263:     ```\nL264:     `\nL265: ###\nL266: \nL267: cite19†​ L268: \nL269: Checklists for multi-step workflows\nL270: An explicit checklist helps the agent track progress and avoid skipping steps, especially when steps have dependencies or validation gates.\nL271: \nL272:     `## Form processing workflow\nL273: \nL274:     Progress:\nL275:     - [ ] Step 1: Analyze the form (run `scripts/analyze_form.py`)\nL276:     - [ ] Step 2: Create field mapping (edit `fields.json`)\nL277:     - [ ] Step 3: Validate mapping (run `scripts/validate_fields.py`)\nL278:     - [ ] Step 4: Fill the form (run `scripts/fill_form.py`)\nL279:     - [ ] Step 5: Verify output (run `scripts/verify_output.py`)\nL280:     `\nL281: ###\nL282: \nL283: cite20†​ L284: \nL285: Validation loops\nL286: Instruct the agent to validate its own work before moving on. The pattern is: do the work, run a validator (a script, a reference checklist, or a self-check), fix any issues, and repeat until validation passes.\nL287: \nL288:     `## Editing workflow\nL289: \nL290:     1. Make your edits\nL291:     2. Run validation: `python scripts/validate.py output/`\nL292:     3. If validation fails:\nL293:        - Review the error message\nL294:        - Fix the issues\nL295:        - Run validation again\nL296:     4. Only proceed when validation passes\nL297:     `\nL298: A reference document can also serve as the “validator” — instruct the agent to check its work against the reference before finalizing.\nL299: ###\nL300: \nL301: cite21†​ L302: \nL303: Plan-validate-execute\nL304: For batch or destructive operations, have the agent create an intermediate plan in a structured format, validate it against a source of truth, and only then execute.\nL305: \nL306:     `## PDF form filling\nL307: \nL308:     1. Extract form fields: `python scripts/analyze_form.py input.pdf` → `form_fields.json`\nL309:        (lists every field name, type, and whether it's required)\nL310:     2. Create `field_values.json` mapping each field name to its intended value\nL311:     3. Validate: `python scripts/validate_fields.py form_fields.json field_values.json`\nL312:        (checks that every field name exists in the form, types are compatible, and\nL313:        required fields aren't missing)\nL314:     4. If validation fails, revise `field_values.json` and re-validate\nL315:     5. Fill the form: `python scripts/fill_form.py input.pdf field_values.json output.pdf`\nL316:     `\nL317: The key ingredient is step 3: a validation script that checks the plan (`field_values.json`) against the source of truth (`form_fields.json`). Errors like “Field ‘signature_date’ not found — available fields: customer_name, order_total, signature_date_signed” give the agent enough information to self-correct.\nL318: ###\nL319: \nL320: cite22†​ L321: \nL322: Bundling reusable scripts\nL323: \nL324: When cite24†iterating on a skill , compare the agent’s execution traces across test cases. If you notice the agent independently reinventing the same logic each run — building charts, parsing a specific format, validating output — that’s a signal to write a tested script once and bundle it in `scripts/`.
