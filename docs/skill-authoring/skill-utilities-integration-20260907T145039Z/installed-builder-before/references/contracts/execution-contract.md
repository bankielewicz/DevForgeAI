# Packaged execution and authority contract

Operational derivation of DevForgeAI docs/mvp/execution-contract.md, draft revision 2, 2026-09-05; exact selected bytes are identified in ../derivation.json. These are requirements, not a claim that a registry, outbox adapter, native launcher or hooks are implemented.

## Authority and assignment

Use normal subscribed Codex sessions and supported deterministic helpers. Human-operated transitions are valid. Native installation, discovery, activation, resource loading and output must each be demonstrated for the stated provider. Do not invent slash commands, DevForge commands or a callable skill for a draft capability.

A writing assignment names the actual owner, task, provider, permitted source paths, evaluation output area, protected paths, runtime configuration and integration owner. Git work also records the repository/common-directory identity, worktree, branch/detached state and real base commit. Missing metadata does not prove exclusive ownership.

Concurrent Git writing sessions require separately assigned worktrees and unique branches or recorded detached state. Worktrees share metadata and do not isolate credentials, client state, services, policy or acceptance. A greenfield single-writer bootstrap may record actual user scope and missing Git facts; never fabricate a base or commit user work automatically merely to fill a template.

Observe collision/assignment evidence before dependent writes. An existing writer conflict blocks those writes while permitted reporting can continue. A worker-authored session ID cannot establish a lease or override another assignment. Protect shared Git/policy as required; report a denied operation instead of relaxing protection to make it succeed.

## Runtime and evidence

Identify actual installed skills and effective environment before testing. Candidate/baseline and each retry have separate disposable consuming projects, writable outputs and history/memory state. Record visible instructions/skills/plugins/tools, source visibility and actual tool assistance. A new chat or directory does not demonstrate clean isolation.

Test required filesystem and process boundaries before model execution. Keep credential/global client state outside evidence and assigned writes. Authentication uses the operator's explicit arrangement. Missing boundary or runtime support yields COULD_NOT_RUN for dependent claims; no unconfined fallback. Terminate only processes whose identities and ownership match the run.

The operator may persist reports manually in the permitted store and read them back. There is no assumed general outbox service. Report actual errors and recovery owner instead of claiming files were saved.

## Hooks and external acceptance

Hooks can support context and early feedback, but do not own acceptance. Before any hook-dependent claim, verify the actual client version, supported event/tool matching, trust, disabled/skipped behavior, timeouts/errors and observed denial. Do not treat a failed/skipped hook as completion.

The paired builder authors hook proposals only. It does not install, activate or execute hooks. The proposed validator receipt gates cannot alone guarantee native event coverage or semantic completion. External authority independently examines actual candidate/evidence.

Do not modify sibling DevForge policy, runner, shared contracts or gate definitions to make a candidate pass. Route contract defects to the owning integration task. API-backed CI, protected-branch changes, hosted checks, merge and deployment are outside this local subscription evaluation unless separately assigned and observed.

## Handoff and re-evaluation

Freeze the candidate and preserve receipts before another owner evaluates it. Integration, rebase, conflict resolution or changed governing context creates a new relevant identity requiring affected checks. Passing task-branch evidence does not certify a combined candidate.

Completion does not authorize deleting a worktree, global state, old attempts or another session's work. Record custody, remaining tasks, actual gate state and next owner. A proposed continuation, discovered sibling and actually invoked sibling are separate facts.
