# PRD-002 — DevForgeAI CLI

## 1. Summary

The DevForgeAI CLI is an open-source terminal coding agent that runs on a user's Codex or Grok
sign-in or on a local model. It enforces guardrails in the harness itself and runs the DevForgeAI
SDLC planning chain as a workflow enforced in code. Every session is journaled so it can be
replayed and audited. The Prototype, due in about a month, proves this deterministic core with
Bryan and 5 to 10 outside users.

## 2. Problem and opportunity

Developers who put rules on an AI coding agent can't rely on them. Hooks, instructions and
permission rules in today's provider CLIs can be ignored by the model, switched off, or fail open,
and a shell subprocess can write around them (BRN-001#PRB-01). The same weakness affects
spec-driven work: SDLC steps that live in prompts and plugins can be skipped, so planning quality
varies from run to run (BRN-001#PRB-03). When something goes wrong, nobody can reproduce or audit
the session, because the same request takes different steps and leaves no replayable record
(BRN-001#PRB-05).

Developers also pay for the tool they use. Each subscription ties them to its vendor's CLI, so
moving between Codex, Grok, Claude or a local model means switching tools, configuration and habits
(BRN-001#PRB-02). Each CLI also has strengths the others lack (BRN-001#PRB-04). Local models call
tools less reliably and have smaller context windows, so agent loops built for frontier models break
on them (BRN-001#PRB-06). Open-source users can't add their own guardrails or skills without forking
the tool (BRN-001#PRB-07).

The opportunity is one harness that owns enforcement and the workflow itself. It would combine
the Claude Code and Codex CLI features developers rely on and let them choose the model by cost or
strength, while giving DevForgeAI a runtime of its own instead of a plugin inside someone else's CLI.

## 3. Users and personas

| Persona | Job to be done | Current workaround | Pain |
|---|---|---|---|
| Solo developer with several subscriptions | Use whichever model is cheapest or strongest for the task | Switch between Claude Code, Codex CLI and Grok CLI | Duplicate configuration, lost context, different habits per tool |
| Spec-driven developer | Run the planning chain with gates that actually hold | DevForgeAI skills as a plugin inside a provider CLI | The model can skip steps; hooks fail open |
| Reviewer or auditor | Know exactly what an agent did and repeat it | Read transcripts by hand | No replay; runs differ |
| Local-model user | Run the same workflow offline or for free | Ad-hoc scripts around Ollama or LM Studio | Tool calling breaks; loops stall |
| Open-source adopter | Add team-specific rules and skills | Fork or patch the tool | No extension point for guardrails |

The Prototype's users are Bryan first, then 5 to 10 outside developers from these personas.

## 4. Goals and non-goals

**Goals**
- Guardrails hold under every supported provider: no action inside a session can bypass or switch
  them off.
- SDLC phases advance only through gates enforced in code, and approvals and confirmed decisions come
  only from a human.
- Every session can be audited and replayed exactly, without calling a model.
- Developers move between subscription sign-ins and local models without changing tools or
  configuration.
- Users and teams extend the CLI with their own guardrails and skills without forking it.

**Non-goals** (explicitly out of scope)
- Per-model capability profiles that adapt tool use to weaker models (parked in the brainstorm until
  local-model tool calling is measured).
- Reading other CLIs' configuration files (CLAUDE.md, skills folders, MCP server configuration)
  beyond the AGENTS.md support that comes with the fork (parked in the brainstorm as polish after
  the core).
- Shipping local models first and adding sign-in providers later (parked in the brainstorm as a
  fallback order; not needed while the Codex sign-in is allowed).
- Claude subscription sign-in (parked in the brainstorm until Anthropic's terms allow third-party
  use).
- Running the existing vendor CLIs headless under an external sequencer instead of building a CLI
  (rejected in the brainstorm: it keeps the enforcement gap).
- An IDE extension or a GUI: the product is terminal-only.
- A hosted service: the project runs no cloud service, accounts or servers; the CLI runs on the
  user's machine.

## 8. User experience

A terminal-only CLI with no IDE extension or GUI. Users work in an interactive session, choose an
approval mode, or run headless in exec mode for scripts and CI (PRD-002#FR-002). SDLC phases run as
gated steps in which the model proposes, the CLI validates, and the user records every approval and
confirmed decision (PRD-002#FR-005). A new user completes a first session in under 10 minutes
(PRD-002#NFR-016).

## 9. Constraints and dependencies

- **Build base.** A hard fork of the Codex CLI at one stable release, in Rust (PRD-002#NFR-001), which brings
  its sandbox, approval modes, AGENTS.md support and exec mode. The upstream `main` branch changes
  quickly (3,602 commits and 279 releases from 2026-06-28 to 2026-09-28), and OpenAI accepts no
  outside pull requests, so upstream fixes are taken selectively (PRD-002#NFR-015).
- **Licence and platforms.** Apache-2.0 with the Codex NOTICE file (PRD-002#NFR-002); Linux and macOS, with
  Windows through WSL (PRD-002#NFR-003); local models on one 16–24 GB consumer GPU (PRD-002#NFR-004).
- **Provider terms.** The Codex sign-in is allowed for third-party tools today, with no terms clause
  guaranteeing it (PRD-002#ASM-01). The Grok sign-in is unconfirmed (PRD-002#ASM-02). The Claude subscription sign-in
  is not allowed (PRD-002#ASM-08). See PRD-002#NFR-014.
- **Model serving.** The fork speaks only the Responses API. Ollama (0.13.4 or newer) and LM Studio
  serve `/v1/responses`; Unsloth serves a non-stateful `/v1/responses` with tool calling.
- **DevForgeAI.** The built-in SDLC skills and their eval suites come from the DevForgeAI plugin. The
  workflow order follows ADR-002, and the skills keep the policy contract of ADR-003.
- **Timeline.** A first Prototype in about a month.

## 11. Release and rollout

**Prototype** (about a month): the current-release requirements. Bryan uses it first; then 5 to 10
outside developers try it, which also validates PRD-002#ASM-06. The Prototype tests PRD-002#ASM-03 to PRD-002#ASM-06, and
the code is kept and built upon if those assumptions hold. Its metrics targets (PRD-002#SM-01 to PRD-002#SM-04) must
hold at the Prototype release; PRD-002#SM-05 is measured over the 3 months after it. PRD-002#FR-011 (Claude through
an API key) is in the backlog for a later release.
