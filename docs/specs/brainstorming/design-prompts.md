# Brainstorm skill: prompts for Claude Design

**Status:** prompts for mock-ups, written 2026-11-18 by claude-code on the model Fable 5.2 (session
fa59a935-ed2e-4502-b6c4-93bb6d847546) at Bryan's request ("generate an ai prompt for various screens to be
generated by claude design ... the look and feel of the claude mod for brainstorm (if one is created) along with
the 'next steps'/handoff at the end of the workflow"). They specify no behaviour and no mod. Whether a brainstorm
pane is built is Bryan's decision; a build would need its own spec.

P1 to P5 are recorded as they were sent: Bryan ran them in Claude Design the same day, and the mock-ups and his
chosen directions are in [design/](design/README.md). P6 to P10 are the next prompts: each carries one chosen
direction across the states its first prompt named.

## Workflow steps these screens show

| Step (SKILL.md's line) | Screen that shows it | Prompt |
|---|---|---|
| 1. Intake: topic, existing BRNs, clarifying questions | The pane's header (topic, project kind) and its first step row | P1, P5 |
| 2. Select a framework | The pane's framework line | P1 |
| 3. Diverge: problems, ideas, assumptions | The pane's counts and the newest items | P1 |
| 4. Evaluate with the framework | The pane's scored ideas | P1, P6 |
| 5. Propose dispositions and ask the user to confirm | The confirmation screen, with the assumption ranking and the first release cut made at this step | P2, P7 |
| 6. Write the BRN, 7. Validate the BRN | The pane's last two step rows and the validator's result | P1, P5 |
| 8. Report and hand off | The hand-off screen | P3 |
| every step | The two-row band above the prompt and the status line | P4 |

## How to use them

- Paste one prompt at a time into Claude Design, as the first message of a new canvas. Each is complete alone.
- Each follows the six-part brief of the ui skill (`src/claude/DevForgeAI/skills/ui/references/briefs.md`): lead
  line, context, content, must-haves, style, closing line. Each asks for three directions of one key screen; pick
  one, then ask Claude Design to carry it across that prompt's other screens and states.
- The content is one worked example, the dental-clinic brainstorm of the skill's own examples, in the shapes of
  [README.md](README.md) §4. Replace it with a real brainstorm's content when one exists.
- The surface is a terminal. What a Claude Code mod can draw there is recorded in
  `docs/specs/devforgeai-claude-mods.md` §4 and `docs/specs/devforgeai-progress-ui.md` §6: a pane beside the
  transcript (about 58 columns when docked, any width when opened by a command), a band of a few rows above the
  prompt, one status-line entry, and toasts. A button draws as `[ label ]`. The prompts state these as
  constraints so the mock-ups can be built.
- Style is by reference, never by colour values: where a prompt says "the default design system", name yours as
  Claude Design lists it, or leave the words "propose one".

## P1. The brainstorm pane during a run

```text
The Brainstorm pane of DevForgeAI, a spec-driven planning plugin for Claude Code, for a product owner who is running a brainstorm in the terminal and wants to see where the session stands without scrolling the conversation.

Context: The owner types /devforgeai:brainstorm and works through eight steps with Claude: intake, choosing a framework, diverging into problems, ideas and assumptions, evaluating, confirming decisions, writing the document, validating it, and handing off to the PRD step. The conversation scrolls away. The one job of this pane: show the step the session is on and what has been captured so far, so the owner always knows what is decided and what is still only proposed.

Content (real data from one session; use it as given):
- Topic: "Cut appointment no-shows at our dental clinic". Project kind: greenfield. Document: BRN-001, status draft.
- Framework: diverge-converge, chosen because "the options are still wide open".
- The eight steps, in order, with their state: 1. Intake (done), 2. Select a framework (done), 3. Diverge (done), 4. Evaluate with the framework (in progress), 5. Propose dispositions and ask the user to confirm (not started), 6. Write the BRN (not started), 7. Validate the BRN (not started), 8. Report and hand off (not started).
- Captured so far: 3 problems, 10 ideas (2 in the owner's own words), 4 assumptions.
- Problems: PRB-01 "Patients forget appointments booked weeks ahead" (severity high); PRB-02 "A missed visit leaves an empty chair the clinic can't refill" (high); PRB-03 "Rescheduling needs a phone call during work hours" (medium).
- Ideas with scores so far: IDEA-01 "Text a reminder two days before, with a one-tap reschedule link" value high, effort low, risk low, score 4; IDEA-04 "Take a deposit at booking" value high, effort medium, risk high, score 1; IDEA-06 "Overbook the busiest hours" value medium, effort low, risk high, score 0. Seven ideas are not scored yet.
- Riskiest assumption: ASM-01 "We believe that patients read texts from the clinic", confidence low.
- Every idea's disposition is "open": nothing is decided until step 5.
- States to show after the key screen: the pane at step 1 with nothing captured yet; the pane at step 7 when the validator reports "line 42: unknown field in ideas"; the same run for a brownfield project, whose header reads "Project kind: brownfield" and lists "PRD-001 v3 read, 6 requirements already covered".
Key screen: the pane at step 4, as described above.

Must-haves:
- A terminal surface: a monospace cell grid 58 columns wide and 40 rows high, drawn only with text, box-drawing and block characters, 24-bit colour. No images, no proportional type.
- It must read at a glance which step is current, which are done and which are not started.
- "Proposed" and "decided" must never look alike: an open disposition is visibly different from a confirmed one.
- Keyboard-driven: any action is a labelled button drawn as [ label ].

Style: the default design system, or propose one. It sits beside DevForgeAI's progress pane and must look like the same product.

Give me 3 distinctly different directions of the key screen first, with a one-line tradeoff under each.
```

## P2. Confirming decisions (step 5)

```text
The Confirm decisions screen of DevForgeAI's brainstorm, a spec-driven planning plugin for Claude Code, for a product owner who must accept or change what the AI proposes before anything is written as decided.

Context: At step 5 of a brainstorm, Claude proposes what to do with each idea (promote, park or reject) and which promoted ideas form the first release. Only the owner's answer makes any of it a decision; whatever the owner doesn't confirm stays open. The one job of this screen: let the owner see every proposal with its reason and confirm, change or leave it open, in one pass, without mistaking a proposal for a decision.

Content (real data from one session; use it as given):
- Document BRN-001, "Cut appointment no-shows at our dental clinic", framework diverge-converge, 10 ideas.
- Proposed dispositions, each with its reason: IDEA-01 "Text a reminder two days before, with a one-tap reschedule link" promote, "highest score, cheap to try"; IDEA-02 "Let patients reschedule online" promote, "removes the phone call in PRB-03"; IDEA-04 "Take a deposit at booking" park, "needs a legal check first"; IDEA-06 "Overbook the busiest hours" reject, "harms patients who arrive on time"; six more ideas proposed as park.
- Question 1: "Confirm these dispositions?" with the answers "Accept all as proposed" and "Leave them open"; changes are typed.
- Question 2: "Has the brainstorm converged?" with "Converged" and "Not yet".
- Question 3: "Confirm the first release cut?" with "Accept as proposed" and "Leave it proposed". The proposed cut: IDEA-01 yes, "tests ASM-01, the riskiest assumption, at the lowest effort"; IDEA-02 no, "depends on IDEA-01's result".
- For a brownfield project only, question 4: "Confirm these assumption updates?" with "Accept all as proposed" and "Leave them open". The proposal: ASM-02 of BRN-001, "We believe that patients read texts from the clinic", from open to validated, because "the pilot's reminder texts were opened by 8 of 10 patients".
- States to show after the key screen: the owner has typed a change ("park IDEA-02"); the owner chose "Leave them open", after which every idea stays open and the document stays a draft; the brownfield variant with question 4.
Key screen: question 1 with the proposals table and its reasons visible.

Must-haves:
- A terminal surface: a monospace cell grid 100 columns wide and 36 rows high, drawn only with text, box-drawing and block characters, 24-bit colour.
- The proposals and their reasons are visible while the owner answers; nothing the owner needs is hidden behind the question.
- The recommended answer is marked, and the answer that keeps everything open is always present.
- Keyboard-driven: answers are chosen by number or arrow keys; typed changes are possible.

Style: the default design system, or propose one. It must look like the same product as the Brainstorm pane.

Give me 3 distinctly different directions of the key screen first, with a one-line tradeoff under each.
```

## P3. The hand-off at the end of the workflow (step 8)

```text
The Hand-off screen of DevForgeAI's brainstorm, a spec-driven planning plugin for Claude Code, for a product owner who has just finished a brainstorm and needs to know what was written and what to do next.

Context: A brainstorm ends with one document, BRN-001, and one next step: turning it into a product requirements document with /devforgeai:prd. Owners lose the thread here: the result is buried in a long reply, and what is still open is easy to miss. The one job of this screen: state what was written, what is decided, what is still open, and the single next step, so the owner can continue in one keystroke.

Content (real data from one session; use it as given):
- "BRN-001 written to docs/specs/brainstorm/BRN-001.md (framework: diverge-converge)".
- "Project kind: greenfield".
- "Problems: 3 · Ideas: 10 · Assumptions: 4".
- "Promoted: IDEA-01, IDEA-02". "First release: IDEA-01".
- "Open questions: current no-show rate (PRB-01's evidence); ASM-01 not yet tested, cheapest test: ask ten patients whether they read texts from the clinic".
- The validator's result: "OK: docs/specs/brainstorm/BRN-001.md".
- The next step, last on the screen: "Next step: run /devforgeai:prd BRN-001 to turn this brainstorm into a PRD."
- Other things the owner may do, lesser than the next step: open the document; continue the brainstorm later; test the riskiest assumption first.
- States to show after the key screen: nothing was confirmed ("Promoted: none confirmed yet (proposals are in section 6)", the document is a draft, and the next step is to confirm the proposals, not the PRD); the validator still reports problems after three attempts (the document is a draft and the problems are listed with their line numbers); a brownfield run ("Project kind: brownfield", "Already covered by PRD-001: 2 suggestions", "Assumptions updated: ASM-02 of BRN-001 validated").
Key screen: the converged, validated brainstorm with its next step.

Must-haves:
- A terminal surface: a monospace cell grid 100 columns wide and 30 rows high, drawn only with text, box-drawing and block characters, 24-bit colour.
- The next step is the last thing on the screen and the most prominent action; it can be taken with one key, drawn as [ label ].
- What is decided and what is still open are separated and can't be confused.
- The command is shown exactly as typed: /devforgeai:prd BRN-001, with the document's ID and never a file path.

Style: the default design system, or propose one. It must look like the same product as the Brainstorm pane.

Give me 3 distinctly different directions of the key screen first, with a one-line tradeoff under each.
```

## P5. The start of a run: greenfield or brownfield

```text
The Intake screen of DevForgeAI's brainstorm, a spec-driven planning plugin for Claude Code, for a product owner starting a brainstorm either for a new product or for one that already exists.

Context: A brainstorm for a new product starts from a blank page; one for an existing product starts from what is already written and already learned. The skill decides which it is, says what it read, and asks a few questions before any idea is generated. The one job of this screen: show the owner what the session starts from, so a wrong starting point is caught before the brainstorm builds on it.

Content (real data from two sessions; use it as given):
- Greenfield session: topic "Cut appointment no-shows at our dental clinic"; "Project kind: greenfield" because the project holds no PRD; questions asked: "What triggered this?", "Who is affected, and what do they do today instead?", "What constraints apply?"; sources recorded so far: none.
- Brownfield session: topic "Improve online booking for returning patients"; "Project kind: brownfield" because the project holds PRD-001; read: "PRD-001 v3: online booking for returning patients (FR-001 to FR-006)" and "BRN-001 v2: 2 promoted, 1 parked, 1 rejected, 1 assumption still open"; sources recorded: "document: docs/specs/prd/PRD-001.md v3", "data: booking funnel export, October 2026"; offered to the owner: reconsider the parked idea "Take a deposit at booking"; not re-proposed: the rejected idea "Overbook the busiest hours".
- In both: the choice between extending BRN-001 and starting a new document, when a brainstorm on a similar topic exists.
- States to show after the key screen: the kind can't be decided and the owner is asked; a document that can't be read is skipped and named ("PRD-002 could not be read and was skipped").
Key screen: the brownfield session, showing what was read.

Must-haves:
- A terminal surface: a monospace cell grid 100 columns wide and 32 rows high, drawn only with text, box-drawing and block characters, 24-bit colour.
- What the skill read and what it concluded are both visible, with the conclusion ("brownfield") easy to correct.
- Nothing is shown as an idea yet: this screen is before ideas.

Style: the default design system, or propose one. It must look like the same product as the Brainstorm pane.

Give me 3 distinctly different directions of the key screen first, with a one-line tradeoff under each.
```

## Notes for whoever builds from the mock-ups

- The data on every screen comes from the BRN and the run's work file; no screen needs a field that
  [README.md](README.md) R1 forbids.
- The question forms of P2 are AskUserQuestion dialogs today; a mod can redraw a dialog but the options and their
  order are the skill's (README §4, C-10).
- A pane, a band and a status entry for a tracked run already exist in the progress tracker (SPEC-013). A
  brainstorm pane would be a second pane of the same mod or a new mod; that choice, and whether to build it, is
  open.
