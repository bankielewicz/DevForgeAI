# ADR-010 — Decision-ownership settings: one policy key, decisions.owner, that can only tighten what an agent may decide and log

## Context and problem statement

ADR-009 D4 has every expert answer name its decision owner and the rule it applies. That rule needs a home.

The framework already fixes most of it:
- **ADR-003:**
  - A1 gives "decision ownership" to the fixed core workflow;
  - A2 makes "the AI never decides scope" a framework requirement;
  - A4 lets nothing override a framework requirement.
- **FR-003** leaves decisions to people.
- **ADR-004 D8:**
  - an agent logs a small, reversible choice outside every spec obligation as an `ENT-` entry and goes on;
  - it asks, and never logs, about behaviour, scope, interfaces, permissions, security, spec or AC obligations,
    policy values, approvals, new dependencies and major versions;
  - "Hard boundary: logging never authorizes contradicting a spec, inventing a requirement or bypassing an
    approval."
- **ADR-006 D2** says rules for user-owned steps are changed by "No layer", and **D4** says layers "may never
  remove or relax a rule".

**The fit report (issue #162, local), approved by Bryan on 2026-11-08,** found that a key that could hand a
user-owned decision to the agent conflicts with all of the above (its C1 and C2). Bryan resolved it:
- ADR-010 only tightens ADR-004 D8;
- there are two owners, `agent_logged` and `user`, with no `agent` owner;
- a project may move an item from `agent_logged` to `user`, never back;
- changing an expert's tools or denied paths is always `user`;
- A7's "whether a human decision is required" is kept and derived from the owner.

The question: what can an organization or project configure about who decides, within those limits?

## Decision drivers

- ADR-003's model holds unchanged:
  - only approved policy binds;
  - layers apply in A3's order, with A4's precedence and A5's recording;
  - the schema enforces types;
  - semantic rules cover what the schema can't express.
- Nothing configurable may widen what ADR-004 D8 lets an agent decide.
- Organizations and projects need to tighten D8 for their own work, for example "a dependency's patch version is
  `user` here".
- ADR-009 D4 needs one rule ID per answer to cite.
- ADR-005 is the precedent: it added keys under ADR-003's own rules without editing ADR-003.

## Considered options

1. One key, `decisions.owner`, with two owners and a stricter-only merge.
2. The same key with a third owner, `agent`, that decides without logging (issue #162's first draft).
3. No key: ADR-004 D8 alone.
4. A delegation file outside policy (the advisor spec's `.advisors/delegation.md`).

## Decision outcome

**Chosen option:** option 1, as Bryan resolved the fit report's C1 to C3 on 2026-11-08.
- Option 2 has no counterpart in D8, which logs such choices.
- Option 3 leaves organizations and projects no way to tighten.
- Option 4 sits outside ADR-003's policy interface, with no layers, approval or validation.

### D1. The key

| Key | Class | Value | Framework default | Merge rule |
|---|---|---|---|---|
| `decisions.owner` | organizational policy | `{rule, scope, owner, source}`, one setting per rule | ADR-004 D8 itself: `agent_logged` for its small, reversible class, `user` for everything else | Collected across layers; stricter only (D2) |

- `rule`: an ID such as `D-01`, unique within its document.
- `scope`: what the rule covers, in plain words.
- `owner`: `agent_logged` or `user`.
- `source`: where the rule came from, for example a team agreement or an incident.
- The key is unconditional: `applies_when` isn't allowed, so it's resolved with A4's R2.
- `overridable_by` may list `project` and never `local`. Organizational-policy settings can't allow `local`
  (ADR-003 A4).

### D2. Stricter only

- **Order of strictness:** `agent_logged`, then `user`.
- **A later layer may move a scope to `user`, never back.** An organization or project rule may move a scope from
  `agent_logged` to `user`. No rule may move anything from `user` to `agent_logged`, the way ADR-006 D4 forbids
  relaxing a rule.
- **Choices no rule can give `agent_logged`:**
  - anything ADR-004 D8 says to ask about;
  - any choice a framework requirement reserves: scope, priority or release, brainstorm dispositions, approvals,
    an ADR's acceptance, and an expert's tools or denied paths (ADR-009 D2).

  A rule that gives `agent_logged` to one of these is invalid (D4).

### D3. Logging

- **Every choice made under an `agent_logged` rule is an `ENT-` entry** in the work item's ambiguity log (ADR-004
  D8), naming the rule's ID.
- **Review is unchanged:** entries are reviewed at the pull request, and QA lists the open ones, as D8 says.
- **Logging never authorizes** contradicting a spec, inventing a requirement or bypassing an approval: D8's hard
  boundary, unchanged.

### D4. Validation

- **Schema:** `policy.schema.json` gets one branch for the key, in the pattern of the existing branches. It
  fixes:
  - the value's four fields and their types;
  - `class: organizational_policy`;
  - no `applies_when`;
  - `overridable_by` limited to `project`.
- **SV-09 (new; stop):** `decisions.owner` rule IDs are unique within a document.
- **SV-10 (new; stop):**
  - an `owner` is `agent_logged` or `user`;
  - a rule that gives `agent_logged` to a choice D2 reserves is invalid;
  - across layers, a project rule may not move a scope an organization rule set to `user` back to
    `agent_logged`.
- **Numbering:** both rules follow SV-08 (ADR-005), the last in use. The shared `validate_policy.py` enforces
  them, and a violation is labelled `SV-09` or `SV-10`.

### D5. Resolution and recording

- **Resolution:** the key resolves with the unconditional settings (A4 R2).
- **Recording:** A5's resolution line names the rules that applied.
- **Citing:** an expert's answer cites the rule behind its decision owner (ADR-009 D4). When no setting applies,
  the answer cites ADR-004 D8 as the framework default.

### D6. When it's built

- The schema branch, the byte-identical copies in the prd, architecture and context skills,
  `validate_policy.py` and the defaults are plugin files.
- They change with the first build that uses the key: the reviewer's spec, or a later expert's.
- When ADR-006 D3's `progress.mode` is still waiting for a shared-schema change, both keys ride in the same
  change.
- No project policy is written with this ADR. A project's own rules belong in that project's repository.

### Consequences

- **Good:**
  - Organizations and projects can make the agent ask more, never less.
  - Every expert answer can cite the rule behind its owner.
  - The framework requirements and ADR-004 D8 stay where they are.
- **Bad:**
  - One more key in the shared schema, with the cost ADR-006 D3 describes: the shared-schema change, the copies,
    and requalifying the skills that validate policy.
  - The list of choices D2 reserves must be kept in step with the framework requirements as they grow.

### Confirmation

- **Policy checker tests:**
  - SV-09 and SV-10 each stop on their violation;
  - a stricter project rule wins;
  - a looser one stops.
- **An expert eval case:** an answer under an `agent_logged` rule writes an `ENT-` entry, and an `adjacent`
  answer is owned by `user` (ADR-009 D4).

## Pros and cons of the options

### Option 1: one key, two owners, stricter only (chosen)
- Good, because it tightens within D8 and fits ADR-003's interface.
- Bad, because it needs the shared-schema change (D6).

### Option 2: a third owner, `agent`, with no log
- Good, because it gives the agent more freedom.
- Bad, because it widens D8, contradicts FR-003, and conflicts with ADR-003 A1, A2 and A4 (the fit report's C1
  and C2).

### Option 3: no key
- Good, because it adds nothing.
- Bad, because an organization can't make the agent ask about something D8 would let it log.

### Option 4: a delegation file outside policy
- Good, because it's simple to write.
- Bad, because it has no layers, approval, validation or recording, so it duplicates ADR-003 A3 badly.

## Out of scope

- Any change to what ADR-004 D8 itself allows. That would be a new version of ADR-004.
- `applies_when` conditions for the key.
- A project's own rules, which belong in its repository.
- The schema change itself (D6).
