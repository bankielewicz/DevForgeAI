# ADR-003 — Adaptive foundations: policy, knowledge, experts and custom workflows around a fixed core

## Context and problem statement

DevForgeAI is meant to be an **adaptive** spec-driven engineering framework. The established term for
this is *process tailoring*. Its core workflows are fixed, and each organization's rules and knowledge
shape how they run: required quality categories, mandated platforms, development approach, coverage
rules, and how and where a library is used.

The first two skills already contain values that differ between organizations. If every new skill
hardcodes its own, adapting later means rewriting all of them. But not every value is configurable:
some are DevForgeAI's own quality requirements, some are document contracts that other workflows depend
on, and some are platform limits.

This ADR draws the boundaries now, and defers the broader expert system.

## Decision drivers

- Organization-specific behaviour must not require editing a core workflow.
- A setting that downstream consumers depend on (a document contract) can't be changed through configuration.
- Human decisions stay human (PRD-001 FR-003). Experts recommend; they don't decide.
- What informed a document must be recorded, so a policy change is traceable to what it affects.
- Everything must work with what Claude Code offers today. Anything not yet exercised is marked as such.

## Considered options

1. **Separate core, policy, knowledge, experts and custom workflows behind explicit contracts, with a small configuration contract now.**
2. Put organizational rules into the prose instructions of experts (subagents) and skills.
3. Defer adaptation until the core workflow set is finished.

## Decision outcome

**Chosen option:** option 1. Option 2 makes conflicts, updates and verification hard, because a
threshold hidden in prose can't be checked or overridden cleanly. Option 3 means retrofitting every skill.

### Part A — Logical design (independent of any tool)

#### A1. Five components

| Component | Responsibility | Example |
|---|---|---|
| Core workflow | Required outcomes, document contracts, decision ownership, evidence | The prd skill writes a PRD that satisfies the PRD schema |
| Policy | Explicit, approved, versioned rules and preferences | "Identity must use the Org A platform"; interview length |
| Project knowledge | What the product and implementation actually are, with sources and freshness | Which API client exists, where it's used, which ADR governs it |
| Expert | Applies policy and knowledge to one task and explains the result | An integration expert assesses a change to the payment adapter |
| Custom workflow | An organization-specific procedure with declared inputs, outputs and checks | An organization's database-migration workflow |

**Observed practice is not policy.** A pattern found throughout a codebase is knowledge. It becomes
policy only when someone approves it. Likewise, "tests passed" and "accepted under a policy exception"
are always reported separately.

#### A2. Classification of values (before any extraction)

Every value that might vary is assigned one class. Only the organizational-policy and interaction-default
classes are configurable, and configuration contract v1 exposes only three settings.

| Class | How it changes | Current examples | Exposed in v1 |
|---|---|---|---|
| **Framework requirement** | DevForgeAI's own PRD or an ADR | Eval threshold 0.8 for DevForgeAI's skills (PRD-001#NFR-003); provenance fields; ID-only names; the AI never decides scope; the quality **floor** per operating context (SPEC-002 BEH-03); validation retries (3) | No |
| **Document contract** | Schema version, plus a mapping for consumers | MoSCoW `priority`; `stage`, `operating_context` and `release` values; BRN `disposition`; NFR categories; item prefixes | No. A different prioritization method needs a mapping to MoSCoW or a schema change, not a setting |
| **Organizational policy** | Approved policy document, with applicability | Extra required quality categories; mandated platforms. *Later:* development approach (TDD or not), coverage metric, scope, exclusions and threshold, test-failure exceptions, deployment approval | `quality.required_categories`, `architecture.mandated_platforms` |
| **Interaction default** | Policy document or local preference | Interview call budget (8); brainstorm idea count (5–15); clarifying-question limit (3) | `interview.max_calls` |
| **Platform limit** | Not configurable | AskUserQuestion: at most 4 questions per call, with 2–4 options each | No |

#### A3. Policy interface (configuration contract v1)

- **A policy document** (`POL-NNN`, schema `policy.schema.json`) holds citable **settings** (`SET-NN`). Each setting has:
  - `key` (one of the supported keys) and `class`;
  - `value`, typed per key;
  - `applies_when`, an optional applicability condition (v1: operating context);
  - `overridable_by`: which lower layers may override it;
  - `rationale`.
- **Only approved policy binds.** A draft or in-review policy document is a proposal and is ignored when
  resolving. A workflow that finds one says so.
- **Scopes and layers**, from general to specific:
  1. framework defaults, shipped inside each skill;
  2. organization policy (`scope: organization`), which must record its `source`;
  3. project policy (`scope: project`);
  4. local preference (interaction defaults only; format below).
- **Conditional settings.** In v1 only `quality.required_categories` may carry `applies_when`, and it must name at
  least one operating context. Every other key is unconditional, so it can be resolved before the interview starts.
- **Local preference format.** A user-local, gitignored file `.claude/devforgeai.local.md` whose YAML
  frontmatter is its entire content: `devforgeai_local: 1`, then one entry per interaction-default key, for
  example `interview.max_calls: 5`. An entry is used only when the key is an interaction default and the
  effective setting's `overridable_by` includes `local`. Any other entry (unknown key, organizational-policy
  key, bad type or range, or not allowed) is **ignored and reported, never fatal**, because local preferences
  can't block a shared workflow. A local value has no policy ID, so it is recorded in the resolution line (A5)
  as `<key>=<value> (local)`, never as a link.
- **Where each layer lives:** organization and project policy live in the project repository under
  `docs/specs/policy/`, at most one approved document per scope. **Organization policy is vendored**, a
  copied file whose `source` records the origin repository and ref. Keeping copies in several
  repositories in sync is out of scope for v1.
- **Supported keys (v1):**

  | Key | Class | Value | Merge rule |
  |---|---|---|---|
  | `quality.required_categories` | organizational policy | list of NFR categories, with required `applies_when` | **Additive only**: added to the framework floor and never removes a floor category |
  | `architecture.mandated_platforms` | organizational policy | `{capability, platform, source}`, one setting per mandate | Collected across layers. A project may override only when the organization setting allows `project` |
  | `interview.max_calls` | interaction default | integer 1–20 | The most specific layer that is allowed to set it wins |

#### A4. Resolution sequence, precedence and validation

**Sequence.** Every workflow resolves policy in this order, so two implementations reach the same result:

| Step | What happens |
|---|---|
| R1. Load and validate | Read every `docs/specs/policy/POL-*.md`. Validate each approved document against the schema, then against the semantic rules below. Any violation in an approved document stops the workflow before anything is written. Draft or in-review documents are skipped and reported |
| R2. Resolve unconditional settings | Layer framework defaults, then organization, then project, then local preference, for the keys without `applies_when` (in v1, `interview.max_calls` and `architecture.mandated_platforms`). The interview budget is therefore known before the first question |
| R3. Establish operating context | From the request, the input document, or the first interview question |
| R4. Evaluate conditional settings | Apply each `quality.required_categories` setting whose `applies_when` includes the context. If the context is still unknown (for example, a run with no user), evaluate as `production`, the fail-safe choice, and record that |
| R5. Record | Write the links and the resolution line (A5) |

**Precedence.** Two questions are answered separately:
- **Which value wins?** The most specific layer that is *allowed* to set the value.
- **Who may override?** A setting's `overridable_by`. Local preferences may change interaction defaults only.
  Framework requirements, document contracts and platform limits are not settings, so nothing overrides
  them. Framework floors are additive-only.

**Validation: where each rule is enforced.**

| Rule | Enforced by |
|---|---|
| Types, ranges, known keys, key/class match; `applies_when` names a context and appears only on `quality.required_categories`; organization scope records `source`; organizational policy can't allow `local` | Schema (`policy.schema.json`) |
| **SV-01** Setting IDs are unique within a document | Semantic, R1 (stop) |
| **SV-02** At most one approved document per scope | Semantic, R1 (stop) |
| **SV-03** `interview.max_calls` at most once per document | Semantic, R1 (stop) |
| **SV-04** At most one active `architecture.mandated_platforms` per capability per document. Across layers, a project setting for the same capability overrides only if the organization setting allows `project`; otherwise stop | Semantic, R1/R2 (stop) |
| **SV-05** Only `status: active` settings take part. Deprecated settings stay in the document for traceability but never apply | Semantic, R1 |
| **SV-06** Only approved documents take part. Others are reported | Semantic, R1 |
| **SV-07** Local preference entries follow the local format rules (A3) | Semantic, R2 (ignore and report) |

**Failure behaviour**

| Situation | Behaviour |
|---|---|
| No approved policy document | Use framework defaults and record it in the resolution line |
| Schema or SV-01 to SV-04 violation in an approved document | **Stop before writing anything.** Name the file, setting and rule |
| A lower layer overrides a setting that disallows it | **Stop** and report the attempted override |
| Bad local preference entry | Ignore it and report it |
| Knowledge conflicts with policy (the code uses a platform that policy doesn't mandate) | Not an error. Report it as a finding, labelled as observed practice |

#### A5. Recording what informed a document

A workflow records each policy setting it applied as an `upstream` link carrying the policy version, for
example `{id: POL-001, item: SET-02, relation: informed_by, version: 3}`. A mandated platform that becomes a
constraint is cited with `relation: constrains`. When a policy changes, every dependent document's link
becomes suspect through the existing mechanism, so no new machinery is needed.

Because links can't express defaults, local values or skipped documents, the Change Log entry also carries
one **resolution line** in a fixed format:

`Policy resolution: <entry>; <entry>; …`

Each entry has one of these forms:
- `<key>=<value> (POL-NNN#SET-NN)`
- `<key>=<value> (default)`
- `<key>=<value> (local)`
- `POL-NNN#SET-NN not applicable (<context>)`
- `operating context unknown, resolved as production`
- `ignored <file or local entry> (<reason>)`

For example: `Policy resolution: interview.max_calls=5 (local); quality.required_categories=+compliance (POL-001#SET-02); operating context unknown, resolved as production`.

#### A6. Knowledge interface

In v1, knowledge sources are accepted ADRs and documents the input names (SPEC-002 BEH-16). Each citation
records the source ID, or its path and the date read. A knowledge source may declare a `last_verified`
date. A workflow flags sources older than the freshness window it declares, as a finding, not an error.
A broader knowledge register and automatic reassessment on code changes are later capabilities (PRD-001 FR-010).

#### A7. Expert contract (logical; implementation deferred)

| | |
|---|---|
| **Consulted when** | A workflow reaches a decision within the expert's declared domain |
| **Inputs** (explicit, since an expert has no access to the conversation) | The task and question; the resolved policy settings that apply, with their IDs; the knowledge sources, with IDs or paths; the relevant document excerpts |
| **Outputs** | A recommendation; references to the settings and sources that support it; conflicts found (policy vs knowledge, source vs source); open questions; whether a human decision is required |
| **Authority** | Recommends only. Settings are applied by the workflow, and choices go to the user. An expert may recommend a different approach from an approved rule, but that recommendation stays labelled as a proposal until the policy changes |
| **Evidence** | Every claim cites a setting or source. Claims without a source are marked as the expert's judgment |
| **Lifecycle** | Domain, sources and their freshness, permitted actions, behavioral evals, and the changes (code, dependencies, architecture, policy) that trigger reassessment. Specified when the first expert is built |

#### A8. Custom workflow contract (logical)

A custom workflow declares:
- inputs, as document types or IDs;
- outputs, as document types and schemas;
- its handoff (the next step and how it's detected);
- the required checks (validation and evals);
- the settings it consumes;
- the core contract versions it's compatible with.

It's built from the skill template in `src/staging/templates/skill/`. The template gains these fields
when the first custom workflow needs them, not before.

**Levels of customization:**
1. Configuration, when only values differ.
2. A workflow variant or supporting skill, when the procedure differs (for example TDD vs another approach).
3. A custom workflow, when the activity or artifact is distinct.

This keeps organizations from maintaining a copy of every core workflow.

### Demonstration plan (Architecture Definition, future SPEC-003)

Run the same **policy-neutral input PRD**, one with no existing identity decision, constraint or ADR, through
the Architecture Definition workflow under two organizations' policies. The policies are staged in
`src/staging/examples/policy-two-orgs/` and validate against `policy.schema.json`.

- **Organization A** mandates an identity platform (`SET-01`). **Pass criterion:** the result recommends
  reusing it, cites `POL-001#SET-01` with `relation: constrains`, and records no identity decision as open.
- **Organization B** mandates nothing for identity. **Pass criterion:** the identity choice appears as an
  open decision (a `[NEEDS ADR]` marker), with the sources consulted.
- **Both runs** cite the policy they used in links and the resolution line. Swapping the two policy files
  swaps the results. **The loaded workflow is identical in both runs:** a SHA-256 manifest of the deployed
  plugin (`.claude/skills/devforgeai/`, excluding `evals/results/`) matches before and after each run,
  `/plugin` shows the same plugin version, and `git diff src/` is empty.

This validates the boundary with an explicit policy reader and a small knowledge source. It doesn't need an expert system.

### Consequences

- Good: adaptation has a contract before most workflows exist, so each new skill reads settings instead of hardcoding them.
- Good: policy changes are traceable through the existing suspect-link mechanism.
- Bad: every skill must implement resolution (A4) until `devforgeai check` exists, a duplication risk. Mitigated by keeping the rules in one reference file per skill, copied from this ADR.
- Bad: vendored organization policy can drift from its source. Recording the source's ref makes drift visible, but not automatic.

## Out of scope

- The expert catalog, and expert creation and maintenance (PRD-001#FR-010, later).
- Generating custom workflows (PRD-001#FR-011, later).
- Settings beyond the three v1 keys.
