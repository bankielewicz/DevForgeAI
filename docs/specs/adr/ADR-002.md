# ADR-002 — Add a system-architecture step between the PRD and epics

## Context and problem statement

The workflow was brainstorm → prd → epic → story → spec. Architecture first appeared in story-level
specs, so decisions shared by several epics were made late, and separately in each spec: component
boundaries, data ownership, major interfaces, deployment and shared technical constraints. Different
people or agents could build incompatible foundations for separate epics. SPEC-002 already flags open
architecture decisions with `[NEEDS ADR]` markers that block the affected epics, but no step in the
workflow resolves them.

## Decision drivers

- Separate epics must be implementable without inventing conflicting foundations.
- The PRD states what and why, and must not become a design document (SPEC-002 BEH-16).
- Detailed feature design (exact API contracts, data structures, migrations) belongs just before the
  feature is built, in its spec.
- The step must stay cheap when little changes: an expansion of an established product, or a local prototype.

## Considered options

1. **A system-architecture step between the PRD and epics (a future `architecture` skill).**
2. Keep architecture in story-level specs, and write ADRs by hand when someone notices a shared decision.
3. Put architecture in the PRD.

## Decision outcome

**Chosen option:** option 1. The workflow becomes:

```mermaid
flowchart LR
    B[Brainstorm] --> P[PRD]
    P <--> A[Architecture review and ADRs]
    A --> E[Epics]
    E --> S[Stories]
    S --> D[Detailed specs]
    D --> I[Implementation]
```

Two levels are distinguished:

| Level | Decided in | Establishes |
|---|---|---|
| System architecture | The architecture step, before work is split into epics | Component boundaries and responsibilities, data ownership, major interfaces, deployment approach, shared technical constraints |
| Detailed feature design | Each spec, before the feature is implemented | Exact API contracts, data structures, state transitions, error handling, migrations, verification approach |

"Accepted" means reviewed and agreed for the current scope. It doesn't mean frozen: later changes are new
ADRs that supersede earlier ones.

**The PRD ⇄ architecture loop has a mechanism in both directions.**
- **PRD to architecture:** `[NEEDS ADR]` markers (SPEC-002 BEH-16) are the architecture step's input
  queue. An accepted ADR resolves a marker and unblocks the epics it named.
- **Architecture to PRD:** when architecture work shows a requirement is infeasible, too costly or in
  conflict with a constraint, the change goes back through the prd skill's controlled extension
  (SPEC-002 BEH-09). The version is bumped, and an approved PRD returns to review. The architecture step never edits a PRD.

The prd skill hands off to the architecture step instead of the epic step (SPEC-002 BEH-13). The
architecture step's outputs, depth and document types are specified by its own spec. That includes
whether it adds a system-overview document type, and how it only confirms the existing architecture
for an expansion.

### Consequences

- Good: shared technical decisions are made once, before epics are split, and are recorded as ADRs that epics and specs cite.
- Good: `[NEEDS ADR]` markers now have a step that resolves them.
- Bad: one more step in the workflow. For small or established scopes it must be a short confirmation, or it becomes ceremony.
- Bad: until the architecture skill exists, the step is done by hand, by writing ADRs with the ADR template.

### Confirmation

- The prd skill's handoff names the architecture step (STORY-002 AC-07, SPEC-002 VER-07).
- The architecture skill's spec implements this decision (future SPEC-003).

## Pros and cons of the options

### Architecture step between PRD and epics (chosen)
- Good, because it matches where shared decisions must be settled. BMAD's architecture phase, Spec Kit's
  technical planning and Kiro's design phase sit in the same place, between requirements and task breakdown.
- Bad, because it adds a step.

### Architecture in story specs, ADRs by hand
- Good, because it adds no step.
- Bad, because shared decisions are made late and separately for each spec, and nothing prompts anyone to write the ADR.

### Architecture in the PRD
- Bad, because it mixes what and why with how, and design would be approved as a product decision.
