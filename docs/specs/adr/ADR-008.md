# ADR-008 — A guard for DevForgeAI's own plugin changes: a dev-only mod refuses edits outside a plugin-dev iteration, and a commit check backs it

## Context and problem statement

Bryan's rule is that every change to the `devforgeai` plugin goes through `/plugin-dev:create-plugin` and
`/plugin-dev:skill-development`. It lived only in Claude's memory and was broken twice:
- 444a38c, 2026-10-02;
- every plugin commit on PR #126, which Bryan closed unmerged on 2026-10-31 ("I closed the pr due to your violation!").

Issue #137 is the incident and the enhancement. It specifies:
- A, a `dev-guard` mod that refuses plugin edits without an open ticket;
- B, a commit check;
- C, the rule in CLAUDE.md.

C shipped in PR #138 (merged 2c2f419). A and B are builds, and CLAUDE.md says "never build what no spec, ADR or
recorded decision covers". ADR-006 decides when a hook may block, but leaves guards out:
- it says "a guard fails closed" (D1);
- its out-of-scope list says: "Guard rules for commands and paths, such as the mods document's dev-guard … need
  policy keys of their own, in a later ADR."

This is that ADR, for DevForgeAI's own repository. It takes the number ADR-007 named for a different, hypothetical
supersession (ADR-007:431).

**The question:** where does the guard live, what may it refuse and when, where do its rules live, and what backs it
where it can't see?

## Decision drivers

- **A reminder is not a gate.** The rule was known and still broken, the second time in a worktree and through a
  subagent. The guard has to refuse, not remind.
- **ADR-006 D1:** a hook blocks only where an ADR says it may, by refusing the call with a reason the model reads. A
  guard fails closed.
- **ADR-006's dogfooding driver:** "watching without blocking must remain possible."
- **ADR-006's portability driver and its rejected option 3:** a rule can't live only in Claude Code's own settings,
  because "a project can't approve or version a rule there, and another tool's adapter can't read it."
- **The guard can't see everything.** A mod runs only inside Claude Code; edits from Codex, an editor or a shell need
  a second check (#137, A.6).
- **Bryan's preferences:** deterministic logic and hooks over heuristics, and strict with recovery.

## Considered options

1. **A dev-only mod outside the plugin**, in `src/tools/mods/dev-guard/`, plus a commit check in `src/tests/`
   (#137 decision 1 (a)).
2. **The guard inside the plugin's one hooks module**, shipped to every user but inert by default (#137 decision
   1 (b), ADR-006's one-mod view).
3. **No mod:** the CLAUDE.md rule (C) and the commit check (B) only.

## Decision outcome

**Chosen option:** option 1 (Bryan, 2026-10-31, "src/tools/mods/dev-guard/ (Recommended)").
- Option 2 would ship a guard for DevForgeAI's own development to every user of the plugin. It would also put a
  fail-closed guard in the same module as the progress tracker, which fails open (ADR-006 D1).
- Option 3 is the reminder that failed twice; B alone finds the problem only after the commit.

### D1. A separate guard, not the tracker's hook

- The guard is its own mod, `src/tools/mods/dev-guard/`, loaded through `CLAUDE_CODE_PLUGIN_DIRS` (mods reference.md:409).
  It is not part of the `devforgeai` plugin, and the progress tracker's hook is not involved. This answers EVAL.md
  row ADR2's "tracker's hook or a separate guard".
- **Its job is the mods proposal's A3 skill-gate:** plugin edits only inside an iteration
  (`docs/specs/devforgeai-claude-mods.md` §5). The proposal's A1 rules (`git add -A`, ADR-005 D7's commands, the push
  traps) are out of scope, and the name stays "dev-guard" (Bryan, 2026-10-31, items h and i).

### D2. What it protects and what it refuses

- **Protected path (item a, the path anchor).** A path is protected when two things hold:
  - its real path contains the segment `/src/claude/DevForgeAI/`;
  - that folder's `.claude-plugin/plugin.json` names the plugin `devforgeai`.

  That covers skill text, references, scripts, hooks, the manifest and generated eval cases, in any checkout or
  worktree. No machine path is configured. The anchor is inside the protected tree, so removing it is itself a
  refused edit.
- **Also protected:** `docs/process/plugin-workflow/guard.json` (D5) and `ledger.jsonl` (D6). Only a person, or the
  mod's own close, changes them. Both R1 and R2 cover them. Reports in `reviews/` are written by the session; D6's
  close and D8's check don't take them on the session's word alone.
- **Deny rules.** R1 covers Write, Edit and NotebookEdit. R2 covers Bash that isn't read-only and either names a
  protected path (the plugin path, `guard.json`, `ledger.jsonl`) or `make_evals.py`, or runs with a protected working
  directory. R3 covers `git commit` with a staged
  plugin file. The requirements are #137's A.3. The API facts behind them:
  - `tool.check` answers `{decision: 'deny', reason}` (reference.md:59);
  - `e.agentId` marks a subagent's call (:64-66; P2);
  - `e.isReadOnly` is the tool's own report (:71-75; P3).
- **R2's allowlist (item b; Bryan changed it, 2026-10-31).** `guard.json` lists the plugin's read-only invocations that
  run without a ticket:
  - `claude plugin validate` and `claude plugin test` on the plugin;
  - `pytest`;
  - the read-only scripts that CLAUDE.md's Commands run from the plugin path (`validate_brn.py`, `check_docs.py`,
    `find_spec.py`).

  P3 found `isReadOnly` absent for `python3`, so without the list the "Look it up before building it" script would be
  refused. A command is allowed only when it is one listed invocation alone, matched on the whole command, never a
  substring: no `>`, `>>`, `|`, `;`, `&&` or `tee`. **A limit:** `pytest` and `claude plugin test` run repository code
  (tests, a `conftest.py`) that can write plugin files unseen; whether to narrow the list is SPEC-019's to settle.
- **R2 and R3 are best effort.** They match command text, which the platform treats as a reminder for Claude. R3 reads
  only the index, so `git commit -a`, `commit <path>`, cherry-pick and merge pass it. D8's check is the proof.
- **Generator and grader edits.** An edit under `src/tests/<skill>/` doesn't open an iteration on its own;
  regenerating the cases does, through R2. Bryan was asked "Should a generator or grader edit itself open a
  plugin-dev iteration?" and answered "No, leave the rule (Recommended)" (2026-10-31).

### D3. When a guard may block (extends ADR-006 D1)

ADR-006 D1 lets a hook block only at the tracker's gates, and only when `progress.mode` is `enforce`. This ADR
extends it:
- A guard may refuse the tool calls its rules name, on the paths its scope names, whatever `progress.mode` is.
- It refuses with a reason the model reads, naming the rule, the first protected path and the remedy (#137, A.3).
- It never changes content silently.

ADR-006's own text points here at its next change (Bryan, 2026-10-31, "At its next change").

### D4. No mode

The guard always refuses; it has no observe mode and no second mode key.
- **ADR-006's dogfooding driver** keeps watching possible because a guard that corrects Claude also hides the *skill*
  defect it corrected. This guard refuses a *process* skip, not a skill behaviour, and every refusal is logged, so
  nothing is hidden.
- **The refusal log carries each refused command's full text.** Reviewing the first iteration's refusals is part of
  its close, so the allowlist grows from evidence (Bryan, 2026-10-31).
- **Recovery from a broken guard** is a person's act: start the session with `--safe-mode`, or drop the folder from
  `CLAUDE_CODE_PLUGIN_DIRS` (overview.md:234; reference.md:409). Both stop installed mods. Neither is a file the
  model can write in the repository.

### D5. Where the guard's rules live

- **The rules:** the protected path is fixed by D2's anchor. What a ticket must have read (`requiredReads`) lives in a
  tracked file, `docs/process/plugin-workflow/guard.json`. It is read by the mod (A) and the commit check (B), and
  protected by R1.
- **A missing or invalid file is a refusal, not an off switch.** A protected write is refused with a reason that names
  the file. That is "a guard fails closed" (ADR-006 D1).
- **Class:** under ADR-003 A2, a rule for DevForgeAI's own development is a framework requirement, changed only by
  DevForgeAI's PRD or an ADR. This ADR fixes the values, and the file carries them with the repository.
- **This departs from ADR-006's out-of-scope line,** which says guard rules "need policy keys of their own". For one
  repository's own development rules, a framework requirement in a tracked file avoids a shared-schema change. Guards
  for users' projects would still need policy keys in a later ADR.
- **The alternatives:**
  - `userConfig` as #137 wrote it, which is ADR-006's rejected option 3;
  - policy keys in `policy.schema.json`, at the cost ADR-006 D3's key carried: three skill version bumps and
    requalification.

### D6. The ticket

#137's A.2 holds, with these changes:
- **Storage and opening.** One ticket per branch, in `$.store`, which every session on the machine shares, a parallel
  one included (reference.md:221, :391; P6). It opens when `plugin-dev:create-plugin` loads. `skill.prompt` carries
  `e.skill` `plugin-dev:create-plugin` and `e.pluginName` `plugin-dev`, and the Skill tool call carries the same name
  (P1). The ticket's scope is the skill's arguments, which the build reads from the Skill tool call's input or the
  typed command; P1 recorded the name only.
- **When it permits.** Only once `/plugin-dev:skill-development` has loaded and every `requiredReads` file has been
  Read in this iteration. Reads don't carry over to the next ticket. A Read of any range counts, which is a nudge,
  not a proof that the guide was read.
- **`requiredReads` resolution.** A worktree reads the main checkout's copy, the parent of
  `git rev-parse --git-common-dir`. With no copy found, the ticket doesn't permit, and the remedy is to capture the
  pages by each PROVENANCE.md's recipe. That is the sentence now in CLAUDE.md's rule and #137's C block; Bryan's
  word was "Apply all of item 4" (2026-10-31).
- **Reports** go in `docs/process/plugin-workflow/reviews/<UTC>-<tool>-<hash>.md`, committed on the branch. Bryan,
  2026-10-31: "Put them in docs/process/plugin-workflow/ now, not after A ships … keeping the <UTC>-<tool>-<hash>.md
  pattern so /dev-guard close adopts it unchanged". This replaces #137 A.2's `<id>/<hash>-<tool>.md`.
- **Closing binds to the plugin's content, not to HEAD (item f).**
  - `/dev-guard close` refuses unless the plugin-validator and skill-reviewer reports exist for a commit X whose
    plugin subtree hash, `git rev-parse X:src/claude/DevForgeAI`, equals HEAD's.
  - A docs-only commit, the reports' own commit included, leaves that hash unchanged (checked 2026-10-31: `1744e6c` on
    a docs commit, its parent and main).
  - On close, the mod appends one line to `docs/process/plugin-workflow/ledger.jsonl`. The line carries the
    evidence, not only a reference to it:
    - the ticket's id, scope and times;
    - when skill-development loaded, and the reads;
    - both observed reviewer calls (their `agentId` and time);
    - the subtree hash (`tree`) and the report paths.

    SPEC-019 fixes the line's schema. The ledger line and the reports go out in one records commit, which EVAL.md's
    carry-forward rule must also allow (issue #140).
  - Bryan, 2026-10-31: "Reports only: no hand-written ledger.jsonl lines; the mod writes those."
- **The reviewers' runs are observed, not asserted** (Bryan, 2026-10-31). The ticket records each Agent call it sees
  whose `subagent_type` is `plugin-dev:plugin-validator` or `plugin-dev:skill-reviewer`. Close refuses unless both ran
  during the ticket. P2 showed the mod sees Agent calls; reading their `subagent_type` is the build's first test,
  because the probe didn't log that field.
- **Only a person's command closes (item g, from P7).** The model can't run `/dev-guard close` through the Skill tool.
  A nested `claude -p` from Bash would run it with `origin.kind` `sdk` (P4), so the close refuses `sdk`.
- **Cleanup.** A closed ticket leaves `$.store` once its ledger line is written.

### D7. Failure, and where the guard can't see

- **It fails closed** (ADR-006 D1). Each guard hook's `.catch` refuses the call it was checking, naming the error. The
  handler does no I/O, because a `.catch` gets one second (reference.md:373), and a test covers a throwing hook.
- **It doesn't run** in these cases:
  - sessions started with `--bare` or `--safe-mode`, or with `disableAllHooks` set, including in a project settings
    file (overview.md:234);
  - a Desktop WSL session (overview.md:193) or a cloud session;
  - a `claude plugin eval` run (P5);
  - a session where the module failed to load.

  It also sees no edit made by Codex, an editor or a shell. D8's check covers all of these at review time.

### D8. The commit check (B)

- **The test.** `src/tests/process/test_plugin_workflow.py` compares the branch head's plugin subtree hash with its
  merge base's. In a pull request's CI job, the branch head is the PR's head commit, not the merge commit GitHub
  checks out, so a plugin change on main can't fail an unrelated PR. It passes when either holds:
  - the branch leaves the plugin unchanged: the two hashes are equal;
  - the head's hash equals the `tree` of a `ledger.jsonl` line that validates against SPEC-019's schema, with its
    reports present and both reviewer calls and skill-development's load recorded.

  Rebases, amends and squashes don't matter, because only the final content is checked. No commit needs an
  exemption, because commits already on main are never checked.
- **Where it runs.** The test carries a pytest marker that `pytest src/tests` skips by default, so an open iteration
  doesn't make G2 red. A GitHub Actions job runs it on every pull request, with `fetch-depth: 0` so the merge base
  resolves. It passes at once when the plugin's subtree is unchanged, so a required check never waits on a docs-only
  PR. Bryan's answer was "docs/process + CI job" (2026-10-31).
- **The job becomes a required check when B ships** (Bryan, 2026-10-31: "Decide now: B's CI job becomes a required
  check when B ships."). Without it B is advisory, because the guard doesn't run in Desktop WSL or cloud sessions
  (D7). Setting it is the Owner's step.

### Consequences

- **Good:** the rule is a refusal at the moment of the edit, in the main conversation, in subagents and in worktrees,
  with the remedy in the reason.
- **Good:** each iteration leaves evidence a reviewer can check from the PR: the reports, and a ledger line bound to
  the plugin's content (REVIEW.md check 3).
- **Good:** the guard holds no machine path and no off switch in the repository.
- **Bad:** a broken guard stops plugin edits until a person restarts the session without it (D4).
- **Bad:** R2 and R3 are best effort, and the guard's own source isn't guarded (#137, "Not covered"); it is built
  through `/mod-builder:build`. Sessions it can't see rely on B, so a bad change is found at review time, not at the edit.
- **Follow-up:**
  - #137 gets a comment pointing to this ADR and SPEC-019, which replace its A.1 to A.7 and B where they differ;
  - ADR-006's D1 points here at ADR-006's next change; until then CLAUDE.md's line on the accepted ADRs says so;
  - SPEC-019 carries A's and B's requirements, with EVAL.md's A and B rows as its VER table; its drafts review and
    Bryan's approval come before A starts, and the mod is built through `/mod-builder:build`;
  - the Owner's settings: GitHub's managed Code Review (which reads REVIEW.md), and B's job as a required check
    when B ships;
  - EVAL.md's carry-forward rule allows `ledger.jsonl`, and its rows ADR1 ("Change Log row", where an ADR keeps a
    Status history) and P5 ("A.1 keeps it inert") are reworded (issue #140).

## Pros and cons of the options

### Option 1: a dev-only mod and a commit check
- Good, because it refuses at the edit, and it ships nothing to plugin users.
- Bad, because it is a second mod beside the tracker, and its own source isn't guarded.

### Option 2: inside the plugin's hooks module
- Good, because it is ADR-006's one-mod view, and its source would be guarded too.
- Bad, because every user ships a guard for DevForgeAI's own development, and a fail-closed guard shares a module with
  a fail-open tracker.

### Option 3: no mod
- Good, because there is nothing to build beyond B.
- Bad, because it is the reminder that failed, and B finds the problem only after the commit.

## Departures from issue #137

Each is Bryan's to confirm, and #137 changes only after he does:
- **Scope:** the path anchor (D2), instead of `repoRoots`.
- **Rules home:** `requiredReads` in a protected, tracked `guard.json` (D5), instead of `userConfig`.
- **Closing and the commit check:** both bind to the plugin's subtree hash (D6, D8), instead of HEAD's short hash and
  a list of commit hashes. Only a person's command closes a ticket.
- **B:** skipped by default in `pytest src/tests` and run in CI (D8).
- **R1 and R2** also protect `guard.json` and `ledger.jsonl` (D2).
- **Close** also requires both reviewers' Agent calls observed during the ticket (D6). **R2** has an allowlist in
  `guard.json` (D2).
- **Decided by Bryan before this ADR:** the report path (D6), and `requiredReads` found through the main checkout from
  a worktree (D6).
- **Probes:** #137 runs them "before the build"; these ran before acceptance, which is earlier.
