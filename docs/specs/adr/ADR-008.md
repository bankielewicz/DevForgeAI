# ADR-008 — A guard for DevForgeAI's own plugin changes: a dev-only mod refuses edits outside a plugin-dev iteration, and a commit check backs it

## Context and problem statement

Bryan's rule is that every change to the `devforgeai` plugin goes through `/plugin-dev:create-plugin` and
`/plugin-dev:skill-development`. It lived only in Claude's memory and was broken twice:
- 444a38c, 2026-10-02;
- every plugin commit on PR #126, which Bryan closed unmerged on 2026-10-31 ("I closed the pr due to your violation!").

Issue #137 is the incident and the enhancement. It specifies:
- A, a `dev-guard` mod that refuses plugin edits without an open ticket;
- B, a commit check;
- C, the rule in CLAUDE.md.

C shipped in PR #138 (merged 2c2f419). A and B are builds, and CLAUDE.md says "never build what no spec, ADR or
recorded decision covers". ADR-006 decides when a hook may block, but leaves guards out:
- it says "a guard fails closed" (D1);
- its out-of-scope list says: "Guard rules for commands and paths, such as the mods document's dev-guard … need
  policy keys of their own, in a later ADR."

This is that ADR, for DevForgeAI's own repository.

**The question:** where does the guard live, what may it refuse and when, where do its rules live, and what backs it
where it can't see?

## Decision drivers

- **A reminder is not a gate.** The rule was known and still broken, the second time in a worktree and through a
  subagent. The guard has to refuse, not remind.
- **ADR-006 D1:** a hook blocks only where an ADR says it may, by refusing the call with a reason the model reads. A
  guard fails closed.
- **ADR-006's dogfooding driver:** "watching without blocking must remain possible."
- **ADR-006's portability driver and its rejected option 3:** a rule can't live only in Claude Code's own settings,
  because "a project can't approve or version a rule there, and another tool's adapter can't read it."
- **The guard can't see everything.** A mod runs only inside Claude Code; edits from Codex, an editor or a shell need
  a second check (#137, A.6).
- **Bryan's preferences:** deterministic logic and hooks over heuristics, and strict with recovery.

## Considered options

1. **A dev-only mod outside the plugin**, in `src/tools/mods/dev-guard/`, plus a commit check in `src/tests/`
   (#137 decision 1 (a)).
2. **The guard inside the plugin's one hooks module**, shipped to every user but inert by default (#137 decision
   1 (b), ADR-006's one-mod view).
3. **No mod:** the CLAUDE.md rule (C) and the commit check (B) only.

## Decision outcome

**Chosen option:** option 1 (Bryan, 2026-10-31, "src/tools/mods/dev-guard/ (Recommended)").
- Option 2 would ship a guard for DevForgeAI's own development to every user of the plugin. It would also put a
  fail-closed guard in the same module as the progress tracker, which fails open (ADR-006 D1).
- Option 3 is the reminder that failed twice; B alone finds the problem only after the commit.

### D1. A separate guard, not the tracker's hook

- The guard is its own mod, `src/tools/mods/dev-guard/`, loaded through `CLAUDE_CODE_PLUGIN_DIRS` (mods reference.md:409).
  It is not part of the `devforgeai` plugin, and the progress tracker's hook is not involved. This answers EVAL.md
  row ADR2's "tracker's hook or a separate guard".
- **It does the mods proposal's A3 skill-gate job** (`docs/specs/devforgeai-claude-mods.md` §5): plugin edits only inside an
  iteration. The proposal's A1 dev-guard rules (`git add -A`, ADR-005 D7's commands, the push traps) are out of scope
  here. The name follows #137 (open question 8).

### D2. What it protects and what it refuses

- **Protected path:** a path whose real path is inside the repository (its worktrees included) and that contains the
  segment `/src/claude/DevForgeAI/`. That covers skill text, references, scripts, hooks, the manifest and generated
  eval cases (#137, A.1).
- **Deny rules** R1 (Write, Edit, NotebookEdit), R2 (Bash that isn't read-only and names the plugin path or
  `make_evals.py`, or runs with a protected working directory) and R3 (`git commit` with a staged plugin file). Their
  requirements are #137's A.3, with `tool.check`'s `{decision: 'deny', reason}` (reference.md:59), `e.agentId` for
  subagents (:64-66) and `e.isReadOnly` (:71-75).
- **Generator and grader edits** under `src/tests/<skill>/` don't open an iteration on their own. Regenerating the
  cases does, through R2 (Bryan, 2026-10-31, "No, leave the rule").

### D3. When a guard may block (extends ADR-006 D1) — proposed, open question 1

ADR-006 D1 lets a hook block only at the tracker's gates, and only when `progress.mode` is `enforce`. Proposed
addition:
- A guard may refuse the tool calls its rules name, in the repositories its scope names, whatever `progress.mode` is.
- It refuses with a reason the model reads, naming the rule, the first protected path and the remedy (#137, A.3).
- It never changes content silently.

### D4. Observe and enforce — proposed, open question 2

ADR-006 requires that watching without blocking stays possible. #137 has no observe mode. Proposed:
- `enforce` by default in this repository;
- `observe` available for diagnosis: it logs the refusal it would have made and lets the call run;
- every refusal, and every one it would have made, is logged in both modes.

### D5. Where the guard's rules live — open question 3

The rules are:
- the scope (which repositories);
- the protected path segment;
- the files a ticket must have read (`requiredReads`);
- where reports go.

The options:
- **(a) `userConfig`**, as #137 wrote it (`repoRoots`, `requiredReads`). That is ADR-006's rejected option 3: the
  rules aren't versioned with the repository, and B can't read them.
- **(b) A tracked file, `docs/process/plugin-workflow/guard.json`**, read by both A and B. **Recommended.**
  - **Scope:** the mod acts in a session whose git root holds that file, and stays inert everywhere else. That
    replaces `repoRoots`, so the mod holds no machine path.
  - **Class:** under ADR-003 A2, a rule for DevForgeAI's own development is a framework requirement, changed only by
    DevForgeAI's PRD or an ADR. This ADR fixes the values, and the file carries them with the repository.
  - **Cost:** no shared-schema change.
  - **ADR-006's out-of-scope line:** guards for users' projects still need policy keys, in a later ADR.
- **(c) Policy keys** in `policy.schema.json`. These cost what ADR-006 D3's key cost: the shared-schema change, three
  skill version bumps and requalification. They would be for a rule that applies to one repository.

### D6. The ticket

#137's A.2 holds, with these changes:
- **Storage and opening.** One ticket per iteration, in `$.store` (shared by every session on the machine, 4 MiB;
  reference.md:221, :391). It opens when `plugin-dev:create-plugin` loads (`skill.prompt`'s `e.skill` and
  `e.pluginName`, reference.md:92-104, or the Skill tool call).
- **When it permits.** Only once `/plugin-dev:skill-development` has loaded and every `requiredReads` file has been
  Read.
- **`requiredReads` resolution** (Bryan, 2026-10-31, item 4):
  - A worktree reads the main checkout's copy, which is the parent of `git rev-parse --git-common-dir`. The guides
    under `docs/research/` are gitignored, so a worktree has no copy of its own.
  - When no copy is found, the ticket does not permit. The remedy it names is to capture the pages by the recipe in
    each PROVENANCE.md.
- **Reports** go in `docs/process/plugin-workflow/reviews/<UTC>-<tool>-<hash>.md`, committed on the branch (Bryan,
  2026-10-31, "Put them in docs/process/plugin-workflow/ now"). This replaces #137 A.2's `<id>/<hash>-<tool>.md`.
- **Closing.** `/dev-guard close` refuses unless the plugin-validator and skill-reviewer reports exist for HEAD's
  short hash. On close it appends the ticket as one line to `docs/process/plugin-workflow/ledger.jsonl`. No ledger
  line is written by hand (Bryan, 2026-10-31).

### D7. Failure, and where the guard can't see

- **It fails closed** (ADR-006 D1). Each guard hook's `.catch` refuses the call it was checking, naming the error.
- **It doesn't run** in sessions started with `--bare` or `--safe-mode`, with `disableAllHooks` set (overview.md:234),
  or in a Desktop WSL session (overview.md:193). It sees no edit made by Codex, an editor or a shell. B covers
  those at review time.

### D8. The commit check (B)

- **The test.** `src/tests/process/test_plugin_workflow.py` lists the branch's commits since `git merge-base HEAD
  origin/main` that touch `src/claude/DevForgeAI/`. It fails for any commit that no closed ticket's `commits` in
  `ledger.jsonl` contains, and it runs in `pytest src/tests`.
- **The CI job.** A GitHub Actions job runs the test on pull requests that touch `src/claude/DevForgeAI/**`
  (Bryan, 2026-10-31, "docs/process + CI job").
- **Plugin commits made before the first ledger line:** open question 5.

### Consequences

- **Good:** the rule is a refusal at the moment of the edit, in the main conversation, in subagents and in worktrees,
  with the remedy in the reason.
- **Good:** every iteration leaves committed evidence, reports and a ledger line, that a reviewer can check from the
  PR (REVIEW.md check 3).
- **Good:** with option (b), A and B read one versioned rules file, and no machine path is configured.
- **Bad:** a fail-closed guard can stop work when it breaks. The refusal names the error, and `observe` (D4), if
  accepted, is the way around it while it's fixed.
- **Bad:** the guard's own source isn't guarded (#137, "Not covered"); open question 6 is about its build.
- **Bad:** sessions it can't see rely on B, so a bad commit is found at review time, not at the edit.
- **Follow-up:**
  - #137's text moves to match D5 and D6 once Bryan approves them;
  - ADR-006 gains a version whose D1 points here, the next time it changes for another reason, as ADR-006 did for
    ADR-003;
  - GitHub's managed Code Review, which reads REVIEW.md, is an Owner's setting, not part of this ADR.

## Pros and cons of the options

### Option 1: a dev-only mod and a commit check
- Good, because it refuses at the edit, and it ships nothing to plugin users.
- Bad, because it is a second mod beside the tracker, and its own source isn't guarded.

### Option 2: inside the plugin's hooks module
- Good, because it is ADR-006's one-mod view, and its source would be guarded too.
- Bad, because every user ships a guard for DevForgeAI's own development, and a fail-closed guard shares a module with
  a fail-open tracker.

### Option 3: no mod
- Good, because there is nothing to build beyond B.
- Bad, because it is the reminder that failed, and B finds the problem only after the commit.

## Open questions

Each question below is Bryan's to decide, with a recommendation:
1. **Blocking (D3).** Extend ADR-006 D1 so a guard may refuse the calls its rules name, in the repositories its scope
   names, whatever `progress.mode` is. *Recommended: yes.*
2. **Mode (D4).** *Recommended:* `enforce` by default here; `observe` for diagnosis; every refusal logged in both
   modes.
3. **Rules home (D5).** *Recommended: (b), a tracked `guard.json`.*
4. **Spec home.** The project's pattern is an ADR for the decisions and a spec for the behaviour, as with SPEC-005 and
   SPEC-013. #137's A.1 to A.7 and B are requirements in an issue. *Recommended:* a short SPEC-019 that carries them
   as BEH and VER items, so the build has a spec to cite. The alternative is this ADR plus #137, as written.
5. **Plugin commits before the first ledger line (D8).** B checks only the branch's commits since the merge base, so
   commits already on main are never checked. *Recommended: no exemptions.* A branch that holds plugin commits from
   before the guard redoes them inside a ticket, as Bryan chose for PR #126 ("(b) Redo everything").
6. **The mod's own build.** CLAUDE.md's rule covers only `src/claude/DevForgeAI/`. *Recommended:* the mod is built
   through `/mod-builder:build` (spec-first, with validate, test and tsc). That is the mods' counterpart of
   create-plugin.
7. **EVAL.md in `requiredReads`.** CLAUDE.md can only point to EVAL.md (PR #139's review, R9). *Recommended: yes.*
   Reading it would then be part of opening an iteration.
8. **The name.** The mods proposal uses "dev-guard" for its A1 trap rules. *Recommended:* keep "dev-guard" as #137
   has it, and say here that A1's rules are out of scope (D1). The alternative is "plugin-gate".
9. **Who may close a ticket** (from P7). The model can't run `/dev-guard close` through the Skill tool. It could run
   a nested `claude -p "/dev-guard close"` from Bash, and that child session shares `$.store`. *Recommended:* the
   close refuses a `command.run` whose `origin.kind` is `sdk`, so only a person's typed command closes a ticket. The
   reports for HEAD are still required either way.
