# ADR-006 — Mods and progress tracking in the layered model: each rule's class decides who changes it, one mode key, project manifests as custom-workflow checks, and how hooks block and fail

## Context and problem statement

DevForgeAI's rules live mostly in text that Claude must remember: the skills, `CLAUDE.md` and the specs. Claude Code mods are hooks that run inside Claude Code as things happen. They can refuse a tool call, read results and replies, and show the user what's going on. Two drafts use them:
- the progress tracker, which judges each skill step by evidence (`docs/specs/devforgeai-progress-ui.md`; SPEC-012, draft, its core);
- guardrail mods (`docs/specs/devforgeai-claude-mods.md`).

Bryan's vision (2026-10-02) is an adaptive framework:
- **one mod** that serves DevForgeAI's own development and any project built with it;
- **rules in layers:** a core set of skills and rules, then the project's own skills and rules, then personal settings.

ADR-003 already defines that layering for policy:
- **A3:** framework defaults, then organization policy, then project policy, then local preference, with `overridable_by` and additive-only floors;
- **A2:** classes of values;
- **A8:** custom workflows that declare their required checks.

But ADR-003 Part B also says: "Hooks: not part of this design until a hook's blocking behaviour and failure mode are specified and tested."

**The question:** how do mods and the progress tracker fit ADR-003's layers? Who may change each of their rules? And how may a hook block, and how does it fail?

## Decision drivers

- **Decisions are the user's** (PRD-001 FR-003): no layer may let a skill write a decision the user didn't make.
- **Projects add their own workflows with their own checks** (PRD-001 FR-011; ADR-003 A8).
- **One resolution order** (ADR-003 A4): mods must not bring a second precedence model.
- **Portability:** the progress evaluator is Python, and adapters for tools other than Claude Code must read the same rules. Anything that holds a rule can't live only in Claude Code's own settings.
- **ADR-003 Part B's condition:** a hook's blocking behaviour and failure mode must be specified and tested.
- **Dogfooding:** a guard that corrects Claude also hides the skill defect it corrected, so watching without blocking must remain possible.

## Considered options

1. Extend ADR-003. Map each tracker rule to an ADR-003 class, add one interaction-default key, treat a project skill's manifest as an A8 check, and specify how hooks block and fail.
2. A configuration system of its own for mods, with its own files and precedence.
3. Configure mods only through Claude Code's plugin settings (`userConfig`).

## Decision outcome

**Chosen option:** option 1, because it keeps one layering for skills and mods, as Bryan's vision asks.
- Option 2 would add a second precedence model next to ADR-003 A4.
- Option 3 can't express an approved project rule, and an adapter for another tool can't read it.

### D1. Mods enter the design: when a hook may block, and how it fails

This meets ADR-003 Part B's condition for hooks.

**Blocking.** A hook may block only:
- at one of the progress tracker's gates: the write gate, the report gate or the run's end (SPEC-012 BEH-08);
- and only when the effective `progress.mode` is `enforce` (D3).

It blocks by refusing the gate's tool call with a reason the model reads. It never blocks by changing content silently.

**Confirming the user's own command (version 2; Bryan, 2026-10-05: "Amend ADR-006").** A question the adapter asks
the user before a command the user typed runs, such as `/clear` or `/exit` while a tracked run is unfinished
(SPEC-013 BEH-28), is not a block: it refuses nothing Claude does, the user answers it, and the command runs on the
user's go-ahead. It may be asked in both modes. It fails open: when the question can't be shown, the command runs;
only the user's own answer or dismissal keeps it from running.

**Failure.**
- **The tracker fails open.** When the evaluator can't run (SPEC-012 exit 2), the adapter lets the call proceed, shows the user a visible notice, and logs it. A broken tool must not stop the user's work, and the tracker's flags are a review aid that a later run can raise again.
- **A rule that can't be checked is not a flag.** For example, written content may be unavailable (SPEC-012 ERR-05).
- **A guard fails closed.** A guard hook that refuses specific commands or paths does so with a `.catch` that refuses the call it was checking, naming the error. A guard exists to stop that call, and a crashed guard that lets it through would fail silently. Guard rules themselves are out of scope (below); this only fixes how a guard fails.

**Testing.** The adapter's spec tests these with `claude plugin test`:
- refusals in both modes;
- a guard's `.catch` failing closed;
- the tracker failing open when the evaluator exits 2.

### D2. Each rule's class decides who can change it

| Rule | ADR-003 class | Who can change it |
| --- | --- | --- |
| Content rules for user-owned steps: a BRN's dispositions stay `open` and its status `draft`, an ADR stays `proposed`, an ARCH's `outcome` stays `null` without the user's answer (SPEC-012 §4) | framework requirement (A2 lists "the AI never decides scope") | No layer. They follow FR-003 |
| Gates and evidence rules in the manifests the plugin ships | framework default | Organization and project layers may add rules, never remove or relax one (D4) |
| Manifests for a project's own skills | custom-workflow required check (A8) | The project layer supplies them |
| Whether the tracker blocks: `progress.mode` | interaction default (new key, D3) | Project policy sets it and decides whether local preference may override it |
| Character, animation, how the pane opens | not policy | Each host's own settings (D6); they change no rule |

### D3. One new key: `progress.mode`

| Key | Class | Value | Framework default | Merge rule |
| --- | --- | --- | --- | --- |
| `progress.mode` | interaction default | `observe` or `enforce` | `observe` | The most specific layer allowed to set it wins (A4). A project that requires enforcement sets `enforce` without `local` in `overridable_by` |

- **The framework default is `observe`** while the tracker is new: it flags without blocking, so dogfooding keeps finding skill defects (the mods document's rule 4).
- **Resolution.** The adapter resolves the key at session start, with the unconditional settings (A4 R2), and records the value and its source in the run's event log.
- **Cost of the key.** Like ADR-005's keys, it needs the shared-schema change: `policy.schema.json` in `src/schemas/` and its byte-identical copies in the prd, architecture and context skills, plus `validate_policy.py` and the defaults. That bumps SKL-002, SKL-003 and SKL-010, which are requalified on their policy eval cases.
- **Timing** (Bryan, 2026-10-02): the key's schema change rides with the next shared-schema change. Until it lands, the adapter applies the framework default and honours an entry in the local preference file; locking the mode at project level arrives with the schema change.
- **Switching it yourself** (Bryan, 2026-10-02):
  - The band and pane show the effective mode, with a button to switch it: **Switch to enforce** in observe mode, **Switch to observe** in enforce mode.
  - Pressing it writes `progress.mode` to your local preference file (D6), so the choice persists across sessions.
  - When the project's setting doesn't allow `local` in `overridable_by`, the button is unavailable and the band names the setting that locks the mode, for example `set by project policy (POL-001#SET-04)`.

### D4. Project manifests are custom-workflow checks, and layers only add rules

- **A project's own skill** (an A8 custom workflow) declares its progress manifest as one of its required checks, in the format of SPEC-012 DM-01.
- **Layers only add.** Manifests apply in A3's order: the plugin's (framework), then organization, then project. A later layer may add evidence rules, gates or content rules to a framework manifest, and may supply manifests for skills the framework doesn't have.
- **A layer may never remove or relax a rule** from an earlier one. An attempt stops evaluation with the file and rule named (SPEC-012 exit 2), as ADR-003 A4 stops a disallowed override.
- **Personal settings never change rules.**
- **Where manifests live in a project** (Bryan, 2026-10-02): `devforgeai/manifests/` at the project root, tracked in git, one `<skill>.json` per skill. Vendored organization manifests go in `devforgeai/manifests/organization/`, each recording its `source` as A3 requires of organization policy. Every tool's adapter reads the same folder. Run files stay apart, in `devforgeai/progress/`, gitignored by default.

### D5. Recording which layers applied

The progress state lists the manifest files applied, in layer order. This is the tracker's counterpart of A5's resolution line, so a renderer can show "framework rules" or "framework and project rules", and a reviewer can see which rules judged a run.

### D6. Personal settings: portable rules in one place, display in the host

- **`progress.mode`** is the one personal value that affects rules. A user's entry goes in the host's local preference file, in A3's format: `.claude/devforgeai.local.md` for Claude Code, while the Codex port keeps its own (`.codex/devforgeai.local.md`). Each adapter reads its host's file; the button of D3 writes it.
- **Display-only settings** (character, animation, how the pane opens) stay in each host's own mechanism, such as Claude Code's plugin settings. They are not policy, they don't travel between tools, and they change no rule.

### Consequences

- **Good:** skills and mods share one layering, and DevForgeAI's own repository is just a project with a richer project layer: its own rules, checks and settings. The same mod serves any project.
- **Good:** user-owned decisions stay protected in every layer, because their rules are framework requirements.
- **Good:** an adapter for another tool reads the same manifests, policy and local preference file.
- **Bad:** `progress.mode` costs a shared-schema change, with three skill version bumps and requalification. It can be batched with the next shared-schema change.
- **Bad:** layers only add. A project that disagrees with a framework gate must propose a framework change; it can't switch the gate off.
- **Bad:** failing open means a broken install loses enforcement until someone fixes it. The visible notice and the log make that loss seen.
- **Follow-up:**
  - SPEC-012 cites this ADR and gains layered manifests, while it stays blocked on this ADR's acceptance;
  - the adapter's spec implements and tests D1, D3 and D6;
  - ADR-003 gains a version whose Part B "Hooks" row points here the next time it changes for another reason (Bryan, 2026-10-02), so its 7 citing documents aren't re-linked for this alone.

### Confirmation

- **Structural:** this ADR's frontmatter validates against `src/schemas/adr.schema.json`; the result is in the Status history.
- **SPEC-012's tests** show that a project layer's added content rule applies, and that an attempt to relax a framework rule exits 2.
- **The adapter's spec** shows with `claude plugin test` the blocking and failure behaviour of D1, and the resolution of D3.
- **The shared-schema change's tests** cover `progress.mode`'s valid and invalid values and its `overridable_by`.

## Pros and cons of the options

### Option 1: extend ADR-003
- Good, because ADR-003's layers, precedence and recording apply unchanged.
- Good, because a project skill's manifest is just one more A8 check.
- Bad, because one key costs a shared-schema change across three skills.

### Option 2: a configuration system of its own for mods
- Good, because it could change without touching the skills.
- Bad, because two precedence models would have to stay consistent, and users would learn both.

### Option 3: Claude Code's plugin settings only
- Good, because it's built in and needs no schema change.
- Bad, because a project can't approve or version a rule there, and another tool's adapter can't read it.

## Out of scope

- **Guard rules for commands and paths,** such as the mods document's dev-guard (refusing `git add -A`, protecting a deployed copy). They need policy keys of their own, in a later ADR. D1 fixes only how a guard fails.
- **Distributing organization manifests** beyond ADR-003's vendoring.
- **Renderers and their display,** and the layout of the pane.
- **The adapters themselves.** Claude Code's is a later spec; other tools' adapters follow these layers through their own.
