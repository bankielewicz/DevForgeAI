# ADR-009 — Run experts as read-only plugin agents, on the subscription by default or through an API runner the plugin ships, chosen per expert

## Context and problem statement

ADR-003 A7 defines the expert contract, "logical; implementation deferred", with its Lifecycle "Specified when
the first expert is built". Part B describes an expert as "A plugin subagent (`agents/<name>.md`) invoked by a
skill, with the A7 inputs passed explicitly", marked "Documented only, not tested here". This ADR calls them
experts, as ADR-003 and PRD-001 do (issue #162, decision 4.2 A).

PRD-001 version 15 makes experts current work:
- FR-010 (should, current) covers experts DevForgeAI ships and experts organizations add;
- FR-026 (must, current) is the first one: an independent review that answers the question before it sees the
  session's answer, then critiques that answer.

Bryan decided on 2026-11-08 (recorded in issue #162's comment of 2026-11-09; his 2026-11-09 decisions on the
issue's §4 are recorded in the session, with an issue comment to follow):
- the MVP is the Phase 0 documents plus the independent reviewer;
- each expert carries `billing: max | api`, exposed through the devforgeai mod: "each subagent for skill will be
  customizable to use max plan or api key";
- the API runner ships in the plugin, in TypeScript: "Keeping the runner separate isn't great for usability";
- the core names no project, language or domain.

**Platform facts this ADR relies on.** Each is labelled with its source. The local captures of Anthropic's pages
are under `docs/research/Claude/`.

The question: how do experts run in Claude Code, what may they touch, who pays for each run, and how does the
first expert fit?

## Decision drivers

- **A7 holds:**
  - an expert recommends and never decides;
  - its inputs are passed explicitly;
  - every claim cites a source;
  - human decisions stay with people (FR-003).
- **Usability:** one install (Bryan, 2026-11-08).
- **Billing stays where the user put it.** The main session stays on its subscription unless the user chooses
  otherwise, and an API run never falls back to the subscription.
- **Independence for review (FR-026):** the reviewer answers before it sees the session's answer.
- **A project- and language-agnostic core** (Bryan, 2026-11-08).
- **No spend without a cap.**
- **Confirmation:** platform behaviour not yet verified is confirmed before anything relies on it.

## Considered options

1. Plugin agents only, on the subscription; API runs only in a tool outside the plugin (issue #162's first
   draft).
2. API runs for every expert, through the Agent SDK.
3. Skills only, with no agent.
4. Plugin agents on the subscription by default, plus an API runner the plugin ships, chosen per expert with
   `billing: max | api`.

## Decision outcome

**Chosen option:** option 4, from Bryan's decisions of 2026-11-08 and 2026-11-09. It meets every driver:
- the subscription by default;
- the API where an expert is set to it, with one install;
- A7 kept intact.

### D1. An expert is a plugin agent, and its inputs are explicit

- **Its file** is `src/claude/DevForgeAI/agents/<name>.md`. The frontmatter sets `model`, `effort`, `maxTurns`
  and `tools`; the body is the expert's role.
- **A skill calls it** and passes A7's inputs in the task message:
  - the task and question;
  - the resolved settings that apply, with their IDs;
  - the knowledge sources, with IDs or paths;
  - the relevant excerpts.
- **"Called by a skill" is a convention** that the agent's description carries (P1).
- **The reviewer (FR-026) may also be asked for by the agent at a decision point,** through the mod's tool (D6).
- **Calling skills pass no `model`** (P2), so the frontmatter's choice holds.

### D2. Experts are read-only, and the caller writes

- **Tools:** an expert's tools are Read, Grep and Glob. WebSearch and WebFetch are for a research expert only,
  after the MVP. An expert never gets Write, Edit, Bash or Agent.
- **Where the limit comes from:** `tools` in the agent's frontmatter, and the runner's tool list for `api` runs.
  It never comes from `permissionMode`, which plugin agents ignore (P3).
- **The caller writes.** The calling skill checks what the expert returns and does any writing, so no hook limits
  an expert's writes. ADR-006 D1 now says when a hook may block. The conclusion still holds, because the caller
  writes.
- **Changing an expert's tools or denied paths is always the user's decision** (Bryan, 2026-11-08, in the fit
  report's resolution).

### D3. Each expert's spec sets its model, effort and turns

- The values sit in the agent's frontmatter. The spec names them, with the calibration that justifies them.
- The approved advisor spec's defaults (local, not tracked) apply when those experts are specified after the MVP
  (issue #163), for example Opus 5.5 at `xhigh` for an architect.

### D4. The answer

- **A7's outputs:**
  - a recommendation;
  - references to the settings and sources that support it;
  - conflicts;
  - open questions;
  - whether a human decision is required.
- **Two more fields:**
  - a scope rating, `in_scope`, `adjacent` or `out_of_scope`, that cites the PRD or spec item;
  - the decision owner, `agent_logged` or `user`, with the ADR-010 rule it applies.
- **"Whether a human decision is required" is kept,** and derived from the owner: it's yes when the owner is
  `user`.
- **Only an `in_scope` answer may carry `agent_logged`,** and only within ADR-004 D8's small, reversible class.
  `adjacent` and `out_of_scope` answers are always `user`, because D8 asks about scope (the fit report's C2,
  resolved by Bryan on 2026-11-08).
- **Each expert's spec names its schema file.** The reviewer's answer is a list of findings. Each finding has a
  severity, its evidence, and whether it was verified, and the caller answers it accept, reject or escalate
  (FR-026).

### D5. Usage and spend

- **`max` runs:** the progress tracker's ledger counts their tokens under the subagent's ID (SPEC-012 DM-04).
  Counting by expert would need a change to SPEC-012 and SPEC-013; it is an open question and isn't built.
- **`api` runs:** the runner keeps its own ledger. Each row records:
  - the run's cost in dollars;
  - the credential source the child reported;
  - the outcome.
- **Caps:**
  - a daily and a monthly cap, checked before each run;
  - a per-run cap (the Agent SDK's `maxBudgetUsd`). The SDK's estimate can overshoot by about one turn, so the
    cap is set with headroom.

### D6. Billing per expert: `max` or `api`

- **Each expert carries `billing: max | api`,** which the user sets in the devforgeai mod's setup, as with the
  review mode (D8). Because of P4 and P5, the attribute routes the work rather than switching credentials:
  - **`max`:** an in-session plugin agent (D1), billed to the subscription.
  - **`api`:** the plugin's runner, a TypeScript program on the Agent SDK. The devforgeai mod starts it as a
    separate process with `$.process.run`. The mod also registers the tool through which the agent asks for a
    review (FR-026), and a command for the user.
- **How the runner is isolated:**
  - The API key is read from a file only the user can read. It never enters the main session's environment or
    settings, a command line, a log, or a tool result.
  - The child gets its own empty home and Claude Code config folder, so it has no subscription login or
    Anthropic CLI profile to fall back to (P7).
  - The child loads no settings, plugins or MCP servers, so it can't call the runner again.
  - The runner refuses to start without the key file or Node. `max` needs neither.
  - Every run's `apiKeySource` is checked and recorded (P7).
- **Dependencies** (Bryan, 2026-11-08):
  - On the first `billing: api` use, and after the user agrees, the Agent SDK is installed into
    `${CLAUDE_PLUGIN_DATA}` without optional packages.
  - The runner points the SDK at the installed `claude`.
  - The SDK isn't listed in the plugin root's `package.json`. Claude Code's automatic install (P6) would
    otherwise download the 325 MB bundled binary for every user, including those who never use the API (P7).
  - The mod compares the SDK's version with the installed Claude Code's and warns when they drift apart.
- **What this replaces:** issue #162's decision 4.3. Cross-review 1.1.1 stays outside the repository, frozen as
  the working reference. Its planned 1.2 items become requirements of the reviewer's spec: the run lock, recorded
  outcomes, the spend guard and the evidence audit (issue #161).

### D7. The core is project- and language-agnostic

- **Shipped expert files** name no project, language or domain (Bryan, 2026-11-08).
- **Project facts come from the installed project's own records,** assembled when the expert is called: A7's
  explicit inputs. The records are:
  - `CLAUDE.md`;
  - the context documents, loaded by ADR-004 D1's rule (`index.md` first, then only what the question needs);
  - the ARCH, ADRs, PRD and approved policy.
- **How they're assembled:**
  - each source is cited with its path and the date it was read (A6);
  - each source has a size cap, and so does the whole;
  - a redaction pass replaces recognized secrets before anything is sent.
- **A project may add its own reviewer roles and denied paths** in its own repository. They add rules and never
  relax shipped ones (ADR-006 D4).

### D8. The reviewer answers blind first, unless the user sets fork mode

- **The default is `mode: blind`:**
  - **First pass:** the reviewer gets the question, the evidence and the project facts, never the session's
    answer.
  - **Second pass:** it critiques the session's answer (FR-026).
  - **Hidden files:** files that hold the session's answer can be hidden from the first pass.
- **`mode: fork` is an attribute the user sets** per expert, in the devforgeai mod's setup, beside `billing`
  (D6). Bryan, 2026-11-09, as sent: "Add fork mode as an attribute the end user will be able to configure via the
  mod setup".
  - In fork mode the expert receives a copy of the session's conversation instead of a blind first pass.
  - It is a recorded exception to A7's input row ("explicit, since an expert has no access to the
    conversation"). The exception applies only to the experts the user sets to fork, and only while the setting
    stays on.
  - A forked answer is labelled as forked in the answer and the ledger, since it is less independent: the
    expert has seen the session's reasoning.
  - How each billing route forks is the reviewer's spec's to decide, after its probes. For `api`, the runner
    resumes a copy of the session file in its own config folder; that is a probe still to run.

### D9. A7's Lifecycle, filled in for the first expert

| Lifecycle field | The reviewer |
|---|---|
| Domain | Independent review of a decision or change, within the project's recorded documents |
| Sources | The question, the files involved and the project records of D7, each cited with its path and the date read |
| Permitted actions | Read only |
| Behavioural evals | Its spec's eval suite, plus a calibration set with planted flaws |
| Reassessment | When the Agent SDK or Claude Code's agent fields change, or a framework requirement on review changes |

Other experts fill in this row in their own specs.

### Consequences

- **Good:**
  - One install. The subscription stays the default, and the API is used only where an expert is set to it, with
    caps and a ledger.
  - A7 becomes real, with its outputs, its explicit inputs and read-only access.
  - The same expert definition serves both billing routes.
  - The reviewer's independence rests on its process boundary, its blind first pass and its own tools, not on
    the session's restraint.
  - The user chooses, per expert, between independence (blind) and full context (fork), and every answer says
    which it was.
- **Bad:**
  - The plugin gains a Node runner and an optional dependency installed on first use. `billing: api` needs Node
    on the machine.
  - Two code paths, `max` and `api`, must stay in step.
  - Claude Code and the pinned Agent SDK can drift apart in version.
  - An API key is one more secret to keep on the machine.
  - Since P1 makes "called by a skill" a convention, the main conversation can call a plugin agent directly.
    Its answer then carries no skill's checks.
  - Fork mode departs from A7's input row for the experts it's set on. Accepting this ADR accepts that exception.

### Confirmation

1. A manual check, before the first expert relies on them, that a plugin agent honours `model`, `effort`,
   `maxTurns` and `tools` on Bryan's Claude Code version (D1 to D3).
2. The probe of 2026-11-08 (done, P7).
3. Before the reviewer ships, a paid smoke run confirms three things:
   - the API is billed;
   - `apiKeySource` names the key;
   - `/status` in the main session still shows the subscription.
4. The reviewer's spec: its offline tests against a fake Claude Code CLI, its evals, and its manual VER items.

## Pros and cons of the options

### Option 1: plugin agents only; API runs in a tool outside the plugin
- Good, because the plugin gains no Node dependency.
- Bad, because the user installs and updates two things. Bryan rejected it on usability (2026-11-08).
- Bad, because the agent can't ask for an API review through the plugin.

### Option 2: API runs for every expert
- Good, because there's one code path, and every run has a hard dollar cap.
- Bad, because every call spends money, and every user needs an API key, even when the subscription would do.

### Option 3: skills only
- Good, because there are no agents to configure.
- Bad, because a skill runs in the main context: no fresh context, no tool list of its own, and the session's
  reasoning in view. That fails A7's explicit inputs and FR-026's independence.

### Option 4: plugin agents, plus a per-expert API runner the plugin ships (chosen)
- Good, for the reasons in the decision outcome.
- Bad, for the costs in Consequences.

## Open questions

- Counting usage by expert or by calling skill (D5): a change to SPEC-012 and SPEC-013, not built.
- Whether the progress tracker should mark an `api` run in the run log beyond the tool call it already records.

## Out of scope

- Building any expert, agent, skill, runner, schema or hook. The reviewer's spec does that, after this ADR.
- Codex versions of experts (issue #162, decision 4.5 A).
- The architect and the specialist experts (issue #163).
- Where verified facts live (decision 4.4 A; FR-027, release later).
