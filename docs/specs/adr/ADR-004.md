# ADR-004 — Enforce skill safeguards in layers: tool-level controls, a Bash sandbox, and deterministic checks

**Status: proposed.** This records what was observed, what is only documented, and what is proposed. Acceptance
needs the Confirmation steps below, and Bryan's decision. Version 2 adds:
- the round-2 results: complete Bash denial (option 7) and the combined design, both run headless;
- the documentation checks;
- the FH-1 function-hook results (option 8);
- confirmation steps for plugin routes (C5).

No confirmation step has passed, and nothing here completes STORY-004.

## Context and problem statement

Every safeguard in the DevForgeAI skills is an instruction in `SKILL.md` or its references. STORY-003 and
STORY-005 showed that instructions make behaviour likely, not certain:
- the architecture skill misreported readiness in its reply four times (SPEC-003 §9; STORY-004 AC-04);
- it wrote an ARCH with `sed -i` through Bash instead of Edit (SPEC-003 §9 row p);
- its draft warning came after the first write (VER-12 (c); STORY-004 AC-02);
- it listed folders outside the inspection scope on v2 (VER-12 (b); STORY-004 AC-01).

STORY-004 records these obligations and asks which mechanism enforces or checks AC-01, AC-02, AC-04 and AC-05.
ADR-003 excludes hooks "until a hook's blocking behaviour and failure mode are specified and tested". This ADR
specifies and tests them, within what Claude Code offers today.

The question is which safeguards can be **prevented** (the forbidden action never happens), which can only be
**detected** (a check finds the violation after it happens), and which have **no tested mechanism** yet.

## Decision drivers

- **Nothing aspirational:** only mechanisms observed working in this terminal count as available.
- **Name the failure modes:** a control that fails open must be described that way.
- **Prevention and detection are different claims.** A passing check or a deny message isn't proof that a
  boundary holds.
- **Approvals stay human:** a check can validate an approval field, but that doesn't establish human approval.
- **Don't widen scope:** this decides mechanisms; it doesn't implement them or change STORY-004's obligations.

- **The evidence** is in `~/devforgeai-evidence/ENF-11/`, outside the repository: settings, hook scripts,

### Documented only (not observed here)
Sources: code.claude.com `/docs/en/hooks.md`, `/hooks-guide.md`, `/permissions.md`, `/sandboxing.md` and

  when the skill is invoked, and stay for the rest of the session.
- `disableAllHooks` turns hooks off; hooks from managed settings still run unless it is set there.
- None of the plugin statements above were tested: no plugin was installed or reloaded in these experiments.

**Added in version 2** (checked 2026-09-26 against the snapshots under Sources):

*Permissions and settings*
- "An allow rule can't carve an exception out of a deny rule" (permissions). A deny naming a whole tool, such as
  `Bash`, removes it from Claude's toolset, from the next tool call if added mid-session.
- `--settings` applies above user, project and local settings and below managed ones, and merges with them. A key
  it omits keeps the lower value, and permission lists combine (settings). So a session's `--settings` deny adds to
  the project's denies and can't remove them.
- A single-value key takes the value from the highest-precedence file that sets it. So `sandbox.enabled`,
  `allowUnsandboxedCommands`, `failIfUnavailable` and `disableAllHooks` in `.claude/settings.local.json` override
  the project file. (That applies the documented precedence rule; it hasn't been tested.)
- Claude Code reloads settings files during a session, "including edits to `permissions`, `hooks`" (settings,
  "When edits take effect"). Whether sandbox settings reload isn't stated.
- **Protected paths** (permission-modes, "Protected paths"). Writes to `.claude/` (except `.claude/worktrees`),
  `.git` and similar paths are never auto-approved:
  - prompted in default and acceptEdits mode;
  - sent to the classifier in auto mode;
  - denied in dontAsk mode;
  - allowed in bypassPermissions mode.

  Allow rules don't pre-approve them.
- **Auto mode is the default starting mode for interactive sessions from 2.1.283** (permission-modes).

*The sandbox*
- It applies to Bash, PowerShell and Monitor commands and their child processes (sandboxing).
- It always denies writes to `.claude` settings files, to `.claude/skills`, `agents`, `commands` and `hooks`, to
  `.mcp.json` and to `.git/hooks` and `.git/config`. "There is no way to exempt one of these paths" except by
  turning off filesystem isolation (sandboxing).
- The first time a command needs a new network domain, Claude Code prompts. In auto mode the classifier reviews the
  hosts instead (sandboxing, "Network isolation").

*Hooks*
- The `if` filter is best-effort: "use the permission system rather than a hook to enforce a hard allow or deny"
  (hooks, line 448).
- A settings hook's `allow` can't loosen deny rules (hooks guide, line 969). That applies to settings hooks only;
  see option 8 for function hooks.
- A Stop hook "does not run if the stoppage occurred due to a user interrupt", and feedback that makes Claude
  continue has an 8-consecutive-continuation cap (hooks, lines 2542, 2631). So it can't guarantee that an invalid
  artifact never reaches downstream work.
- MessageDisplay hooks receive the assistant's text but are display-only. They can't block, don't fire for replies
  that are only tool calls, and run once per message in `-p` (hooks, lines 1451–1467).
- Settings hooks wait for the workspace-trust prompt in interactive sessions and run without it in `-p`.
- A ConfigChange hook can block a settings change, except to managed policy.

## Considered options

1. Instructions only (the status quo).
2. PreToolUse hooks as the gate.
3. Permission rules.
4. The Bash sandbox.
5. Layered: tool-level controls, plus the sandbox for Bash, plus deterministic checks for detection.
6. Deterministic checks only (detect, never prevent).
7. Complete Bash denial for planning sessions: Bash, Monitor and any other command tool denied (round 2).
8. Function hooks: a plugin's own TypeScript hooks on tool calls and host APIs (experimental, early access; FH-1).

## Decision outcome (proposed)

**Proposed option: 5, layered, within the limits below.** The layers:
- **Tool-level controls** stop Claude's Edit and Write tools from touching paths no skill may write. Use
  permission deny rules (E3b); a hook deny (E1) is the alternative where a rule can't express the condition.
- **The Bash sandbox** stops Bash and anything it launches from writing to protected paths, whatever the
  route (E6a, E6b), with `failIfUnavailable: true` and `allowUnsandboxedCommands: false`.
- **A deterministic checker,** the FR-018 `devforgeai check` release, detects violations in the written files
  and git history before downstream work consumes them. It never counts as prevention.

**The combination has been observed only headless, and is not confirmed.** Round 2 ran it in one fixture
configuration:
- **Forbidden:** every shell write tried was blocked (b1–b4, b6).
- **Permitted:** Write to `docs/specs/arch/`, `git commit` and the epic skill worked (p1, p2, c-epic).

**That isn't C1 passing:**
- `gh issue view` failed (p3), and the allowlist retry was inconclusive (p3b);
- no eval case was run;
- C1's literal-path `sed -i` wasn't run (b2 was the computed-path one);
- in this configuration the deployed copy got the Write tool (b5), not Edit, and `docs/specs/arch/` got Write
  only (p1);
- b4's block can't be attributed to the configured `denyWrite`.

Interactive behaviour is C2's scope.

The layered design stays a proposal until C1 and C2 show that the forbidden operations are all blocked **and** the
permitted ones still work.

**Option 7 is the alternative for planning sessions.** Complete Bash and Monitor denial closed every shell route
tried headless (R1b), and the planning skills ran without Bash (s-epic, s-arch). Which option applies to planning
sessions waits for C2, which confirms that an interactive session with Bash denied can still find documents.

**Loaded plugins are part of the boundary (FH-1).**
- **An Edit path-deny rule constrains Claude's file tools. It isn't a filesystem-wide restriction on every
  extension.** In L10, under `deny: Edit(docs/specs/prd/**)`, a loaded plugin changed two protected files through
  `$.fs.write` and `$.process.run` (observed). That holds for that rule and those two APIs, in that configuration.
  It doesn't show that every permission rule or sandbox setting is bypassed. Whether the sandbox confines those APIs
  is untested.
- **So the layered design has to account for the plugins a session loads and what their host APIs can reach.**
  Two things don't do that job:
  - **the deterministic checker**, which finds a plugin's write only after it happens: detection, never
    prevention;
  - **the function-hook switch.** At 0 it stopped the installed plugins' modules from loading, silently to the
    model, but the built-in plugins' modules still loaded (F2). A rollout flag also decides whether installed
    modules load, and the environment variable overrides it (F2's debug log). So the default can change with no
    local setting changing. The switch is a setting, not a boundary that can't be bypassed.
- **Trust assumptions keep two groups apart:**
  - **installed extensions:** plugins loaded with `--plugin-dir`, installed from a marketplace, or loaded from a
    skills folder;
  - **Claude Code's built-in runtime:** `agents-md` and `telemetry` loaded in every FH-1 run. Which other built-in
    mods are seated depends on the installation (mods README). FH-1 didn't rely on any of them.
- **Which plugins a planning session may load is an open question.** This version proposes no new control for it.
  C5 defines what the routes must show.

### Consequences

- **Good:** each obligation is labelled prevented, detected or open, from evidence rather than wording. The
  write-route result (E2, E3c, E3d against E6a, E6b) explains the `sed -i` finding and gives it a concrete
  proposed prevention.
- **Good:** hooks are used only where a plain rule can't express the condition, and never as the only gate,
  because every failure mode observed (E4, E5) fails open.
- **Bad:** the sandbox is a project-wide Bash boundary. It can't be scoped to one skill, and its network
  isolation may affect `git push`, `gh` and `claude plugin eval`. Headless, `gh issue view` failed and
  `git commit` worked (p3, p2); `git push` and an eval run are untested (C1 must test them).
- **Bad:** the sandbox's built-in protection of `.claude/skills/` can't be exempted (documented). So under
  option 5, a deploy into `.claude/skills/devforgeai/` can't run from Claude's sandboxed Bash (inferred from the
  documented protection; b4 is consistent with it but didn't separate the causes), and deploys move to a plain
  terminal, as evals already have.
- **Bad (option 7):** operator work (git, `gh`, deploys, evals) needs Bash or a plain terminal. Nothing restores
  Bash automatically, and interactive document discovery rests on one observation until C2 confirms it.
- **Bad:** the sandbox needs bubblewrap and socat on Linux and WSL, and isn't available on native Windows.
  `failIfUnavailable: true` turns a missing sandbox into a hard failure rather than a silent skip.
- **Bad:** several obligations have no prevention at all: per-skill write sets, the inspection scope, warning
  timing and approvals. They stay open with detection only, and the ADR says so rather than implying coverage.
- **Bad:** an Edit rule doesn't stop a loaded plugin's host APIs from writing (FH-1 L10). The design has to account
  for which plugins load, and nothing tested yet confines them.
- **Neutral:** a plugin can't ship permission or sandbox settings (documented, not tested). The preventive
  layer is a project `.claude/settings.json` the framework recommends; see #19. A function-hook plugin can
  intercept tool calls and host APIs itself (FH-1), but that API is early access (option 8).

## Pros and cons of the options

### 1. Instructions only
- Good, because there's nothing to configure.
- Bad, because the recorded failures happened under exactly this: prevention is never guaranteed.

### 2. PreToolUse hooks as the gate
- Good, because a deny blocks in every permission mode (documented; E1), and a hook can express conditions
  a rule can't.
- Bad, because timeouts, crashes and missing scripts all let the call through (E4, E5), and a hook matching
  Edit misses Bash writes (E2).
- Bad, because Anthropic's documentation says to use the permission system, not a hook, for a hard allow or deny
  (documented).
- Bad, because a skill-frontmatter hook stays registered after its skill ends (documented).
- Bad, because a Stop hook doesn't run on a user interrupt and stops after 8 consecutive continuations, so it
  can't guarantee that an invalid artifact never reaches downstream work (documented).

### 3. Permission rules
- Good, because they're declarative and block the Edit tool (E3b), and literal Bash writes (E3, E3e). An allow
  rule elsewhere, `--settings` included, can't override a deny (documented).
- Bad, because interpreter writes and computed paths get through (E3c, E3d), and a loaded plugin's
  `$.fs.write` and `$.process.run` weren't constrained by an Edit rule (FH-1 L10).

### 4. The Bash sandbox
- Good, because the OS blocks every Bash route tried, including interpreters and computed paths (E6a, E6b).
- Bad, because it doesn't cover Claude's own Edit and Write tools (E6d), and it's project-wide.
- Bad, because it blocked `gh` headless (p3), and its protection of `.claude/skills/` can't be exempted
  (documented), so deploys can't run from sandboxed Bash (inferred).

### 5. Layered (proposed)
- Good, because each layer covers the routes the others miss, and detection catches what prevention can't.
- Bad, because the combination is unverified until C1, and it adds project configuration.
- Bad, because an Edit rule doesn't cover a loaded plugin's host APIs (FH-1 L10), so the design must account for
  which plugins a session loads. Whether the sandbox confines those APIs is untested.

### 6. Checks only
- Good, because it's deterministic and cheap, and it's already planned (FR-018).
- Bad, because a violation is found after it happens. For writes to protected documents, that's too late
  without git.

### 7. Complete Bash denial for planning sessions
- Good, because a denied tool is removed from the session. With Monitor denied too, no shell route remained among
  those tried (R1b), and neither a subagent nor a skill's `!` preprocessing could run a shell command (R2, R3).
- Good, because the real epic and architecture skills completed without Bash (s-epic, s-arch), and it needs no
  sandbox dependencies.
- Bad, because denying Bash alone left Monitor as a shell route (R1). Every command tool has to be denied:
  PowerShell is documented as one, and C2 inventories the rest. Denying Bash doesn't by itself establish "no shell
  execution".
- Bad, because EnterWorktree still works (R6).
- Bad, because the Write tool into `docs/specs/prd/` isn't blocked (the per-skill gap, as in option 5).
- Bad, because a loaded plugin's `$.process.run` under Bash denial is untested (C5d).
- Bad, because operator work (git, `gh`, deploys, evals) needs Bash or a plain terminal, and nothing restores
  Bash automatically.
- Bad, because interactive document discovery rests on two single observations. Glob and Grep were absent with
  Bash available (FH-1 I0) and present after Bash was denied (Evidence). C2 has to confirm this.

### 8. Function hooks (experimental)
- Good, because the tested guard intercepted every route FH-1 recorded for Claude's file tools, Monitor, a
  subagent's Edit, a skill's `!` preprocessing, and plugins' `$.fs.write` and literal-path `$.process.run`
  (L1–L4, L6–L9, L11, L12).
- Good, because a `.catch` returning a deny held after a throw (F4).
- Good, because it is the only mechanism found that a plugin can ship itself.
- Good, because `claude plugin test` checked the guard's hook decisions at no cost (FH-1 step 0: observed $0 and
  0.74 s; no model calls inferred).
- Bad, because the API is early access and may change without notice (documented).
- Bad, because a missing module, an uncaught throw, a `.catch` that throws and a budget overrun each let the
  write through (F1, F3, F5, F6). A `.catch` handler has its own 1-second limit, so adding one doesn't guarantee
  failing closed (documented).
- Bad, because a deny reported after the hook has let the tool run doesn't undo it (maintainer, #91870). Results
  have to be measured on the files, not on deny messages.
- Bad, because the switch that turns off installed plugins' modules leaves the built-in ones loaded (F2).
- Bad, because a `tool.check` hook may change a verdict in either direction, loosening included (documented; not
  exercised, L13b). So
  plugin trust, plugin order and protecting the module from modification become part of the design; turning the
  feature on doesn't strengthen anything by itself.
- Guard-specific, not a limit of function hooks in general: the tested guard's command-string matching let
  computed paths through (L5, L11 computed) and over-blocked a read (L1). Whether any function-hook design can
  confine a shell's writes is untested.
- **Bryan's decision (2026-09-26):** early access is acceptable for isolated research at this stage. It is not
  acceptable as a shipped default or as a required safeguard.
- **Before any future proposal to use it,** a bounded experiment would have to show:
  - a permitted action succeeds and a forbidden one leaves no side effect;
  - exceptions, timeouts, a failing handler and a module that fails to load can't silently remove the
    protection;
  - other plugins, nested calls and subagents can't weaken it;
  - planning stays usable.

  The validation rules would stay in the `devforgeai` CLI, with the hook calling it, so there's one implementation.

## Open questions

- A per-skill write set, for example the architecture skill never writing `docs/specs/prd/`, has no static
  mechanism. Is a skill-frontmatter hook, which fails open and persists for the session, or a function hook in
  the plugin (early access, fails open, untested for per-skill scoping), acceptable as an added layer, or is
  detection enough?
- How is a human approval established in the terminal? Is the owner's PR merge the only recognized signal?
- The inspection scope and warning timing (STORY-004 AC-01 and AC-02) have no tested mechanism. What would
  count as a sufficient detection-only answer?
- Should DevForgeAI ship a recommended project `.claude/settings.json` for its users (#19), given that plugins
  can't carry permissions or sandbox settings?
- Which plugins may a planning session load, and how is that recorded? An Edit rule doesn't cover a loaded
  plugin's host APIs (FH-1 L10), and the function-hook switch doesn't unload built-in modules (F2). C5 defines the
  routes to check.
- For planning sessions, is it option 7 (Bash and Monitor denied), option 5 (the combined design), or both? The
  answer waits for C2, which confirms that an interactive session with Bash denied can find documents.
