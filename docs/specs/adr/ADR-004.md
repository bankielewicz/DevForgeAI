# ADR-004 — Enforce skill safeguards in layers: tool-level controls, a Bash sandbox, and deterministic checks

**Status: proposed.** This records what was observed, what is only documented, and what is proposed. Acceptance
needs the Confirmation steps below, and Bryan's decision.

## Context and problem statement

Every safeguard in the DevForgeAI skills is an instruction in `SKILL.md` or its references. STORY-003 and
STORY-005 showed that instructions make behaviour likely, not certain:
- the architecture skill misreported readiness in its reply four times (SPEC-003 §9; STORY-004 AC-04);
- it wrote an ARCH with `sed -i` through Bash instead of Edit (SPEC-003 §9 row p);
- its draft warning came after the first write (VER-12 (c); STORY-004 AC-02);
- it listed folders outside the inspection scope on v2 (VER-12 (b); STORY-004 AC-01).

STORY-004 records these obligations and asks which mechanism enforces or checks AC-01, AC-02, AC-04 and AC-05.
ADR-003 excludes hooks "until a hook's blocking behaviour and failure mode are specified and tested". This ADR
specifies and tests them, within what Claude Code offers today.

The question is which safeguards can be **prevented** (the forbidden action never happens), which can only be
**detected** (a check finds the violation after it happens), and which have **no tested mechanism** yet.

## Decision drivers

- **Nothing aspirational:** only mechanisms observed working in this terminal count as available.
- **Name the failure modes:** a control that fails open must be described that way.
- **Prevention and detection are different claims.** A passing check or a deny message isn't proof that a
  boundary holds.
- **Approvals stay human:** a check can validate an approval field, but that doesn't establish human approval.
- **Don't widen scope:** this decides mechanisms; it doesn't implement them or change STORY-004's obligations.

## Evidence

### Method
- Seven experiments (E1 to E7, 16 fixtures) were run on 2026-09-26 with Claude Code 2.1.283, on Linux (WSL2,
  kernel 6.18.33.2), with bubblewrap 0.9.0 and socat 1.8.0.0.
- Each fixture was a disposable git repository with its own `.claude/settings.json`. Each run was a
  **separate headless process** (`claude -p "<prompt>" --permission-mode acceptEdits --allowedTools <tools>
  --max-turns 6 --output-format json`), launched from the lead session's shell. The lead session staying
  open doesn't affect those processes (checked by Codex against the launch records).
- **The prompts named the exact operation,** for example a specific `sed -i` or `python3 -c` command. That
  tests the control, not the model's choice of route.
- **The outcome was measured on the file,** not on the reply: the target file's SHA-256 before and after,
  the `permission_denials` field of the JSON output, and the experimental hook's own log.
- **Each case ran once.** These are existence results, not rates.
- **The evidence** is in `~/devforgeai-evidence/ENF-11/`, outside the repository: settings, hook scripts,
  diffs, file hashes, transcripts and versions, with a manifest over 120 files.
- **Only project settings were tested.** No plugin was installed or reloaded, and no interactive session was
  used. What the documentation says about plugins is marked "documented" below, and neither kind of evidence
  establishes the other.

### Documented only (not observed here)
Sources: code.claude.com `/docs/en/hooks.md`, `/hooks-guide.md`, `/permissions.md`, `/sandboxing.md` and
`/plugins/components.md`.
- A PreToolUse deny blocks "even in `bypassPermissions` mode".
- A timed-out hook "doesn't block the tool call… don't count on a stalled hook to act as a gate". Other
  non-zero exits, invalid JSON and schema errors are non-blocking errors.
- The default hook timeout is 600 seconds.
- `transcript_path` "may lag the in-memory conversation". Only Stop and SubagentStop get the final assistant
  text.
- **Plugin hooks** (`hooks/hooks.json`) are registered when the plugin loads, and fire on their events for
  the rest of the session, not only while the plugin's skill runs. **Skill-frontmatter hooks** are registered
  when the skill is invoked, and stay for the rest of the session.
- `disableAllHooks` turns hooks off; hooks from managed settings still run unless it is set there.
- None of the plugin statements above were tested: no plugin was installed or reloaded in these experiments.

## Considered options

1. Instructions only (the status quo).
2. PreToolUse hooks as the gate.
3. Permission rules.
4. The Bash sandbox.
5. Layered: tool-level controls, plus the sandbox for Bash, plus deterministic checks for detection.
6. Deterministic checks only (detect, never prevent).

## Decision outcome (proposed)

**Proposed option: 5, layered, within the limits below.** The layers:
- **Tool-level controls** stop Claude's Edit and Write tools from touching paths no skill may write. Use
  permission deny rules (E3b); a hook deny (E1) is the alternative where a rule can't express the condition.
- **The Bash sandbox** stops Bash and anything it launches from writing to protected paths, whatever the
  route (E6a, E6b), with `failIfUnavailable: true` and `allowUnsandboxedCommands: false`.
- **A deterministic checker,** the FR-018 `devforgeai check` release, detects violations in the written files
  and git history before downstream work consumes them. It never counts as prevention.

**The combination has not been observed.** Each control was tested on its own. The layered design stays a
proposal until Confirmation C1, a combined fixture, shows that the forbidden operations are all blocked
**and** the permitted ones still work.

### Consequences

- **Good:** each obligation is labelled prevented, detected or open, from evidence rather than wording. The
  write-route result (E2, E3c, E3d against E6a, E6b) explains the `sed -i` finding and gives it a concrete
  proposed prevention.
- **Good:** hooks are used only where a plain rule can't express the condition, and never as the only gate,
  because every failure mode observed (E4, E5) fails open.
- **Bad:** the sandbox is a project-wide Bash boundary. It can't be scoped to one skill, and its network
  isolation may affect `git push`, `gh` and `claude plugin eval`. That wasn't tested (C1 must).
- **Bad:** the sandbox needs bubblewrap and socat on Linux and WSL, and isn't available on native Windows.
  `failIfUnavailable: true` turns a missing sandbox into a hard failure rather than a silent skip.
- **Bad:** several obligations have no prevention at all: per-skill write sets, the inspection scope, warning
  timing and approvals. They stay open with detection only, and the ADR says so rather than implying coverage.
- **Neutral:** a plugin can't ship permission or sandbox settings (documented, not tested). The preventive
  layer is a project `.claude/settings.json` the framework recommends; see #19.

### Confirmation (required before acceptance)

- **C1, combined fixture** (headless, as in the method above). The proposed settings: permission rules for
  Edit and Write, sandbox `denyWrite` on `docs/specs/**` and `.claude/skills/devforgeai/**`, `failIfUnavailable`
  and `allowUnsandboxedCommands: false`.
  - **Forbidden, each must leave the file unchanged:** Bash `sed -i`, `>`, `python3 -c` and a computed path into
    `docs/specs/`; Edit into `.claude/skills/devforgeai/`.
  - **Permitted, each must still work:** Write and Edit to `docs/specs/arch/`; Bash reads of `docs/specs/`;
    `git status`, `git commit`, `gh issue view`, and one `claude plugin eval --case <one case>` run.
- **C2, interactive session:** repeat C1's forbidden and permitted set in an interactive session, to check the
  headless results carry over.
- **C3, override paths:** whether a user's local settings or `disableAllHooks` can switch off the rules or the
  sandbox, recorded as a documented limit either way.
- **C4, plugin hooks (only if a hook is shipped in the plugin):** install the plugin, reload it, and observe
  when its hooks register and fire. This is kept separate from C1 to C3, which don't establish it.

Each confirmation keeps its configuration, versions, transcripts and file hashes, like the experiments.

## Pros and cons of the options

### 1. Instructions only
- Good, because there's nothing to configure.
- Bad, because the recorded failures happened under exactly this: prevention is never guaranteed.

### 2. PreToolUse hooks as the gate
- Good, because a deny blocks in every permission mode (documented; E1), and a hook can express conditions
  a rule can't.
- Bad, because timeouts, crashes and missing scripts all let the call through (E4, E5), and a hook matching
  Edit misses Bash writes (E2).

### 3. Permission rules
- Good, because they're declarative and block the Edit tool (E3b), and literal Bash writes (E3, E3e).
- Bad, because interpreter writes and computed paths get through (E3c, E3d).

### 4. The Bash sandbox
- Good, because the OS blocks every Bash route tried, including interpreters and computed paths (E6a, E6b).
- Bad, because it doesn't cover Claude's own Edit and Write tools (E6d), and it's project-wide.

### 5. Layered (proposed)
- Good, because each layer covers the routes the others miss, and detection catches what prevention can't.
- Bad, because the combination is unverified until C1, and it adds project configuration.

### 6. Checks only
- Good, because it's deterministic and cheap, and it's already planned (FR-018).
- Bad, because a violation is found after it happens. For writes to protected documents, that's too late
  without git.

## Open questions

- A per-skill write set, for example the architecture skill never writing `docs/specs/prd/`, has no static
  mechanism. Is a skill-frontmatter hook, which fails open and persists for the session, acceptable as an
  added layer, or is detection enough?
- How is a human approval established in the terminal? Is the owner's PR merge the only recognized signal?
- The inspection scope and warning timing (STORY-004 AC-01 and AC-02) have no tested mechanism. What would
  count as a sufficient detection-only answer?
- Should DevForgeAI ship a recommended project `.claude/settings.json` for its users (#19), given that plugins
  can't carry permissions or sandbox settings?
