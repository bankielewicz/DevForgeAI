# ADR-004 — Project context documents: a curated knowledge layer, written after Architecture Definition and read by story and spec

## Context and problem statement

The story skill is next in the chain (ADR-002). To slice an epic into stories, and for the spec step to
design each story, a skill needs more than the epic and the architecture description (ARCH). It needs:
- the technologies in use and their allowed versions;
- where code lives;
- the conventions of each layer: user interface, application logic, server platform, APIs and data stores;
- how testing is done;
- which designs are approved.

Today none of that has a home:
- the ARCH (SPEC-003) records components, architectural questions and evidence, but "exact API fields,
  migrations and class structures belong in specs";
- ADRs record decisions, one at a time;
- policy (ADR-003) records a few configurable values;
- ADR-003 A1 names **project knowledge** as its own component ("what the product and implementation
  actually are, with sources and freshness"), but A6 limits v1 knowledge sources to accepted ADRs and
  documents the input names, and defers a broader register.

Bryan calls this missing layer the project's "constitution": `tech-stack.md`, `architecture.md`,
`source-tree.md`, `front-end.md`, `middle-tier.md`, `back-end.md`, `rdbms.md`, `api.md`, `ui-mockups.md`
and others. This ADR decides what those documents are, where they live, who writes them, how large they
may grow, and how they relate to the ARCH, ADRs and policy.

## Decision drivers

- **Stories and specs need layer-level context** without every story or spec restating it, which would
  duplicate it and let it drift.
- **Decisions stay where they are decided and approved:** ADRs, policy and the ARCH (ADR-003 A1:
  "observed practice is not policy").
- **Long documents are not reliably followed.** Bryan (2026-09-29): past a certain length, Claude ignores
  content. Anthropic's skill guidance uses progressive disclosure for the same reason: a short entry
  point, detail files one level deep, a SKILL.md body under 500 lines, and a contents list for reference
  files over 100 lines.
- **A project gets only the files it needs.** A CLI tool has no web front end, and a stateless service has
  no relational database.
- **Changes are traceable.** When the ARCH or an ADR changes, the documents that relied on it must show as
  suspect (templates README, suspect links).
- **Work today with Claude Code,** with no new runtime.

## Considered options

1. **Separate context documents, written and maintained by a new context skill that runs after
   Architecture Definition, cited by the story and spec skills.**
2. Extend the architecture skill and the ARCH to hold the conventions.
3. Put the conventions into CLAUDE.md or AGENTS.md.
4. Let each story's spec state the conventions it needs.

## Decision outcome

**Chosen option:** option 1, Bryan's choice on 2026-09-29.
- Option 2 enlarges the skill that was hardest to make reliable, and mixes per-system decisions with
  project-wide conventions.
- Option 3 loads everything into every session, with no versioning, provenance or suspect links.
- Option 4 duplicates the same conventions in every spec, where they drift.

### D1. What a context document is

A context document is **project knowledge** in ADR-003 A1's sense: the project's chosen stack,
structure and conventions, which story and spec work must follow. It records no architectural decision
of its own, but its approved conventions bind the stories and specs that rely on it. So they cite it with
`constrains` ("the document must obey this constraint", templates README §2.4). That adds STORY → CTX and
SPEC → CTX to the vocabulary's owner and target pairs (follow-up M2). Each statement is one of these:
- A **decision** it states cites where it was decided: an accepted ADR, an approved POL setting, or an
  ARCH item. The citation is a `constrains` link at that document's version. The document never restates
  a decision without citing it.
- A **convention** is a lower-weight rule the user confirmed while the context skill wrote the document,
  such as naming rules, folder conventions or a logging format. Approving the context document approves
  its conventions.
- **Observed practice** found by inspection is labelled "observed", with its source and the date read
  (ADR-003 A6). It becomes a convention only when the user confirms it.
- A choice that is significant (hard to reverse, or shared by several epics) but has no ADR gets a
  `[NEEDS ADR: …]` marker, and the context skill hands it back to Architecture Definition.

### D2. The file set

**Core documents** exist in every project that writes code:

| File | ID | Holds |
|---|---|---|
| `index.md` | CTX-001 | The entry point: each context document with its one-line purpose, the component kinds it covers, and its version. It is written by the context skill, and nothing else lives in it |
| `architecture.md` | CTX-002 | A navigable summary of the ARCH or ARCHs: each component with a one-line responsibility and a link to its CMP item, plus the cross-cutting conventions (error handling, logging, configuration, security basics). It links the ARCH; it never restates a DEC outcome |
| `tech-stack.md` | CTX-003 | Each technology in use: name, allowed version range, the components that use it, and the ADR or POL setting that chose it. The version range is what the ambiguities rule (D8) checks a library change against |
| `source-tree.md` | CTX-004 | The repository layout: where each component's code, tests, configuration and documentation live, and which folders are generated |
| `testing.md` | CTX-005 | How testing is done: test levels per component kind, naming (tests cite `STORY-NNN#AC-NN`), fixtures, how to run the tests. The method, coverage metric and threshold are cited from POL settings, never set here (D7) |

**Per-layer documents** exist only when the ARCH has a component of the matching kind. This is Bryan's
"core + per layer" rule. Each ARCH component records its `kinds` (SPEC-003 §4, from version 2), and a
component may have several, such as a service that also exposes an API. The kinds map to documents:

| Kind | A component that is… | Context documents |
|---|---|---|
| `user-interface` | a surface people use: web, desktop, mobile or CLI | `front-end.md`, `ui-mockups.md` |
| `service` | application or business logic | `middle-tier.md` |
| `platform` | background jobs, workers, integrations with external systems, hosting | `back-end.md` |
| `api` | an interface exposed to another component or to external consumers | `api.md` |
| `relational-store` | a relational database | `rdbms.md` |
| `data-store` | a non-relational store: document, key-value, object, search or cache | `datastore.md` |
| `external` | a system outside the project, such as a mandated identity platform | none of its own; `architecture.md` and `tech-stack.md` name it |

An ARCH written before SPEC-003 version 2 has no `kinds`. The context and story skills then ask which
kinds a component has (SPEC-009 ERR-08).

| File | ID | Written when the ARCH has… | Holds |
|---|---|---|---|
| `front-end.md` | CTX-011 | a `user-interface` component | Framework, structure, state, accessibility, interaction and output conventions (for a CLI: command structure, flags, output formats), and the design system |
| `middle-tier.md` | CTX-012 | a `service` component | Domain structure, service boundaries within the component, orchestration, validation and transaction conventions |
| `back-end.md` | CTX-013 | a `platform` component | Runtime, hosting and deployment conventions, jobs and queues, integration and configuration and secrets handling |
| `api.md` | CTX-014 | an `api` component | Style (REST, events, RPC), versioning, error format, authentication, pagination, and where the contracts live (specs hold each operation's exact contract) |
| `rdbms.md` | CTX-015 | a `relational-store` component | Engine and version, naming, migration tool and rules, indexing and transaction conventions |
| `datastore.md` | CTX-016 | a `data-store` component | The same as `rdbms.md`, for its store type |
| `ui-mockups.md` | CTX-017 | a `user-interface` component, CLI included | The design system reference, and the index of approved designs. The context skill builds the index from the approved-design records in stories (SPEC-009 BEH-12): each design's exports, their paths, the approval date, and the link to its Claude Design handoff bundle, which dev uses when it implements |

A new kind needs a change to SPEC-003 and `arch.schema.json`, and a row here. Its document takes the
next free CTX number from 020 upward, and it's recorded in `index.md`.

### D3. Location, naming and identity

- **Location:** all context documents live in `docs/specs/context/`, with detail files in
  `docs/specs/context/<file-name>/` (D4).
- **Names:** the fixed names above, not ID-only names. Each is a singleton per project, found by name
  from `index.md`, like `README.md`. This is a deliberate exception to the ID-only naming rule for
  skill-generated documents, which fits documents that exist many times (BRN, PRD, EPIC, STORY).
- **Identity:** each document has a frontmatter `id` with the fixed number from D2, so other documents
  can link it the usual way, for example `{id: CTX-015, relation: constrains, version: <its version>, hash: null}`.
  It carries the common provenance keys, a `version` and a `status`: draft, then approved by the user,
  and later superseded or deprecated.
- **Citations:** stories and specs cite context documents **at the document level**. Item blocks are used
  only where a skill must read a fact mechanically: `tech-stack.md` entries (name, version range, users,
  deciding source), and `source-tree.md` roots. The context templates (M2) define them.

### D4. Size and progressive disclosure

- **Loading:** a skill reads `index.md` first (at most 100 lines). It then opens only the context
  documents for the component kinds the current story touches, plus the core documents it needs.
- **Size cap:** every context document is **at most 500 lines**, the same cap as a SKILL.md (PRD-001
  NFR-001). A document longer than 100 lines starts with a contents list.
- **Detail files:** content beyond the cap, or detail only some work needs, moves into detail files in
  `docs/specs/context/<file-name>/<topic>.md`. Each is linked from its parent document with a
  one-line description of when to read it. Detail files are **one level deep** and never link further
  detail files. The same size cap and contents rule apply to them.
- **What doesn't belong:** a statement that applies to one story belongs in that story's spec, not in a
  context document.

### D5. Ownership and lifecycle

- **Writing:** a **new context skill** (for example `/devforgeai:context`) writes and maintains the
  context documents. It runs after Architecture Definition and before story, from these inputs:
  - the ARCH;
  - accepted ADRs;
  - approved policy;
  - bounded, read-only inspection of the named components (the SPEC-003 BEH-05 rules);
  - a short interview for conventions.

  The architecture skill's work is unchanged (Bryan, 2026-09-29).
- **Chain integration:** when the context skill ships, the architecture skill's handoff names the context
  step before the epic step. That is a change to the handoff text only: SPEC-003 BEH-15 and its
  `hands-off-to-epic` eval case. The handoff keeps its readiness report, names the context step before
  the epic step, and starts neither workflow itself (Bryan, 2026-09-29). Until the context skill ships,
  the current handoff stays, and the story skill's missing-context handback (SPEC-009 ERR-04) is the
  only place the chain points to the context step.
- **Reading:** the story and spec skills read context documents and never edit them. Neither do dev and
  QA. A needed change goes back to the context skill, or, when it is small and reversible, into the
  ambiguities log (D8) for review.
- **Chain position:** brainstorm → prd ⇄ architecture → **context** → epic → story → spec.
  - The epic skill doesn't need context documents.
  - Story and spec require current ones. When they're missing or suspect, the skill hands back to the
    context skill.
- **Approval:** the user approves each context document. A draft context document makes the stories
  and specs that rely on it proposals, as a draft PRD or ARCH does (SPEC-004 BEH-02).

### D6. Freshness

- **Suspect links:** each context document links the ARCH and ADRs it relies on at their versions. A
  newer version makes the link suspect, and the context skill's next run re-reviews that document.
- **Observed facts:** they carry the date they were read, and the document declares a freshness window.
  Older facts are reported as findings, not errors (ADR-003 A6).

### D7. Testing values come from policy

- **Fixed by this ADR** (Bryan, 2026-09-29): 100% of required tests pass. A failure is accepted only as a
  named exception that records the test, the reason and the approver. It is always reported apart from
  "tests passed" (ADR-003 A1). This is not a configurable pass-rate threshold.
- **Organizational policy** (ADR-003 A2), which a separate ADR adds as POL keys (M5):
  - the development method (TDD or another approach);
  - the coverage metric and threshold (Bryan's example: 95%), with its scope and exclusions;
  - how named exceptions are recorded, and who may approve them.
- **`testing.md`:** explains how to apply those settings and cites them. It restates the fixed rule
  above, but never sets a value that a POL setting defines.

### D8. The ambiguities log is the pressure relief valve

A skill doesn't stop for a small, reversible choice outside every spec obligation. It records the choice
in the work item's ambiguities log and continues. The log is `docs/specs/ambiguities/AMB-NNN.md`, one per
work item: its `work_item` names the story, or the branch when there is no story. Entries are `ENT-NN`,
and later sessions append to the same log (template `src/templates/ambiguities.md`; Bryan, 2026-09-29). Bryan's
example is a library version change within the range `tech-stack.md` allows.

It asks, never logs, about:
- anything that changes required behaviour, scope, an interface, permissions or security;
- a spec or AC obligation;
- a policy value or an approval;
- a new dependency, or a major version.

**Hard boundary:** logging never authorizes contradicting a spec, inventing a requirement or bypassing
an approval.

**Review:**
- entries are reviewed at the pull request, and QA lists the open ones;
- the user accepts an entry, which the context skill folds into the right context document, or rejects
  it, and the change is reverted.

### Consequences

- **Good:** story and spec work gets layer-level context in bounded pieces. Each skill loads only what
  a story touches, which keeps within the size limit Claude follows reliably.
- **Good:** decisions stay single-sourced in ADRs, policy and the ARCH. Context documents cite them, so a
  change shows as a suspect link.
- **Good:** small changes no longer block work (D8), and they stay reviewable.
- **Bad:** one more skill, and one more step in the chain. Mitigated: it runs once per project, then only
  when the ARCH or ADRs change.
- **Bad:** fixed names break the ID-only naming rule for this one folder (D3).
- **Bad:** layer conventions can still drift from the code. Freshness dates make drift visible, but don't
  prevent it.
- **Follow-up work this ADR requires** (each needs Bryan's yes):
  - **M2:** a template, and a schema where needed, for each context document. The same change covers:
    - `CTX` in `common.schema.json`'s document prefixes;
    - the STORY → CTX and SPEC → CTX `constrains` pairs in templates README §2.4 (D1);
    - `CTX` rows in README §1.2 and §2.1;
  - **M14:** when the context skill ships, the architecture skill's handoff names the context step (D5);
  - **M3:** the context skill's spec, then its build;
  - **M4 (done in version 2):** ARCH components carry `kinds` (SPEC-003 version 2, `arch.schema.json`,
    the architecture skill's SKL-003 version 2), mapped in D2;
  - **M5:** the testing-policy ADR (D7);
  - **M6:** a PRD-001 requirement for the context skill.

### Confirmation

**Structural** (when the templates exist):
- every context template validates against its schema;
- a document over 500 lines, or with a detail file linking another detail file, fails the context
  skill's self-check.

**Behavioural** (planned; nothing has run):
- the context skill's eval suite writes only the per-layer documents whose component kinds the fixture
  ARCH has;
- a story skill run on a fixture opens `index.md` and only the context documents for the story's
  components, observed in the run's trace;
- a suspect ARCH link makes story hand back to the context skill;
- a library change within the allowed range is logged, and a major version change is asked about.

## Pros and cons of the options

### Option 1: context documents and a context skill
- Good, because conventions have one versioned home, and decisions stay cited.
- Good, because progressive disclosure bounds what any one run loads.
- Bad, because it adds a skill and a chain step.

### Option 2: extend the architecture skill
- Good, because there's one step fewer.
- Bad, because it grows the most failure-prone skill, and SPEC-003 would change.
- Bad, because it mixes per-system decisions (the ARCH) with project-wide conventions.

### Option 3: CLAUDE.md or AGENTS.md
- Good, because it needs no new skill, and the files load automatically.
- Bad, because everything loads every session, with no version, provenance or suspect links.

### Option 4: conventions in each spec
- Good, because it needs nothing new.
- Bad, because every spec duplicates the same rules, and they drift.

## Out of scope

- The context skill's behaviour in detail (M3), the templates and schemas (M2), and the testing-policy keys (M5).
- The expert catalog (ADR-003 A7; PRD-001 FR-010, later).
- Automatic reassessment when code changes (ADR-003 A6, later).
