# ADR-005 — Testing policy: six organizational-policy keys, a fixed pass rule, named exceptions in the QA verdict, and a safe way to investigate a failing test

## Context and problem statement

PRD-001 FR-020 (must, current) asks for testing policy: "the development method, the coverage metric,
threshold, scope and exclusions, and who may approve a named test exception, as policy settings
(ADR-003), while keeping ADR-004's fixed rule that required tests pass and approved exceptions are
reported separately". Its notes add: "95% is not a framework default. The keys come from a testing-policy
ADR."

ADR-003 names these values but leaves them out of configuration contract v1:
- A2 lists "development approach (TDD or not), coverage metric, scope, exclusions and threshold,
  test-failure exceptions" as organizational policy for *later*;
- A3 supports only three keys, and its out-of-scope list includes "Settings beyond the three v1 keys".

ADR-004 D7 fixes the pass rule and says `testing.md` cites the policy settings and never sets their
values.

This ADR decides:
- the keys and their value types;
- the framework defaults;
- how the keys are validated, resolved and recorded;
- which workflows resolve them;
- where a named exception is recorded.

It extends ADR-003 by adding keys under ADR-003's own rules. It doesn't edit ADR-003.

ADR-003 also treats the development method two ways:
- **A2** makes it a policy value.
- **A8** (levels of customization) lists "TDD vs another approach" as its example of a *workflow
  variant*, because the procedure differs.

This ADR has to reconcile them.

## Decision drivers

- **FR-020's scope:**
  - organizations and projects must be able to set the method, the coverage metric, the threshold,
    scope and exclusions, and the exception approvers as policy;
  - the pass rule stays fixed.
- **ADR-003's model holds unchanged:** approved policy only; layers; A4 precedence; the A5 resolution
  line; schema-enforced types; semantic rules for what the schema can't express.
- **No invented defaults:** PRD-001 says 95% is not a framework default.
- **Each new key needs its own type check.** In `src/schemas/policy.schema.json`, `value` is untyped (`{}`)
  and each key's type comes from its own branch (`:269-387`). A key added only to the enum
  (`:220-226`) accepts any value, class, override or condition. The lead session's policy research
  confirmed this in memory on 2026-09-29.
- **A workflow that doesn't use the keys must still accept valid policy.**
  - prd and architecture validate every approved policy document against their schema copies.
  - A key they don't know makes the policy invalid, and they stop (ERR-08 / ERR-02).
  - So adding keys means updating those copies.
- **Work today** with Claude Code and Codex, with no checker (`devforgeai check` doesn't exist).

## Considered options

1. **Six organizational-policy keys.** The method key selects a procedure variant built into the dev
   step. Named exceptions are recorded in the QA verdict, and failures are investigated without touching
   the working tree.
2. The same keys, plus a separate TDD skill that replaces the dev step when `testing.method: tdd`.
3. No policy keys: testing values are conventions in each project's `testing.md`.
4. A configurable pass-rate threshold instead of named exceptions.

## Decision outcome

**Chosen option:** option 1, Bryan's approved design (2026-09-29).
- Option 2 duplicates the dev step for one ordering difference.
- Option 3 fails FR-020: an organization couldn't mandate a threshold, and conventions aren't policy
  (ADR-003 A1, "observed practice is not policy").
- Option 4 contradicts ADR-004 D7.

### D1. The development method selects a variant; it isn't a separate workflow

`testing.method` is a policy value. It *selects* one of the procedure variants built into the dev step
(Bryan, 2026-09-29):
- **`test-after`:** the code is written first. Tests follow, and every acceptance criterion is verified
  before the story is done.
- **`tdd`** (red, green, refactor): each piece of behaviour starts with a failing unit test. Then comes
  the least code that makes it pass, then refactoring while every test stays green.
- **`atdd`** (acceptance-test-driven): each acceptance criterion first gets an executable acceptance
  test, which is run and seen to fail before the code that satisfies it is written. Unit tests may come
  before or after that code.
- **`bdd`** (behaviour-driven): `atdd`, with each acceptance test written as a Given/When/Then scenario
  in the project's BDD tool, taken from the acceptance criterion's own Given/When/Then text. The tool
  is a technology in the project's `tech-stack.md`.
- **`spike-and-stabilize`:** a prototype may first be written without tests, to learn or to
  demonstrate a capability.
  - Before the work is merged into the default branch, it is either discarded or stabilized. To
    stabilize it, the required tests for its acceptance criteria are written, until the pass rule and the
    coverage threshold hold.
  - Unstabilized spike code is never merged.

The spec step orders each implementation plan's tasks for the method:
- `tdd`: a failing test before each task's code;
- `atdd` and `bdd`: the acceptance tests first;
- `spike-and-stabilize`: the spike tasks, then the stabilization tasks;
- `test-after`: code, then tests.

There is no separate skill for any method.

This reconciles ADR-003:
- the value is configuration (A8 level 1);
- the procedure difference is a variant inside one workflow (A8 level 2).

### D2. The keys

All six keys are:
- `organizational_policy` class;
- **unconditional**: `applies_when` is not allowed in v1, so they're resolved before any interview;
- **not locally overridable**: organizational-policy settings can't allow `local` (ADR-003 A4, `:155`),
  and a local-preference entry for them is ignored and reported (A3).

A project policy may override an organization setting only when that setting's `overridable_by` lists
`project`.

| Key | Value | Framework default |
|---|---|---|
| `testing.method` | `test-after`, `tdd`, `atdd`, `bdd` or `spike-and-stabilize` (D1) | `tdd` (Bryan, 2026-09-29) |
| `testing.coverage_metric` | `line` or `branch` | `line` |
| `testing.coverage_threshold` | a number from 0 to 100, the minimum coverage percentage of the scope, measured with the metric while the required tests run (definitions below) | **none**: coverage isn't enforced, and every report says "no coverage threshold set" |
| `testing.coverage_scope` | a list of repository-relative folder paths, each ending in `/`, at least one, unique | every `holds: code` root in the project's `source-tree.md` (ADR-004) |
| `testing.coverage_exclusions` | a list of repository-relative paths (a folder ends in `/`), unique; glob patterns aren't supported in v1 | no paths beyond the `generated`, `tests` and `fixtures` roots in `source-tree.md` |
| `testing.exception_approvers` | a list of people, written as in documents' `owner` fields, at least one, unique | the story's `owner` |

Names follow ADR-003's two-level form (`<section>.<name>`). One threshold covers the whole scope in v1.

**Definitions** (Bryan, 2026-09-29):
- **Required tests** are every test run by the commands in the "Running the tests" section of the
  project's `testing.md` (ADR-004), at every level: unit, integration, end to end, and any other. The
  pass rule of ADR-004 D7 applies to all of them. A failure anywhere in those runs counts, not only in the
  tests a story adds.
- **Coverage** is measured by running those same commands over `testing.coverage_scope`, less
  `testing.coverage_exclusions`, with `testing.coverage_metric`. The result is one percentage for the
  whole scope, compared with `testing.coverage_threshold`.

### D3. Validation

- **Schema:** `policy.schema.json` gets one branch per key, in the pattern of the existing branches
  (`:269-387`). Each branch fixes:
  - the value type above;
  - `class: organizational_policy`;
  - no `applies_when`;
  - `overridable_by` limited to `project`.
- **SV-08 (new; stop):** at most one active setting per `testing.*` key per document. It extends SV-03's
  rule for single-valued keys. SV-07 is taken (ADR-003 `:162`), so the new rule starts at SV-08. It is
  enforced by the shared `validate_policy.py`, and a violation is labelled `SV-08`.
- Everything else is unchanged: approved documents only, at most one approved document per scope (SV-02),
  deprecated settings ignored (SV-05), and the calendar check.

### D4. Resolution and recording

**Which layer wins:** ADR-003 A4, unchanged. The most specific layer that is allowed to set the key wins:
- a project setting wins over an organization setting only when the organization setting allows `project`;
- otherwise the organization setting wins;
- with no setting, the framework default applies.

**The resolution line** (ADR-003 A5) gets one entry per testing key, after the existing entries, in the
order of the table in D2:
- a setting: `<key>=<value> (POL-NNN#SET-NN)`;
- a default: `<key>=<value> (default)`.

Value formats:
- **List values** are joined with `,` and no spaces, for example
  `testing.coverage_scope=src/,lib/ (POL-001#SET-04)`;
- **The threshold** is written as a number, or `none`, for example `testing.coverage_threshold=90
  (POL-001#SET-03)` and `testing.coverage_threshold=none (default)`;
- **The defaults** are written:
  - `testing.coverage_scope=code roots (default)`;
  - `testing.coverage_exclusions=generated,tests,fixtures roots (default)`;
  - `testing.exception_approvers=story owner (default)`.

The line never contains `|`, as for every entry.

**Links:**
- A context document cites a testing setting it states with `constrains`, as ADR-004 D1 requires for
  every decision it states.
- Every other document records an applied setting as ADR-003 A5 says: `informed_by`, at the policy
  document's version.

When the policy changes, either link becomes suspect by the existing mechanism.

**In the shared `policy.md`:** the text says "a workflow that resolves the testing keys". It names no
skill, so the file stays skill-neutral and byte-identical across skills.

### D5. Which workflows resolve the keys

- **The context skill** resolves all six. It cites each resolved value in `testing.md`, as a
  `POL-NNN#SET-NN` citation with a `constrains` link, or as "(default)". It lists the keys on its
  resolution line. It never sets a value.
- **Later, the spec, dev and QA steps apply them.** Spec plans the test levels and the task order the
  method needs (D1). Dev follows the method and D7. QA checks coverage against the threshold, each
  failing required test against the exception records (D6), and, for `spike-and-stabilize`, that the
  work was stabilized.
- **prd and architecture only validate them.**
  - Their schema copies accept the keys, so a policy that sets them stays valid.
  - They don't resolve them, and their resolution lines keep their current entries until FR-012.
- **brainstorm, epic and story** don't read them. Story's Definition of Done cites `testing.md`
  (SPEC-009 BEH-13).

### D6. Named exceptions are recorded in the QA verdict

ADR-004 D7 fixes the rule: 100% of the required tests pass, and a failure is accepted only as a named
exception, always reported apart from "tests passed".

**Each exception records exactly these fields:**
- the test (its name, or `<file>::<name>`);
- what it covers (`STORY-NNN#AC-NN` or `SPEC-NNN#VER-NN`);
- the reason;
- the approver;
- the date.

**The approver** must be one of the resolved `testing.exception_approvers`.

**Where it goes:** the QA verdict (SPEC-008 §4) lists the accepted exceptions in their own block, after
its `Checks:` line:

```text
Accepted test exceptions:
- <test> covers <STORY-NNN#AC-NN or SPEC-NNN#VER-NN>: <reason>. Approved by <approver> on <YYYY-MM-DD>
```

A verdict with no exceptions omits the block.
- The approver's approval is their own words in the pull request; the QA step records it and never
  infers it.
- An exception without an allowed approver makes the verdict `failed`.

### D7. Investigating a failing test never touches the working tree

A fixed framework rule, not a policy value (Bryan, 2026-09-29).

**Why:** a session that meets a failing test often wants to know whether its own change caused it. If
it answers by restoring old files into the working tree, uncommitted work is lost. The ways it does
this: `git checkout -- <path>`, `git restore`, `git stash`, `git reset`, `git clean`, or downloading
the files again.

This procedure answers the same question safely:

1. **Baseline first.** Before the first change for a work item, run the required tests on the unchanged
   branch, and record the results with the commit they ran on. A later failure is compared with this
   record first.
2. **Compare without touching the working tree.** When the old code has to be run or read:
   - use a separate, disposable worktree at the baseline commit (`git worktree add --detach <path>
     <commit>`), and remove it afterwards;
   - or read the old files with `git show <commit>:<path>`.

   Never restore, check out, stash, reset, clean or download files into the working tree to investigate
   a failure.
3. **Commit before each full run.** Before each full run of the required tests, commit the work in
   progress on the work item's branch, so that everything stays recoverable (`git reflog`).
4. **A failure found in the baseline is still a failure.** It is reported as present before the change,
   so it isn't blamed on the change, but the pass rule still applies to it: it is fixed, or accepted as a
   named exception (D6).

`testing.md` restates this rule for every project, and the dev step implements it.

## Pros and cons of the options

### Option 1: six keys; the method selects a dev variant; exceptions in the QA verdict
- Good, because it uses ADR-003's layers, precedence and recording unchanged.
- Good, because one dev workflow covers both methods.
- Bad, because prd and architecture carry keys they never resolve.

### Option 2: a separate TDD skill
- Good, because each skill stays simpler.
- Bad, because two dev workflows must stay in step, and they differ only in task order.

### Option 3: conventions in `testing.md` only
- Good, because nothing changes in policy.
- Bad, because FR-020 requires policy settings, and an organization couldn't mandate anything.

### Option 4: a configurable pass-rate threshold
- Good, because it's one number.
- Bad, because ADR-004 D7 fixes 100%, and hidden failures are what named exceptions prevent.

## Out of scope

- Deployment approval, which is also on ADR-003 A2's "later" list but outside FR-020.
- The pass rate, which ADR-004 D7 fixes.
- Coverage that depends on operating context (`applies_when`), per-component thresholds, and any other
  test metric (mutation, complexity).
- The dev and QA workflows themselves: SPEC-008 (QA) and a later dev spec apply these keys.
- A spike for one story only, while the project's method stays the same. That is a story-step matter:
  SPEC-009's slicing already names spikes, and its next version can define a spike story form.
