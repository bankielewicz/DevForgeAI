# Product brief: Shiftwell

Synthetic fixture. Not a real product and not a real decision.

## Scope of this slice

A small web application that lets a care agency publish shifts and lets carers claim them. The slice covers publishing, claiming, and a per-agency view of who is booked. Payroll, invoicing and messaging are out of scope for this slice.

## Requirements

| ID | Requirement |
| --- | --- |
| REQ-001 | An agency coordinator can publish a shift with a date, time window, location and required qualification. |
| REQ-002 | A carer sees only shifts they are qualified for and may claim one; a claimed shift is no longer claimable by anyone else. |
| REQ-003 | A coordinator can see, per shift, who claimed it and when. |
| REQ-004 | Each agency's data is visible only to that agency's users. |

## Nonfunctional requirements

| ID | Requirement |
| --- | --- |
| NFR-001 | Two carers claiming the same shift at the same moment must not both succeed. The losing claim gets a clear message. |
| NFR-002 | The agency boundary in REQ-004 is a hard requirement and must be verifiable, not merely conventional. |
| NFR-003 | The team is two developers who both know C# well and neither of whom has run Kubernetes. Operational complexity is a real cost. |
| NFR-004 | Deployment target is a single Linux VM the agency already rents. |
