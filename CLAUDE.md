# DevForgeAI

A spec-driven development framework. The workflow is brainstorm → prd ⇄ architecture → epic → story → spec (ADR-002),
and each step is a skill in the `devforgeai` Claude Code plugin.

## Layout

| Path | What it is |
|---|---|
| `src/claude/DevForgeAI/` | Plugin source: `.claude-plugin/plugin.json`, `skills/<name>/`, `evals/<name>/` |
| `src/schemas/` | Canonical JSON Schemas. Never deployed |
| `src/staging/templates/` | Document templates not yet moved into their skill, plus the conventions README |
| `docs/specs/` | Project documents (PRD, epic, story, spec, ADR, handoffs), written by skills or by hand. `docs/specs/policy/` holds approved organization and project policy (ADR-003) |
| `.claude/skills/devforgeai/` | Operational copy of the plugin, generated by deploy. Gitignored |
| `.claude/worktrees/` | One worktree per story. Gitignored |

## Rules

- Edit only `src/`. Never edit `.claude/skills/devforgeai/`; deploy overwrites it.
- No symlinks under `src/`.
- A skill's **own resources** (instructions, templates, references, scripts) live inside its skill or
  plugin folder and are referenced through `${CLAUDE_SKILL_DIR}` or `${CLAUDE_PLUGIN_ROOT}`, never through
  `src/` or `src/staging/`. The **project documents** a skill works on (BRNs, PRDs, ADRs, policy) are
  read and written in the project's `docs/specs/`, relative to the working directory.
- A document template lives in the `assets/` of the skill that produces it. A skill ships a schema
  only if something in it executes one, as an unchanged copy of `src/schemas/` files.
- Skill-generated documents are named by ID only (`BRN-001.md`, `PRD-001.md`), with the topic in
  `title`, in singular folders (`docs/specs/brainstorm/`, `prd/`, `epic/`, `story/`, `spec/`, `adr/`).
- Follow the provenance rules in `src/staging/templates/README.md`: stable IDs, `upstream` links,
  `[NEEDS CLARIFICATION: …]` for unknowns, and a `version` bump plus Change Log entry when items change.
  Never invent IDs or links.

## Building a skill

Follow `docs/specs/adr/ADR-001.md`: one worktree and branch
(`story/STORY-NNN-<slug>`) per story, deploy before starting the session, validate the deployed copy.

- Run `claude plugin eval` from a plain terminal in the worktree root. Claude Code worktree
  sessions refuse any command containing `claude plugin eval`. The session then reads
  `.claude/skills/devforgeai/evals/results/<timestamp>/aggregate-result.json`.
- Commit messages reference the story ID (`STORY-NNN: …`).
- When documents disagree: SPEC > STORY > ADR > templates. Propose changes to specs; don't edit them
  unless the user agrees.

## Tracking work

Track the current story's work in TASKS.md at the worktree root (gitignored).
Only the lead session edits it; subagents report results, and the lead ticks
an item after checking the evidence. Tag each item with the spec ID it serves
(AC-, VER-, BEH-). Record durable outcomes in the story's Definition of Done
and in commit messages, not in TASKS.md.

Work that isn't scheduled goes in one of two backlogs, never in TASKS.md:

- **Product backlog:** PRD requirements with `release: later` (SPEC-002 §5). A new
  capability becomes a requirement first; issue #22 lists the named capabilities
  that aren't requirements yet.
- **Engineering backlog:** GitHub issues labelled `backlog` (`gh issue list --label backlog`).
  Issues labelled `needs-decision` wait on the owner and list the options. Reference
  the issue in the commit or PR that resolves it (`Closes #NN`).
